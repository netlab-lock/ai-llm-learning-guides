🔄 连续批处理 (Continuous Batching / Iteration-Level Scheduling)

本节目标：深入理解 vLLM 提出的连续批处理技术——在每个 iteration（解码步）级别调度请求，实现 GPU 零闲置。掌握其调度器设计、与 PagedAttention 的配合机制，以及生产环境中的性能调优方法。

1. 核心思想：从请求级调度到 Iteration 级调度

连续批处理（Continuous Batching），也称为 Iteration-Level Scheduling，是 vLLM 论文（Kwon et al., 2023）提出的核心调度创新。其本质洞察是：GPU 闲置的根源不在于没有请求可处理，而在于调度粒度太粗——传统静态批处理以整个请求的生命周期为调度单位，导致短请求完成后 GPU 空等长请求。

理解这一设计动机需要从 GPU 的利用率公式出发。设一个 batch 中有 N 个请求，各请求的生成长度为 L₁, L₂, ..., Lₙ，则静态批处理的总计算时间为 T_total = max(L₁, ..., Lₙ) × t_decode，其中 t_decode 是每步解码延迟。而各请求实际需要的计算时间为 Σ(Lᵢ × t_decode)。定义 GPU 利用率 η 为：

η = Σ(Lᵢ) / (N × max(Lᵢ))

当请求长度差异越大（即 max(Lᵢ) >> mean(Lᵢ)），η 越低。例如 batch_size=4，请求长度为 [10, 10, 10, 100]，则 η = 130 / (4×100) = 32.5%——超过 2/3 的算力被浪费。连续批处理通过动态替换已完成请求，使 η 始终接近 100%。

调度粒度对比

传统批处理 (请求级调度): Batch 1: [A, B, C] ──运行──▶ 全部完成 ──▶ Batch 2: [D, E, F] 调度粒度: 请求生命周期 ✗ 短请求 A 完成后空等 C ✗ GPU 在等待期间利用率降至 0 连续批处理 (iteration 级调度): Step 1: [A, B, C] → A 完成, D 加入 Step 2: [B, C, D] → C 完成, E 加入 Step 3: [B, D, E] → B 完成, F 加入 Step 4: [D, E, F] → ... 调度粒度: 每个 decode step ✓ 每步完成后立即调度新请求 ✓ GPU 始终有完整的 batch 可处理

这个设计的关键洞察是：LLM 推理的 Decode 阶段天然适合 iteration 级调度。因为 Decode 是逐 token 自回归的，每个 step 的计算量完全一致（都是对当前 batch 中所有请求各预测一个 token），不存在训练中不同样本计算量不同的问题。这意味着我们可以在任何 step 边界安全地增减请求，不会破坏计算的正确性。

为什么 Prefill 不能直接 Iteration 级调度？ Prefill 阶段需要一次性处理所有输入 token（并行注意力计算），如果像 Decode 一样逐 step 调度，每个新加入的请求都需要完整重算整个 batch 的注意力矩阵，复杂度从 O(n²) 退化为 O(n³)。这就是为什么 Chunked Prefill（下一节）被提出——将 Prefill 拆分为固定大小的 chunk，使其能与 Decode 交错执行。
与 Orca 的理论联系： 连续批处理并非全新概念。Orca (Yu et al., 2022) 首次提出了 Iteration-Level Scheduling 的理论框架，证明在迭代式计算中，以 iteration 为调度单位可以消除\"队头阻塞\"（Head-of-Line Blocking）。vLLM 的创新在于将其与 PagedAttention 结合，解决了 Orca 中内存碎片化的问题。另一类似实现是 TensorRT-LLM 的 \"Inflight Batching\" 和 DeepSpeed-FastGen 的 \"Dynamic Split-Fuse\"。

2. 工作流程：四步循环调度

连续批处理在每个 decode step 执行一个精密的四步循环。理解这个流程是理解 vLLM 调度器实现的关键。Scheduler 在每个 step 的决策逻辑如下：

Step 1: 移除已完成请求

遍历当前 batch 中所有活跃请求，检查停止条件——是否生成了 EOS token 或达到了 max_tokens 限制。对已完成的请求，执行资源回收：释放其占占用的 KV Cache block（通过 BlockManager 标记为空闲），释放序列组（Sequence Group）的内存，并将结果返回给调用方。

Step 2: 从等待队列补充新请求

当 Step 1 释放了位置后，Scheduler 检查 waiting_queue。对于每个候选请求，计算其 Prefill 所需的 KV Cache block 数：blocks_needed = ⌈input_length / block_size⌉。如果有足够的空闲 block（由 BlockManager 追踪），则将请求加入当前 batch，并为其分配初始 KV Cache block。如果没有足够 block，该请求继续在队列中等待——这是连续批处理的一个关键限制：不能部分执行 Prefill。

Step 3: 执行一步 Decode

将当前 batch 中所有活跃请求送入 ModelRunner，执行一步自回归 decode。对于新加入的请求（Step 2 中加入的），这一步实际上是它们的 Prefill + 第一步 Decode：ModelRunner 先对新请求的所有输入 token 执行并行注意力计算（Prefill），生成初始 KV Cache；然后对所有请求（包括新请求）统一执行一步 token 生成。

Step 4: 检查停止条件并循环

更新每个请求的已生成 token 数，检查是否触发停止条件。将未完成请求标记为继续，已完成的请求返回结果。然后回到 Step 1，开始下一个 step 的调度。

每个 Decode Step 的调度流程: ┌──────────────────────────────────────────────────────┐ │ Scheduler Loop │ │ │ │ Step 1: Sweep Finished │ │ for seq in running_batch: │ │ if seq.is_finished(): │ │ free_kv_cache(seq) │ │ running_batch.remove(seq) │ │ send_response(seq.output) │ │ │ │ Step 2: Fill from Waiting Queue │ │ free_blocks = block_manager.get_free_block_count()│ │ for req in waiting_queue: │ │ need = ceil(req.input_len / BLOCK_SIZE) │ │ if need <= free_blocks: │ │ allocate_blocks(req, need) │ │ running_batch.add(req) │ │ free_blocks -= need │ │ │ │ Step 3: Execute One Decode Step │ │ outputs = model_runner.step(running_batch) │ │ # 对 Prefill 请求: 并行处理输入 │ │ # 对所有请求: 一步自回归 decode │ │ │ │ Step 4: Check & Loop │ │ for seq in running_batch: │ │ seq.update(output_token) │ │ goto Step 1 │ └──────────────────────────────────────────────────────┘ 等待队列: [D, E, F, G, ...] 当前 batch (示例): ┌───────────────────────────────────────────────┐ │ A (step 5/10) B (step 3/20) C (step 8/50) │ │ ▓▓▓▓▓░░░░░ ▓▓▓░░░░░░░░░ ▓▓▓▓▓▓▓▓░░░░░ │ └───────────────────────────────────────────────┘ Step 完成后: A 完成 → 释放 8 blocks → D 需要 3 blocks → D 加入 B 继续 decode → step 4/20 C 继续 decode → step 9/50

这个工作流程的关键设计决策在于：Prefill 和 Decode 在同一个 step 中交错执行。当新请求 D 在 Step 2 加入后，Step 3 需要先对 D 做 Prefill（一次性处理其所有输入 token），然后和已有请求一起做一步 Decode。这种\"混合 step\"的实现避免了 Prefill 阻塞 Decode 的问题——但前提是 Prefill 的输入不能太长（否则会拖慢整个 step）。这正是 Chunked Prefill 要解决的问题。

vLLM 中的实际代码路径： 在 vLLM v0.4+ 中，Scheduler 类的 _schedule() 方法实现了上述四步循环。ScheduleOutputs 对象包含三个列表：scheduled_seq_groups（本轮执行的序列组）、blocks_to_swap_in（需要从 CPU 换入 GPU 的 block）、blocks_to_swap_out（需要从 GPU 换出到 CPU 的 block）。BlockManager 使用 Copy-on-Write 机制支持序列分叉（如 Beam Search 场景），fork() 操作共享相同前缀的 block，swap_out() 在显存不足时将 block 临时换出到 CPU。

3. 性能提升：量化分析与实测数据

连续批处理的性能提升不是理论假设，而是在多个维度上有可量化的显著改进。理解这些数字背后的原因对于生产环境容量规划至关重要。

吞吐量的提升来源于两个机制叠加：(1) GPU 消除闲置后理论利用率从 ~40% 提升到 ~80%，贡献约 2x；(2) 高利用率允许更大的有效 batch_size（因为请求即时进出，不需要凑齐固定数量才启动），又贡献约 1.5-2x。两者相乘得到 3-4x 的吞吐提升。

具体到模型规模，吞吐提升倍数与模型的 Decode 计算模式密切相关。对于小模型（如 7B 参数），Decode 阶段是 memory-bound（受内存带宽限制），batch_size 增大可以更充分地利用 HBM 带宽，因此连续批处理的提升更显著（3-4x）。对于大模型（如 70B+），Decode 趋近于 compute-bound，batch_size 增大的边际收益递减，提升约为 2-3x。

延迟分布分析

连续批处理对延迟的改善不仅体现在平均值上，更重要的是延迟分布的形状。在静态批处理中，延迟分布是双峰的——短请求的延迟取决于 batch 中最长请求的长度，因此即使是短输出也有一个高延迟的\"地板\"。连续批处理消除了这个地板效应，使延迟分布变为单峰且与请求实际长度成正比。

在实际部署中（以 ShareGPT 数据集为基准，vLLM 论文的评测设置），连续批处理在不同负载下的表现如下：当 QPS（每秒请求数）从 1 增加到 20 时，静态批处理的 p99 TTFT（首 token 时间）从 150ms 飙升到 12s（因为请求堆积在队列中等待凑满 batch），而连续批处理的 p99 TTFT 始终保持在 200-400ms 区间（因为新请求可以立即加入当前 batch）。

性能陷阱：Prefill 延迟累积 连续批处理虽然解决了 Decode 阶段的调度问题，但引入了新的延迟来源——Prefill 阻塞。当新请求在 Step 2 加入后，Step 3 需要先执行 Prefill（处理该请求的所有输入 token），这会延长该 step 的执行时间。如果一个 step 中有多个新请求同时加入，它们的 Prefill 会串行执行（因为 GPU 需要依次处理每个请求的输入），导致已有 Decode 请求的延迟增加。这就是 \"Prefill Interference\" 问题，Chunked Prefill（下一节）通过将 Prefill 拆分为小 chunk 来缓解此问题。
性能瓶颈的 Roofline 分析： 从 Roofline 模型看，Decode 阶段的算术强度（Arithmetic Intensity）决定了连续批处理能压榨多少性能。对于 LLaMA-7B (d=4096, 32层, 32头)，每步 decode 的 FLOPs 约为 2×7B = 14 GFLOPs（忽略注意力的小量），内存访问量为模型参数量（KV Cache 命中时只需读取参数，不重复读取 KV Cache）。A100 的 HBM 带宽为 2 TB/s，因此单请求的 t_decode ≈ 14GB / 2TB/s ≈ 7ms。当 batch_size=32 时，GPU 可以利用更宽的内存带宽（batch 越大，参数读取被更多请求共享），t_decode 降低到约 4ms。连续批处理通过保持高 batch_size，确保始终运行在 Roofline 的平坦区域（带宽充分利用），这就是为什么吞吐提升显著。

4. 与 PagedAttention 的协同设计

连续批处理和 PagedAttention 是 vLLM 的两大核心创新，它们分别解决推理系统的两个独立瓶颈：计算利用率和内存利用率。两者必须协同工作——连续批处理需要动态分配和回收 KV Cache，而 PagedAttention 提供了无碎片的细粒度内存管理。

内存碎片：连续分配的致命问题

理解为什么需要 PagedAttention，首先要理解传统 KV Cache 分配的内存碎片问题。在连续批处理中，每个请求在任意时刻都可能需要写入新的 KV Cache（每生成一个 token 就需要存储该 token 的 K 和 V）。如果采用连续内存分配（预先分配 max_length 的空间），会产生两种碎片：

内部碎片 (Internal Fragmentation)：预分配空间按 max_length 计算，但实际生成长度通常远小于此。实验数据显示，ShareGPT 数据集中 50% 的请求实际生成长度不足 max_length 的 20%。公式化表示：设请求 i 预分配空间为 M_max，实际使用为 Mᵢ，则浪费率 = 1 - Mᵢ/M_max。对所有请求平均，传统方式的内存浪费率可达 60-80%。

外部碎片 (External Fragmentation)：在连续批处理动态添加/移除请求的过程中，不同请求的完成时间不同，释放的内存块大小不一且位置不连续。经过一段时间运行后，即使总空闲内存足够容纳新请求，也可能找不到一块足够大的连续空间。

PagedAttention 的解决方案

PagedAttention 借鉴操作系统的虚拟内存分页机制，将 KV Cache 分解为固定大小的 block（默认 BLOCK_SIZE=16 个 token）。每个请求维护一个 block table，记录逻辑 block 到物理 block 的映射关系。核心公式：

物理 block 数 = ⌈序列长度 / BLOCK_SIZE⌉ 内存浪费率 ≤ BLOCK_SIZE / (2 × 平均序列长度)

当 BLOCK_SIZE=16、平均序列长度=512 token 时，浪费率 ≤ 1.56%，远低于连续分配的 60-80%。而且因为所有 block 大小相同，不存在外部碎片——任何空闲 block 都可以被任何请求使用。

协同工作机制

连续批处理和 PagedAttention 的配合体现在每个 step 的内存操作中：

PagedAttention 的性能陷阱： 分页引入了一次间接寻址开销——GPU kernel 在计算注意力时需要通过 block table 查找物理地址，这比直接指针访问略慢。在 FlashAttention v2 的集成中，vLLM 的 paged attention kernel 通过 shared memory 缓存 block table 条目，将间接寻址的开销控制在 2-3% 以内。但如果 block_size 设置过小（如 1），block table 变大，间接寻址开销显著增加。推荐 BLOCK_SIZE=16 作为最佳平衡点。
vLLM 参数调优： 在生产环境中，以下参数直接影响连续批处理的性能：gpu_memory_utilization（默认 0.9，控制显存用于 KV Cache 的比例）、max_num_seqs（最大并发请求数，默认 256）、max_num_batched_tokens（每步最大 token 数，默认 2048，决定 Prefill 的并行度）。增大 max_num_batched_tokens 可以提高 Prefill 吞吐但会增加 Decode 延迟，需要根据工作负载的 Prefill/Decode 比例来调整。

5. 失败模式与调试方法

连续批处理在生产环境中会遇到多种失败模式。理解这些陷阱是构建稳定推理服务的必要条件。

5.1 OOM 与显存压力

虽然 PagedAttention 消除了内存碎片，但连续批处理本身可能导致显存超订（Over-subscription）：当大量请求同时涌入时，Scheduler 可能接受了超过显存承载力的请求数。BlockManager 的 swap-to-CPU 机制可以缓解，但 CPU-GPU 数据传输的延迟（PCIe 4.0 x16 约 32 GB/s）会导致 step 延迟从 ~4ms 飙升到 ~50ms。

诊断方法：监控 vllm:block_cache_usage_perc 指标。当使用率持续 > 95% 时，说明显存压力过大。此时应降低 max_num_seqs 或启用 enable_chunked_prefill 以减少单次 Prefill 的显存需求。

5.2 长输入导致的 Decode 延迟尖刺

当新请求的输入很长（如 2048 token），其 Prefill 会阻塞整个 batch 的 Decode。假设 batch_size=64，每个 Decode step 约 4ms；但一个 2048 token 的 Prefill 需要约 100ms（注意力矩阵计算），导致该 step 内其他 63 个 Decode 请求的延迟从 4ms 增加到 100ms——这是连续批处理最严重的延迟退化场景。

解决方案：启用 Chunked Prefill（vLLM 0.4+ 支持），将长 Prefill 拆分为 256-token 的 chunk，每执行一个 chunk 后检查是否有更高优先级的 Decode 请求需要处理。这种抢占式调度将延迟尖刺从 100ms 降低到 ~10ms。

5.3 请求饥饿 (Starvation)

当持续有高优先级请求到达时，低优先级请求可能长时间滞留在 waiting_queue 中。连续批处理的 FIFO 调度策略不保证公平性——如果一个长请求在队列头部，后续短请求即使只需 1 token 也会被阻塞（因为长请求的 Prefill 占用了所有可用 block）。

解决方案：vLLM 实现了基于 token 预算的调度——每个请求有一个 max_tokens 预算，Scheduler 优先调度预算小的请求（类似 Shortest-Job-First）。TensorRT-LLM 则支持设置 per-request 的优先级和超时时间，确保公平性。

5.4 KV Cache 写入冲突

在连续批处理中，同一 step 内可能有多个请求同时完成 Prefill 和开始 Decode。如果这些请求的 KV Cache block 分配存在竞争（BlockManager 的锁争用），会导致调度器延迟。在高并发（>100 QPS）场景下，这种锁争用可能成为瓶颈。

诊断方法：使用 nvidia-smi dmon 观察 GPU 利用率波动。如果出现周期性利用率归零（每 100ms 一个 gap），很可能是 BlockManager 锁争用或 GC 停顿。vLLM 通过无锁数据结构和 pre-allocation 策略缓解此问题。

连续批处理的替代方案对比： 除了连续批处理，还有几种不同的调度策略各有优劣：(1) Static Batching：最简单但 GPU 利用率最低，适合离线批量推理；(2) Dynamic Batching（Triton Server）：以请求为单位调度，在每个请求完成后才接受新请求，实现简单但仍有 GPU 空等；(3) Dynamic Split-Fuse（DeepSpeed）：将长请求拆分为固定大小的 chunk，在 chunk 粒度上调度，进一步减少延迟方差但增加调度开销；(4) Disaggregated Serving（Splitwise, Mooncake）：将 Prefill 和 Decode 分离到不同 GPU，彻底消除 Prefill 对 Decode 的干扰，但需要更多硬件。连续批处理是目前开源方案中综合最优的选择，但在长输入场景下 Chunked Prefill 或 Disaggregated Serving 更有优势。

6. 实现参考：vLLM Scheduler 核心代码

以下是 vLLM 调度器的简化实现，展示连续批处理的核心逻辑。理解这段代码有助于在需要定制调度策略时进行修改。

# 简化的 vLLM Scheduler 核心逻辑 (基于 vLLM 0.4.x 架构)
class Scheduler:
    def __init__(self, config, cache_config):
        self.waiting = deque()        # 等待队列
        self.running = deque()        # 正在执行的 batch
        self.swapped = {}             # 被换出到 CPU 的请求
        self.block_manager = BlockManager(
            num_gpu_blocks=cache_config.num_gpu_blocks,
            block_size=BLOCK_SIZE,    # 默认 16 tokens
        )
    
    def schedule(self) -> SchedulerOutputs:
        """每个 decode step 调用一次"""
        
        # ===== Step 1: 处理已完成请求，释放资源 =====
        for seq_group in list(self.running):
            if seq_group.is_finished():
                self.running.remove(seq_group)
                self.block_manager.free(seq_group)  # 回收 KV Cache blocks
        
        # ===== Step 2: 从等待队列补充新请求 =====
        # 先处理被换出的请求（swap_in）
        self._schedule_swapped()
        
        # 然后处理等待队列中的新请求
        self._schedule_waiting()
        
        # ===== Step 3: 构建本 step 的输入 =====
        # 当前 batch = running 中的所有请求
        # 新加入的请求需要 Prefill，已有请求继续 Decode
        return SchedulerOutputs(
            scheduled_seq_groups=self.running,
            blocks_to_copy=self.block_manager.get_blocks_to_copy(),
        )
    
    def _schedule_waiting(self):
        """从 waiting 队列中选择请求加入 running batch"""
        while self.waiting:
            seq_group = self.waiting[0]
            
            # 计算 Prefill 需要的 block 数
            num_blocks = self.block_manager.get_num_required_blocks(seq_group)
            
            # 检查是否有足够空闲 block
            if self.block_manager.can_allocate(seq_group):
                # 分配 block 并加入 running
                self.waiting.popleft()
                self.block_manager.allocate(seq_group)
                self.running.append(seq_group)
            else:
                # 显存不足，无法接受更多请求
                break
    
    def _schedule_swapped(self):
        """尝试将被换出的请求换回 GPU"""
        for seq_group in list(self.swapped.values()):
            if self.block_manager.can_swap_in(seq_group):
                self.block_manager.swap_in(seq_group)
                self.running.append(seq_group)
                del self.swapped[seq_group.request_id]
            else:
                break

上述代码展示了连续批处理的核心循环。在实际 vLLM 实现中，还需要处理：(1) Chunked Prefill：如果启用了 chunked_prefill，_schedule_waiting 会将长 Prefill 拆分为 chunk，限制每步处理的 Prefill token 数不超过 max_num_batched_tokens；(2) Preemption：当显存极度不足时，Scheduler 需要将 running batch 中的最旧请求 swap out 或 recompute（丢弃 KV Cache，重新 Prefill）；(3) Prefix Caching：如果新请求的输入前缀与某个已完成请求共享，可以复用其 KV Cache block，避免重复计算。

✅ 参考答案与详解
  1. 加速比推导: 设请求长度 L ~ Exp(λ)，均值 μ = 1/λ。静态批处理 batch 中 N 个请求的期望最大长度为 E[max(L₁,...,Lₙ)] ≈ μ × H_N，其中 H_N 是调和数（≈ ln(N) + γ）。连续批处理每步都有完整 batch，等效吞吐 ∝ N，静态批处理吞吐 ∝ N / H_N。因此加速比 ≈ H_N ≈ ln(N) + γ。当 N=8 时，H_8 ≈ 2.7，即连续批处理加速约 2.7x，与实测 2-4x 一致。
  2. 容量规划: 每个请求生成 100 token 约需 100 × 4ms = 400ms (batch=64 时 t_decode≈4ms)。50 QPS × 0.4s = 20 个并发请求。单个 A100 80GB 运行 LLaMA-7B 时 KV Cache 约需 0.5GB/请求，20 并发需 10GB KV Cache + 14GB 模型 = 24GB。考虑峰值余量（3x），建议 1 张 A100 即可满足，但为保证 p99 延迟建议预留 2 张。
  3. 实验指导: 在 vLLM 启动参数中分别设置 --enable-chunked-prefill 和 --disable-chunked-prefill，用同一组包含 2048-token 长输入的请求测试。预期结果：关闭时长输入会导致其他 Decode 请求延迟尖刺（100ms+），开启后尖刺降低到 chunk_size × t_decode_per_token ≈ 256 × 0.05ms ≈ 13ms。用 wandb 或 prometheus 记录延迟分布对比。
