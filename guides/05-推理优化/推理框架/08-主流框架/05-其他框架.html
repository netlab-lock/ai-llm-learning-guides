一、TGI（Text Generation Inference） ⚠️ 维护模式

核心洞察：TGI 是 Hugging Face 官方开发的推理框架，Rust 核心实现高性能。但 2026 年初 HuggingFace 宣布其进入维护模式（仅接受 bug 修复），推荐新项目迁移至 vLLM 或 SGLang。

⚠️ 2026年重要变更：HuggingFace 已于 2026 年初宣布 TGI 进入维护模式，推荐迁移至 vLLM、SGLang 或 llama.cpp。

量化分析：TGI 的性能数据（Llama-3-8B, A100 80GB）：

指标TGI v1.4vLLM v0.4SGLang v0.3
Decode 延迟7.2ms5.8ms4.9ms
Prefill 吞吐3200 tok/s4100 tok/s4800 tok/s
并发请求数128256512
GPU 显存占用15.2GB14.8GB15.0GB
💡 实用技巧：TGI 的 LoRA 热切换是其独特优势——运行时动态加载不同 adapter 到同一基座模型。每个 adapter 约 500MB，切换 <1s，适合多租户场景。但新项目建议直接用 vLLM（已支持 LoRA）。
⚠️ 注意事项：TGI 的最大并发请求数受 Rust tokio 运行时限制，默认 128。超出后请求排队，延迟线性增长。生产环境需要部署多个实例 + 负载均衡。

二、LMDeploy

核心洞察：LMDeploy 是 InternLM 团队开发的推理框架，核心优势在于 TurboMind C++ 引擎的极致性能和 W4A16 量化技术。对中文模型有特别优化，在中文场景下性能优于 vLLM。

量化分析：LMDeploy W4A16 量化的实测数据：

模型FP16 显存W4A16 显存压缩比速度提升
InternLM2-7B14GB~4GB3.5x2.1x
Qwen2-7B14GB~4.2GB3.3x2.0x
InternLM2-20B40GB~10GB4.0x2.3x
# LMDeploy 启动命令
from lmdeploy import pipeline
from lmdeploy import TurbomindEngineConfig

# 方式1: Python API
pipe = pipeline('internlm/internlm2_5-7b-chat',
                backend_config=TurbomindEngineConfig(
                    model_name='internlm2_5',
                    tp=1,
                    max_batch_size=64))
response = pipe(['你好，介绍一下你自己'])
print(response[0].text)

# 方式2: REST API 服务
# lmdeploy serve api_server internlm/internlm2_5-7b-chat --server-port 8000
💡 实用技巧：TurboMind 引擎使用持久化 kernel 技术——首次推理时编译优化 kernel 并缓存，后续加载速度提升 10x+。建议在生产环境中预热后再接收流量。
⚠️ 注意事项：LMDeploy 对非 InternLM 生态的模型支持有限。部署 LLaMA、Mistral 等模型时可能遇到 tokenizer 不兼容。建议优先用于 InternLM/Qwen/ChatGLM 系列。

三、MLC-LLM

核心洞察：MLC-LLM 基于 Apache TVM 编译器栈，唯一支持 WebGPU 浏览器端推理的框架。通过编译优化生成硬件原生代码，实现"一次编译，全平台部署"。

量化分析：MLC-LLM 跨平台性能对比（Llama-3-8B, Q4_K_M 量化）：

平台硬件推理速度内存占用
浏览器 (WebGPU)M2 Pro~15 tok/s~5GB
Android (Vulkan)Snapdragon 8 Gen 3~12 tok/s~4.5GB
iOS (Metal)A17 Pro~18 tok/s~5GB
Desktop (CUDA)RTX 4090~85 tok/s~6GB
💡 实用技巧：MLC-LLM 的 TVM Auto-tuning 会为特定硬件选择最优 kernel。首次运行需要 5-10 分钟 tuning，之后直接使用缓存的 tuning 结果。
⚠️ 注意事项：WebGPU 推理受限于浏览器内存分配（通常 4-8GB），只能运行 1-3B 小模型。且首次加载需要下载完整模型到浏览器缓存。

四、Xinference

核心洞察：Xinference 不是推理引擎，而是推理引擎的编排层。它管理 vLLM、llama.cpp、TGI 等多个后端的生命周期，提供统一 OpenAI 兼容 API。

量化分析：Xinference 后端切换的性能开销：

操作耗时说明
启动新模型实例30-120s取决于模型大小和后端
后端切换~5s从 vLLM 切换到 llama.cpp
扩缩容（副本数+1）30-60s启动新进程并加载模型
API 请求转发开销<1ms纯 HTTP 代理
# Xinference 启动和管理
# 1. 启动 Xinference 服务
xinference-local --host 0.0.0.0 --port 9997

# 2. 注册并启动模型
from xinference.client import Client
client = Client("http://localhost:9997")
model_uid = client.launch_model(
    model_name="qwen2.5-instruct",
    model_engine="vLLM",  # 或 "llama.cpp", "SGLang"
    model_size_in_billions=7,
    quantization="q4_K_M"
)

# 3. 调用 API（OpenAI 兼容）
model = client.get_model(model_uid)
response = model.chat(messages=[{"role":"user","content":"Hello"}])
💡 实用技巧：Xinference 的模型自动管理功能会根据模型类型选择最优后端——LLM 默认用 vLLM，Embedding 默认用 llama.cpp，图片生成用 Diffusers。
⚠️ 注意事项：Xinference 本身不执行推理，性能取决于底层后端。但它增加了额外的进程管理开销，单模型场景直接用底层框架更高效。

五、Ollama

核心洞察：Ollama 封装 llama.cpp 为非技术用户提供零配置本地推理体验。核心价值是极致的易用性——一行命令运行任何 GGUF 模型。

量化分析：Ollama 性能数据（不同硬件上 Llama-3-8B Q4_K_M）：

硬件内存推理速度首次加载
M4 Max (128GB)~5GB~55 tok/s3s
M2 Pro (32GB)~5GB~30 tok/s5s
RTX 4090 (24GB)~5GB~80 tok/s2s
纯 CPU (64GB RAM)~5GB~8 tok/s10s
# Ollama 常用命令
# 运行模型（自动下载）
ollama run llama3:8b

# 创建自定义模型（Modelfile）
# Modelfile:
# FROM llama3:8b
# SYSTEM "你是一个专业的前端开发工程师"
# PARAMETER temperature 0.7
# PARAMETER top_p 0.9
ollama create frontend-dev -f Modelfile

# 启动 API 服务
ollama serve  # 默认端口 11434

# API 调用
curl http://localhost:11434/api/chat -d '{"model":"llama3","messages":[{"role":"user","content":"Hello"}]}'
💡 实用技巧：Ollama 支持 GPU 和 CPU 混合推理——自动将能放入 GPU 的层放入 GPU，其余用 CPU。通过 OLLAMA_NUM_GPU 环境变量控制 GPU 层数。
⚠️ 注意事项：Ollama 是单请求串行处理引擎，不支持并发推理。当 QPS > 1 时延迟线性增长。生产环境请使用 vLLM 或 TGI。

六、DeepSpeed-MII

核心洞察：DeepSpeed-MII 将 ZeRO 训练的思想应用于推理——通过参数分片和 Offload 将大模型推理显存降至最低。适合已有 DeepSpeed 训练基础设施的团队实现"训推一体"。

💡 实用技巧：DeepSpeed-MII 支持 DeepSpeed 训练产出的分片 checkpoint 直接加载，无需合并为完整权重。这节省了大量存储和传输时间。
⚠️ 注意事项：MII 的开发活跃度较低，2024-2025 年更新缓慢。新功能（如新模型架构支持）可能滞后。建议仅在与 DeepSpeed 训练配合时使用。

七、Mooncake（月之暗面推理平台）

核心洞察：Mooncake 是 Kimi 的生产推理平台，2026 年开源。核心创新是 Transfer Engine（基于 RDMA 的 KV Cache 传输）和分布式 KV Cache 存储（Mooncake Store），支持 Prefill-Decode 分离架构。

量化分析：Mooncake Transfer Engine 的传输性能：

互联方式带宽延迟 (1GB KV Cache)适用场景
NVLink (同机)900 GB/s~1ms单机 TP
InfiniBand HDR200 Gb/s~40ms跨机 PD 分离
RoCE (RDMA)100 Gb/s~80ms跨机推理
TCP (以太网)10 Gb/s~800ms不适用
💡 实用技巧：Mooncake 已集成到 SGLang（Encoder Global Cache Manager）和 vLLM-Omni。如果你使用这些框架，可以直接启用 Mooncake 的 KV Cache 共享能力而无需额外配置。
⚠️ 注意事项：Transfer Engine 需要 RDMA 网卡支持（InfiniBand 或 RoCE）。普通以太网环境无法使用其核心功能。

八、MLX（Apple Silicon 专用）

核心洞察：MLX 是 Apple 官方开发的机器学习框架，专为 Apple Silicon 的统一内存架构设计。CPU 和 GPU 共享内存，无需数据拷贝，大模型加载和推理效率显著优于 llama.cpp。

量化分析：MLX vs llama.cpp 在 Apple Silicon 上的对比（Llama-3-8B, Q4）：

硬件MLX 速度llama.cpp 速度MLX 优势
M4 Max (128GB)~55 tok/s~45 tok/s1.2x
M2 Pro (32GB)~28 tok/s~25 tok/s1.1x
M1 (16GB)~15 tok/s~14 tok/s1.05x
# MLX LM 推理
pip install mlx-lm

# Python API
from mlx_lm import load, generate
model, tokenizer = load("mlx-community/Llama-3-8B-Instruct-4bit")
response = generate(model, tokenizer,
                     prompt="Hello, how are you?",
                     max_tokens=200)
print(response)

# REST API 服务
# python -m mlx_lm.server --model mlx-community/Llama-3-8B-Instruct-4bit
💡 实用技巧：MLX 的统一内存架构意味着模型大小可以超过 GPU 显存限制——只要系统内存足够。M4 Max 128GB 可以运行 70B 模型（Q4 量化约 38GB）。
⚠️ 注意事项：MLX 仅支持 Apple Silicon（M1/M2/M3/M4），不支持 NVIDIA GPU。MLX 模型格式（.safetensors + mlx 权重）与 PyTorch 不兼容。

🔬 深入探讨：2026 年的推理框架生态正走向整合。vLLM 和 SGLang 成为 GPU 推理的事实标准，LMDeploy 占据中文市场，Mooncake 解决大规模部署的 KV Cache 共享问题。TGI 的"退役"标志着 HuggingFace 战略重心的转移——从自研推理引擎转向生态整合（Transformers + Hub + 社区框架）。对于工程团队来说，建议以 vLLM/SGLang 为基座，按需叠加 LMDeploy（中文）或 Mooncake（分布式）。
