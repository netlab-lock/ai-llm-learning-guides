一、框架家族图谱

核心洞察：LLM 推理框架不是"同一类东西的不同实现"，而是针对不同硬件层级（数据中心/GPU/CPU）和不同推理阶段（Prefill/Decode）专门优化的系统栈。理解为什么需要这么多框架，关键在于认识到推理的性能瓶颈随硬件和负载模式变化——没有单一框架能在所有场景下最优。

1.1 为什么需要这么多框架？

推理系统的设计空间由三个正交维度定义：硬件平台（NVIDIA GPU / Apple Silicon / 纯 CPU）、部署规模（单机 / 多机分布式）、负载模式（Prefill 密集 / Decode 密集 / 混合）。每个框架在这个三维空间中占据一个特定的最优区域。例如，TensorRT-LLM 在 NVIDIA 单机的 Decode 阶段最优，但在 CPU 上完全无法运行；llama.cpp 牺牲了峰值吞吐换取了跨平台能力。

算术强度转折点 = 峰值算力 / 峰值带宽 A100: 312 TFLOPS / 2 TB/s = 156 FLOPs/Byte H100: 989 TFLOPS / 3.35 TB/s = 295 FLOPs/Byte
符号说明：峰值算力 = GPU的FP16峰值浮点运算能力（TFLOPS），峰值带宽 = HBM内存带宽（TB/s）。公式含义：算术强度转折点决定任务是计算受限还是内存受限。
数值例子：A100: 312 TFLOPS / 2 TB/s = 156 FLOPs/Byte。当单次推理的算术强度低于此值时，任务是内存受限的。

符号含义：TFLOPS = 每秒万亿次浮点运算，TB/s = 每秒万亿字节带宽。为什么这个公式重要？当单次推理的算术强度（FLOPs per byte of memory access）低于转折点时，任务是内存受限的——增加更多计算单元不会提升性能。以 LLaMA-2-7B 的 Decode 阶段为例：每 token 的计算量 ≈ 14 GFLOPs，内存访问量 ≈ 14 GB，算术强度 ≈ 1 FLOPs/Byte，远低于 A100 的转折点 156，因此99% 的时间花在等待内存。这就是为什么所有框架优化都围绕"减少内存访问"展开，而非"增加算力"。

1.2 推理全流程与框架关注点

LLM 推理分为 Prefill（处理输入）和 Decode（逐 token 生成）两个阶段，它们的计算特征完全不同：

LLM 推理全流程 — 两阶段的计算特征对比
┌─────────────────────────────────────────────────────────────┐
│  Prefill 阶段               │  Decode 阶段                    │
│  ─────────────             │  ──────────                    │
│  输入: 所有 prompt token    │  输入: 1 个新 token             │
│  计算: 矩阵-矩阵乘法        │  计算: 矩阵-向量乘法            │
│  算术强度: 高(O(L·d))       │  算术强度: 低(O(d))             │
│  瓶颈: 计算受限             │  瓶颈: 内存带宽受限             │
│  并行度: 高(GPU利用率>80%)  │  并行度: 低(GPU利用率<20%)      │
│  框架优化: 算子融合          │  框架优化: 批处理/KV Cache      │
└─────────────────────────────────────────────────────────────┘
典型比例: Prefill 占 10-20% 时间, Decode 占 80-90% 时间
(1024 token prompt, 生成 256 token 的场景)

这个不对称性是理解框架设计的关键：vLLM 的 PagedAttention主要优化 Decode 阶段的 KV Cache 内存碎片；NVIDIA Dynamo 的 PD 分离将 Prefill 和 Decode 分配到不同 GPU 以消除干扰；SGLang 的 RadixAttention通过前缀缓存减少重复 Prefill 计算。

💡 实用技巧：理解框架分类时，记住一个简单规则——"你的瓶颈在哪里，就该选哪层的框架"。如果你的 KV Cache 装不下第二个请求（内存瓶颈），选 vLLM（PagedAttention）；如果你在不同地区有 GPU 想共享 KV Cache（分布式瓶颈），选 Mooncake（Transfer Engine）；如果你在 Mac 上想跑 70B 模型（硬件瓶颈），选 MLX（Apple Silicon 优化）。
⚠️ 常见误区：只看 Stars 和热度选框架

很多团队在选型时只看 GitHub Stars 数和社区热度，这是一个危险的误区。Stars 高可能只是因为易用性好（如 Ollama），不代表技术深度。选框架必须考虑：1) 硬件匹配——TensorRT-LLM 只支持 NVIDIA，MLX 只支持 Apple Silicon，选错硬件平台等于白搭；2) 场景匹配——在线服务选 vLLM/SGLang（高并发），本地开发选 llama.cpp/Ollama（低延迟），Agent 应用选 SGLang（结构化生成）；3) 运维成本——TensorRT-LLM 需要编译 TRT engine（每种模型+GPU 组合单独编译），vLLM 需要 Python 环境，llama.cpp 是零依赖单 binary。

🔬 深入探讨：屋顶线模型的扩展分析

屋顶线模型（Roofline Model）不仅用于判断内存/计算受限，还可用于预测框架优化的上限。设当前性能为 P，峰值性能为 P_max，转折点为 I*，算术强度为 I：

P = min(P_max, I × 带宽) 优化上限 = P_max / P_current
符号说明：P = 实际性能（TFLOPS），P_max = GPU峰值算力（A100为312 TFLOPS），I = 算术强度（FLOPs/Byte），带宽 = HBM带宽。公式含义：实际性能取峰值性能与带宽×算术强度之比的较小值。
数值例子：LLaMA-2-7B在A100上Decode阶段，实际吞吐5000 tokens/s，峰值可达30000 tokens/s（batch=256时），优化上限=6x。

例如：LLaMA-2-7B 在 A100 上 Decode 阶段，实际吞吐 5000 tokens/s，峰值可达 30000 tokens/s（batch=256 时），优化上限 = 6x。这就是为什么批处理（增大 batch size → 提高算术强度）是最有效的单卡优化手段。

二、框架速查表

核心洞察：速查表不是"哪个最好"的排名，而是"什么场景用什么"的决策矩阵。每个框架的核心设计选择（如 vLLM 选择 PagedAttention、SGLang 选择 RadixAttention、llama.cpp 选择 GGUF）都源于对特定瓶颈的针对性优化。理解这些选择背后的 trade-off，才能做出合理的选型。

2.2 关键技术选型的量化对比

不同框架在相同硬件上的性能差异主要来自三个方面：KV Cache 管理效率、批处理策略、算子优化程度。以下是 LLaMA-2-7B 在 A100 80GB 上的实测数据：

单请求 Decode 延迟 ≈ Model_Size / (Batch_Size × Bandwidth) 7B 模型 FP16: 14GB / (1 × 2TB/s) = 7ms/token (理论下限) 实际测量: vLLM=9.2ms, TensorRT-LLM=7.8ms, SGLang=9.5ms
符号说明：Model_Size = 模型参数量×字节数（7B×2bytes=14GB），Batch_Size = 并发请求数，Bandwidth = HBM带宽（A100为2 TB/s）。公式含义：单请求decode延迟由模型大小与带宽之比决定。
数值例子：7B FP16模型：14GB/(1×2TB/s)=7ms/token（理论下限）。当batch_size=8时，理论延迟降为7ms/8≈0.9ms/token per request。

符号含义：Model_Size 为模型参数量 × 字节数（7B×2bytes=14GB），Batch_Size 为并发请求数，Bandwidth 为 HBM 带宽。数值例子：当 batch_size=8 时，理论延迟降为 7ms/8 ≈ 0.9ms/token per request（但实际因 KV Cache 竞争会更高）。vLLM 因 PagedAttention 开销比理论值高 32%，TensorRT-LLM 通过算子融合缩小到仅高 11%。

2.3 框架技术决策树

按以下逻辑快速缩小选择范围：

# 框架选型决策逻辑（伪代码）
def select_framework(hardware, scenario, team_capability):
    """根据硬件、场景、团队能力选择推理框架"""
    
    # 第一层：硬件平台过滤
    if hardware == "apple_silicon":
        return "MLX"  # Apple 专用，统一内存架构
    if hardware == "cpu_only":
        return "llama.cpp"  # 唯一主力 CPU 框架
    
    # 第二层：场景匹配
    if scenario == "local_dev":
        return "Ollama"  # 零配置，最快上手
    if scenario == "agent_structured":
        return "SGLang"  # RadixAttention + Constrained Decoding
    if scenario == "datacenter":
        return "NVIDIA Dynamo"  # PD 分离 + 自动扩缩容
    
    # 第三层：团队能力评估
    if team_capability == "low":
        return "vLLM"  # 文档最全，社区最大
    if team_capability == "high":
        return "TensorRT-LLM"  # 需要编译 TRT engine，性能最高
    
    return "vLLM"  # 默认安全选择
💡 实用技巧：如果你在 vLLM 和 SGLang 之间犹豫，记住这个经验规则——当你的请求有共享前缀（如系统 prompt + 不同用户问题的场景，前缀重复率 >60%）时选 SGLang（RadixAttention 可跳过前缀计算，吞吐提升 3-8x）；否则选 vLLM（PagedAttention 内存效率更高，通用场景更稳定）。

三、按场景选框架

核心洞察：框架选型的本质是在性能三角（延迟/吞吐/精度）和资源三角（GPU 数量/显存/带宽）之间找到满足业务需求的帕累托最优。没有"最好"的框架，只有"最适合当前约束"的框架。关键约束通常来自硬件平台（不可变）、QPS 目标（业务决定）、延迟 SLA（用户体验决定）三者之一。

3.1 六类典型场景的选型逻辑

场景一：本地开发测试

约束：单卡/单 Mac，快速迭代，精度要求不高。选型优先级：易用性 > 速度 > 精度。推荐 Ollama（100k+ stars，一键拉取模型+运行）或 llama.cpp（支持 GGUF Q4_K_M 量化，8GB 内存可跑 7B 模型）。

场景二：高并发在线服务

约束：多卡 A100/H100，QPS>100，P99 延迟 <2s。选型优先级：吞吐 > 稳定性 > 成本。推荐 vLLM（PagedAttention 减少 60% KV Cache 浪费，连续批处理提升吞吐 2-3x）或 TensorRT-LLM（算子融合+FP8，吞吐再提升 30-50%，但编译耗时）。

有效吞吐 = Batch_Size / (T_prefill + Batch_Size × T_decode) vLLM 连续批处理: T_prefill 和 T_decode 可以重叠 静态批处理: 必须等最慢请求完成才开始下一批 提升倍数 ≈ 平均生成长度 / 最短生长度 (当生成长度差异 10x 时，提升约 5-8x)
符号说明：Batch_Size = 并发请求数，T_prefill = 输入处理时间，T_decode = 单token生成时间。公式含义：有效吞吐取决于batch大小与总处理时间的比值，连续批处理允许T_prefill和T_decode重叠执行。
数值例子：batch=4，生成长度[100,200,50,300]tokens，静态批处理需等最慢的300token完成；vLLM连续批处理在50/100/200token完成时即可加入新请求，吞吐提升约2-3x。

符号含义：T_prefill 为输入处理时间，T_decode 为单 token 生成时间。数值例子：假设 batch=4，生成长度分别为 [100, 200, 50, 300] tokens。静态批处理需等最慢的 300 token 完成，有效吞吐 = 4/(T_p + 300×T_d)；vLLM 连续批处理在 50/100/200 token 完成时即可加入新请求，吞吐提升约 2-3x。

场景三：Agent / 结构化输出

约束：需要 JSON Schema 约束解码、多轮对话前缀缓存、function calling。选型优先级：结构化生成能力 > 前缀缓存 > 通用吞吐。推荐 SGLang（RadixAttention 前缀复用，JSON Grammar 约束解码，Agent 场景吞吐比 vLLM 高 40-60%）。

场景四：数据中心级部署

约束：多地区 GPU 集群，自动扩缩容，PD 分离。选型优先级：分布式调度 > 资源利用率 > 单卡性能。推荐 NVIDIA Dynamo（KV Cache 感知路由将请求发送到已有缓存的 GPU，PD 分离消除两阶段干扰，Mooncake 的 Transfer Engine 实现跨节点 KV Cache 共享）。

场景五：中文 LLM 专用

约束：部署 Qwen/DeepSeek/GLM 等中文模型，需要中文分词优化、中文 prompt 工程。选型优先级：中文生态 > 中文量化支持 > 中文社区。推荐 LMDeploy（TurboMind C++ 引擎，中文模型量化支持最全，昇腾 NPU 适配）。

场景六：边缘/浏览器推理

约束：无 GPU 或仅有集成显卡，内存 <16GB。选型优先级：可移植性 > 量化效率 > 速度。推荐 llama.cpp（GGUF Q4_0 量化，4GB 内存跑 7B）或 MLC-LLM（WebGPU 在浏览器中运行，WebAssembly 部署）。

⚠️ 常见误区：框架可以随时无缝切换

很多人认为推理框架只是"一层壳"，可以随时替换。实际上框架切换的成本远超预期：1) API 兼容性——虽然大多数框架声称兼容 OpenAI API，但在流式输出格式、function calling、tool use 等细节上差异很大；2) 量化格式不通用——vLLM 用 GPTQ/AWQ，llama.cpp 用 GGUF，TensorRT-LLM 用 TRT engine，切换框架意味着重新量化模型；3) 性能特征不同——同一模型在不同框架上的最优配置（batch size、并行度、KV Cache 策略）完全不同，需要重新调优。建议在项目初期就做好框架选型评估。

四、框架工程的失败模式与调试

核心洞察：生产环境中推理框架出问题，80% 的原因不是框架本身的 bug，而是对框架资源模型的误解。理解每个框架如何管理显存、如何处理并发、如何调度请求，是避免生产事故的前提。

4.1 显存 OOM — 最常见的失败模式

为什么发生？推理框架的显存由三部分组成：模型权重（固定）+ KV Cache（随序列长度增长）+ 中间激活（随 batch size 增长）。框架通过 gpu_memory_utilization 参数预留显存，但实际 KV Cache 占用随请求动态变化。

可用 KV Cache 块数 = (总显存 × 利用率 - 模型权重) / 单块大小 vLLM 默认: block_size=16 tokens, 每块大小 ≈ 2 × num_layers × num_heads × head_dim × sizeof(dtype) LLaMA-2-7B FP16: 每块 ≈ 2×32×32×128×2 = 524KB A100 80GB 利用率 0.9: 可用块数 ≈ (80×0.9 - 14) / 0.000524 ≈ 111,000 块
符号说明：总显存 = GPU显存容量（如A100 80GB），利用率 = gpu_memory_utilization参数（默认0.9），模型权重 = 参数量×字节数（7B FP16=14GB），单块大小 = 2×num_layers×num_heads×head_dim×sizeof(dtype)。
数值例子：LLaMA-2-7B FP16每块≈2×32×32×128×2=524KB，A100 80GB利用率0.9时可用块数≈(80×0.9-14)/0.000524≈111,000块。

符号含义：num_layers=32（LLaMA-2-7B），num_heads=32，head_dim=128，sizeof(dtype)=2（FP16）。数值例子：每个 block 存 16 token 的 KV，111,000 块可支持约 111000×16=1.78M tokens 的 KV Cache。如果每个请求平均 2000 tokens，理论并发数 ≈ 887。但实际因碎片化，有效并发约为理论的 60-70%。

调试方法：nvidia-smi 观察显存占用，如果 torch.cuda.memory_reserved() - torch.cuda.memory_allocated() 差值 >2GB，说明存在显存碎片。对于 vLLM，降低 gpu_memory_utilization 到 0.85 或 0.8 可缓解。

4.2 吞吐不达标 — 瓶颈定位方法论

推理性能不达标时，按以下顺序排查：

  1. GPU 利用率检查：nvidia-smi dmon 观察 SM 活跃率。<30% → 内存受限（需增大 batch size）；>80% → 计算受限（需量化/减少计算）
  2. Prefill/Decode 时间比：如果 Prefill 占总时间 >30%，说明 prompt 太长或 Prefill 未充分优化（检查是否开启 FlashAttention/FlashInfer）
  3. 请求排队时间：如果排队时间 > 处理时间的 50%，说明调度器过载（需扩缩容或启用 disaggregated serving）
  4. KV Cache 命中率：SGLang 的 RadixAttention 有前缀命中率指标，<50% 说明共享前缀少，换用 vLLM 更合适

    num_running = parse_metric("vllm:num_requests_running")
    num_waiting = parse_metric("vllm:num_requests_waiting")
    gpu_cache_usage = parse_metric("vllm:gpu_cache_usage_perc")
    
    # 诊断逻辑
    if num_waiting > num_running * 2:

    if gpu_cache_usage > 95:

    if avg_prefill_time > avg_decode_time * 0.3:
        return "瓶颈: Prefill 占比过高，建议开启 FlashAttention"
    return "状态正常"

4.3 精度退化 — 量化与框架交互

同一模型在不同框架上运行可能产生不同输出，原因包括：

  • Attention 实现差异：FlashAttention、xformers、TRT 的 attention 内核在浮点精度上有微小差异（~1e-4），通过自回归放大后可能导致完全不同的输出
  • 量化方案不兼容：GPTQ-4bit、AWQ、FP8、INT4 的量化误差分布不同，切换框架后即使加载同一模型，输出也可能偏移
  • 采样温度：不同框架的 softmax 精度不同（FP32 vs FP16），在低温度（<0.3）时差异被放大
⚠️ 注意事项：从 llama.cpp 迁移到 vLLM 时，即使使用相同的 AWQ 量化文件，因 attention kernel 实现不同，输出的 perplexity 可能差 0.1-0.3。建议在迁移后用 eval benchmark（如 MMLU、GSM8K）做回归测试，而非仅靠肉眼判断"输出差不多"。

🔬 深入探讨：推理优化的理论上限分析

从信息论角度，LLM 推理的延迟下限由内存带宽决定（内存受限场景）。对于 N 参数模型，每 token 至少读取一次模型权重：

延迟下限 = 2 × N × sizeof(dtype) / 带宽 7B FP16: 2×7e9×2 / 2e12 = 14ms/token (A100) 70B FP16: 2×70e9×2 / 3.35e12 = 83ms/token (H100)
符号说明：N = 模型参数量，sizeof(dtype) = 每个参数的字节数（FP16为2字节），带宽 = HBM内存带宽（A100为2 TB/s，H100为3.35 TB/s）。公式含义：每个token至少需要读取一次模型权重，因此延迟由内存带宽决定。
数值例子：7B FP16模型在A100上：2×7×10⁹×2 / (2×10¹²) = 14ms/token。

实际延迟高于此下限的原因：KV Cache 读取、注意力计算中的 Q×K^T 和 ×V 操作、算子启动开销。目前最优实现（TensorRT-LLM）距理论下限约 30-50%，剩余优化空间来自动态 KV Cache 压缩和投机解码。

五、工程实践与总结

核心洞察：框架选型是项目早期最重要的技术决策之一，因为它的切换成本极高（5-10 人天）。正确的选型逻辑不是选"最好的"，而是选"与当前约束最匹配的"，同时预留迁移路径。

5.1 渐进式框架选型路径

推荐按业务阶段逐步升级框架，而非一步到位：

5.2 生产环境部署 Checklist

# 推理框架生产部署检查清单

## 资源规划
- [ ] 模型显存需求: 参数量 × 字节数 × 1.2 (含 KV Cache 余量)
- [ ] 并发容量评估: max_num_seqs × 平均序列长度 < KV Cache 总量
- [ ] 网络带宽: 多卡场景需确认 NVLink/PCIe 带宽满足 TP 通信需求

## 稳定性保障
- [ ] 健康检查端点: /health (vLLM), /ping (SGLang)
- [ ] 超时设置: 单请求最大时间（建议 <30s）
- [ ] 优雅关闭: 完成当前 batch 后退出（SIGTERM 处理）
- [ ] 显存监控: 告警阈值 = gpu_memory_utilization × 0.95

## 性能基线
- [ ] 单请求延迟: P50 < 1s, P99 < 3s (7B 模型, A100)
- [ ] 峰值吞吐: 在目标 QPS 下延迟不恶化
- [ ] 并发拐点: 找到延迟突增的并发数（通常是 KV Cache 满载点）
💡 实用技巧：在 vLLM 中设置 gpu_memory_utilization 时，不要直接设为 0.95。因为 PyTorch CUDA Context 本身占用 1-2 GB，加上框架开销，实际可用约 0.85-0.90。建议先用 0.8 跑通，逐步调高直到出现 OOM，再回退 0.05 作为安全值。在 A100 80GB 上，LLaMA-2-70B FP16 的推荐值是 0.82。
