主流推理框架

1. 推理框架全景（2026.06 更新）

核心洞察：推理框架的本质是解决一个矛盾——LLM的计算密度（~2 FLOPs/Byte）远低于GPU的算术强度转折点（A100为156 FLOPs/Byte），导致decode阶段GPU计算单元大量空闲等待数据。框架的优化空间就在于：通过智能调度让GPU"永远有活干"，通过内存管理让"能装下更多请求"。2026年推理框架已形成三层分工：编排层解决多节点协调、引擎层解决单节点效率、本地层解决个人部署。

原理展开：推理框架的理论性能极限由Roofline模型决定。Decode阶段每生成一个token需要读取全部模型参数，因此单次推理时间为：

T_decode = P / B_w
符号说明：T_decode = 单个token的解码时间(s)，P = 模型参数所占字节数(如FP16下参数量×2)，B_w = GPU内存带宽(bytes/s)。
数值例子：Llama-3-70B FP16约140GB，A100带宽2TB/s，T_decode = 140GB / 2TB/s = 70ms/token。

其中 P 为模型参数所占字节数（如Llama-3-70B FP16约140GB），B_w 为GPU内存带宽（A100为2TB/s）。当batch=B时，理论吞吐量为：

Throughput_max = B / T_decode = B · B_w / P (tokens/s)
符号说明：Throughput_max = 最大吞吐量(tokens/s)，B = batch大小，T_decode = 单token解码时间，B_w = GPU内存带宽，P = 模型参数字节数。
数值例子：B=64时，Throughput_max = 64 × 2TB/s / 140GB ≈ 914 tokens/s；B=1时仅14 tokens/s。

数值例子：Llama-3-70B在A100上，T_decode = 140GB / 2TB/s = 70ms。B=1时吞吐仅14 tokens/s，B=64时可达914 tokens/s。为什么batch增大能提升吞吐？因为decode阶段每次只计算1个token，计算量极小（约140GFLOPs），GPU的312TFLOPS算力只利用了0.045%。增大batch后，多个请求共享同一份参数读取，将内存受限操作转化为"一次读取、多次使用"。

实现细节：框架通过两个核心机制逼近理论极限。第一是PagedAttention（vLLM）或RadixAttention（SGLang）管理KV Cache内存，将内存利用率从30-50%提升到95%+。第二是连续批处理（Continuous Batching），在每个decode step后动态替换已完成请求，消除GPU空闲。


# vLLM PagedAttention 核心逻辑示意
# 将KV Cache分页管理，类似操作系统虚拟内存

class PagedKVCache:
    def __init__(self, page_size: int = 16, num_pages: int = 10000):
        self.page_size = page_size      # 每页存储16个token的KV
        self.num_pages = num_pages      # 总页数
        self.free_pages = list(range(num_pages))  # 空闲页列表
        self.page_table = {}            # 请求ID -> 页列表映射

    def allocate(self, request_id: str, seq_len: int) -> list:
        """按需分配页面，而非预分配整个最大长度"""
        pages_needed = (seq_len + self.page_size - 1) // self.page_size
        if pages_needed > len(self.free_pages):
            raise MemoryError("OOM: 无空闲页")  # 触发调度器抢占
        allocated = self.free_pages[:pages_needed]
        self.free_pages = self.free_pages[pages_needed:]
        self.page_table[request_id] = allocated
        return allocated

    def free(self, request_id: str):
        """请求完成后释放页面回空闲池"""
        self.free_pages.extend(self.page_table.pop(request_id))

设计权衡：三层架构的本质是不同的优化目标取舍。数据中心级编排（Dynamo/Mooncake）牺牲单节点延迟换取全局吞吐最优——通过PD分离将Prefill（计算密集）和Decode（内存密集）分配到不同GPU，避免互相干扰。高吞吐引擎（vLLM/SGLang）牺牲部分单请求延迟换取最大吞吐——通过连续批处理让GPU始终满载。本地部署（Ollama/llama.cpp）牺牲吞吐换取零配置部署——单请求处理，无调度开销。

失败模式：不使用推理框架直接部署的典型失败场景：(1) OOM崩溃——按最大序列长度预分配KV Cache，80GB显存只能服务4-7个并发请求；(2) GPU利用率极低——静态批处理下batch中最后一个请求完成后，前面完成的请求已空闲等待30-50%的时间；(3) 吞吐崩溃——当请求到达率波动时，静态批处理要么等待凑batch（增加延迟），要么以小batch运行（浪费带宽）。

💡 工程经验：vLLM中设置 gpu_memory_utilization 时不要直接设为0.95——PyTorch CUDA Context本身占用1-2GB显存，加上cuDNN/cuBLAS的工作空间，实际可用显存比标称值少约3-5GB。建议从0.85开始逐步上调，每次增加0.02，观察OOM边界。另外，当业务场景有频繁的共享前缀时（如RAG多轮对话、few-shot prompt），SGLang的RadixAttention通过前缀复用可比vLLM的Prefix Caching额外提升30-50%的KV Cache利用率，这是选型时容易被忽略的关键差异。

🔬 深入探讨：推理框架的性能极限分析 从数学本质角度推导推理框架的理论性能极限。设模型参数量为P（bytes），GPU带宽为B_w，batch大小为B。Decode阶段每生成一个token需要读取全部参数，时间公式为 T_decode = P/B_w。因此吞吐量极限为 Throughput = B/T_decode = B·B_w/P。以Llama-3-70B（FP16, P=140GB）在A100（B_w=2TB/s）上为例：T_decode=70ms/token，B=1时吞吐=14 token/s，B=64时吞吐=914 token/s。实际吞吐远低于这个理论值的原因是：(1) KV Cache的读写也消耗带宽，且随序列长度线性增长；(2) Attention计算是计算受限而非带宽受限（尤其在长序列时）；(3) 调度开销和内存碎片导致实际batch无法达到理论最大值。vLLM、SGLang、TensorRT-LLM等框架的本质差异就在于它们如何逼近这个理论极限——PagedAttention减少KV碎片，RadixAttention复用前缀KV，TRT-LLM的图编译优化减少kernel启动开销。

2. 详细对比

核心洞察：框架对比不能只看"谁快"——不同框架在不同维度上有结构性优势。vLLM的PagedAttention在通用场景下最均衡，SGLang的RadixAttention在共享前缀场景（多轮对话、few-shot）下有独特优势，TensorRT-LLM在NVIDIA硬件上通过图编译实现最低延迟但牺牲了灵活性。理解每个框架的"设计基因"才能做出正确选择。

原理展开：各框架的核心差异源于对KV Cache的不同管理策略。定义KV Cache的内存效率为：

η_KV = ΣS_i / (N × S_max)
符号说明：η_KV = KV Cache内存效率，S_i = 第i个请求的实际序列长度，N = 并发请求数，S_max = 预分配的最大长度。
数值例子：100个并发请求，S_max=4096，平均实际长度512，则η_KV = 100×512/(100×4096) ≈ 12.5%（传统静态分配）。

其中 S_i 为第i个请求的实际序列长度，N为并发请求数，S_max为预分配的最大长度。传统静态分配下η_KV ≈ 30-50%（因为请求长度差异大）。PagedAttention将KV Cache分为固定大小页面（通常16 token/页），效率变为：

η_KV = ΣS_i / (N × ⌈S_max/page_size⌉ × page_size) ≈ 95%+
符号说明：page_size = 页面大小(通常16 token/页)，⌈S_max/page_size⌉ = 每个请求分配的页数，消除内部碎片后效率接近100%。
数值例子：page_size=16，S_max=4096→256页/请求，实际使用512 token→32页，仅最后一页有内部碎片(浪费16-1=15 token位置)，η_KV ≈ 512/(32×16) ≈ 99.6%。

RadixAttention在此基础上增加了前缀复用：当多个请求共享相同前缀（如system prompt）时，只存储一份KV Cache，通过引用计数管理生命周期。这在多轮对话场景下可额外节省40-60%的KV Cache内存。

🔬 深入探讨：框架选型的量化决策原理 从底层分析，核心差异在于三个维度的优化策略：延迟（Latency）、吞吐（Throughput）和资源效率（Resource Efficiency）。TensorRT-LLM通过图编译和FP8量化最大化单请求延迟优化，其原理是将整个推理图编译为最优的CUDA kernel序列，消除Python解释器开销。vLLM和SGLang通过PagedAttention和连续批处理最大化吞吐，其工作机制是始终让GPU处理尽可能多的请求。决策公式可以量化为：如果目标是最小化P99延迟（如聊天场景），选择延迟方差最小的框架（TRT-LLM）；如果目标是最大化吞吐/成本比（如批量处理），选择batch利用率最高的框架（vLLM/SGLang）；如果目标是最小化部署复杂度（如个人开发），选择工具链最简单的框架（Ollama）。这个数学本质上的权衡没有"最优解"，只有"最适合"。

3. 选型建议

核心洞察：框架选型的本质是将业务需求映射到技术特性。关键不是"哪个框架最好"，而是"哪个框架的优化方向与你的瓶颈匹配"。高吞吐场景选vLLM/SGLang（batch利用率优先），低延迟场景选TensorRT-LLM（单请求延迟优先），Agent场景选SGLang（结构化输出优先），本地开发选Ollama（部署简单优先）。

原理展开：选型决策可以用一个量化评分模型来表达。定义场景需求向量 R = (r_throughput, r_latency, r_cost, r_flexibility)，框架能力向量 F = (f_throughput, f_latency, f_cost, f_flexibility)。最优框架为：

framework* = argmax_i (R · F_i) = argmax_i Σ(r_j × f_ij)
符号说明：framework* = 最优框架，R = 需求向量（吞吐量/延迟/成本/灵活性），F_i = 框架i的能力向量，r_j = 第j维需求权重，f_ij = 框架i在第j维的能力评分。公式含义：选择加权得分最高的框架。
数值例子：高吞吐场景R=(0.9,0.3,0.5,0.6)，vLLM得分1.975 > TensorRT-LLM得分1.655，选vLLM。

数值例子：假设你的场景是"高吞吐API服务"，需求向量 R = (0.9, 0.3, 0.5, 0.6)。vLLM能力向量 F_vllm = (0.95, 0.6, 0.7, 0.9)，得分 = 0.9×0.95 + 0.3×0.6 + 0.5×0.7 + 0.6×0.9 = 1.975。TensorRT-LLM能力向量 F_trt = (0.9, 0.95, 0.5, 0.4)，得分 = 0.9×0.9 + 0.3×0.95 + 0.5×0.5 + 0.6×0.4 = 1.655。因此vLLM更适合高吞吐场景。

实现细节：以下是基于实际场景的选型决策树和配置建议：


# 推理框架选型决策逻辑

def select_framework(scenario: str, constraints: dict) -> dict:
    """
    根据场景和约束推荐推理框架
    
    scenario: "api_service", "agent", "local", "edge", "datacenter"
    constraints: {"qps": int, "latency_sla_ms": int, "gpu_type": str}
    """
    if scenario == "api_service":
        # 高吞吐API服务：优先batch利用率
        if constraints.get("qps", 0) > 100:
            return {
                "framework": "vLLM or SGLang",
                "reason": "PagedAttention/RadixAttention最大化GPU利用率",
                "config": {"max_num_seqs": 256, "gpu_mem_util": 0.90}
            }
        else:
            return {"framework": "vLLM", "reason": "低QPS场景vLLM足够"}
    
    elif scenario == "agent":
        # Agent场景：需要结构化输出
        return {
            "framework": "SGLang",
            "reason": "FSM约束解码保证100%格式正确，JSON/Function Calling零开销",
            "config": {"enable_regex_fsm": True}
        }
    
    elif scenario == "local":
        return {"framework": "Ollama", "reason": "一键部署，模型库丰富"}
    
    elif scenario == "edge":
        return {"framework": "llama.cpp", "reason": "GGUF量化，CPU推理，内存效率最高"}
    
    elif scenario == "datacenter":
        return {
            "framework": "NVIDIA Dynamo",
            "reason": "PD分离+KV感知路由，7x-30x吞吐提升",
            "config": {"disaggregated_prefill": True}
        }
    
    else:
        return {"framework": "vLLM", "reason": "默认选择，社区最大，兼容性最广"}

4. 推理框架的核心技术原理与推导

核心洞察：所有推理框架的优化都围绕同一个数学事实——LLM的decode阶段是内存带宽受限的（算术强度仅~2 FLOPs/Byte，远低于GPU的156 FLOPs/Byte转折点）。这意味着优化方向不是"算得更快"，而是"减少数据搬运"和"让每次数据搬运服务更多计算"。PagedAttention、连续批处理、算子融合——这些技术的本质都是在提升有效带宽利用率。

4.1 PagedAttention的数学原理

vLLM的核心创新PagedAttention源于对KV Cache内存管理问题的本质洞察。传统方式为每个请求预分配连续的KV Cache空间（按最大序列长度），导致严重的内存碎片。从推导角度分析：

η_static = S_avg / S_max
符号说明：η_static = 静态分配KV Cache内存利用率，S_avg = 实际平均序列长度，S_max = 预分配的最大序列长度。公式含义：静态分配按最大长度预分配，导致大量内存浪费。
数值例子：S_max=4096，S_avg=1500时，η=36.6%——每分配4.9GB KV Cache只有1.8GB被有效利用。

其中 S_avg 为实际平均序列长度，S_max 为预分配的最大长度。通常 η_static 仅为30-50%。例如当 S_max=4096，S_avg=1500 时，η=36.6%——意味着每分配4.9GB KV Cache，只有1.8GB被有效利用。

PagedAttention的原理是将KV Cache分成固定大小的page（如每页16个token），按需分配。数学本质上，这将内存浪费从O(S_max)降到O(page_size)：

η_paged = (S_avg - S_avg mod page_size) / S_avg ≈ 1 - page_size/(2×S_avg)
符号说明：η_paged = PagedAttention内存利用率，S_avg = 平均序列长度，page_size = 页面大小（默认16 tokens）。公式含义：PagedAttention将内存浪费从O(S_max)降到O(page_size)。
数值例子：page_size=16，S_avg=1500时，η_paged≈1-16/3000≈99.5%。即使S_avg=64，η_paged也仅损失12.5%。

当 page_size=16，S_avg=1500 时，η_paged = 1 - 16/3000 ≈ 99.5%。即使S_avg=64（短序列），η_paged也仅损失12.5%。

为什么这个改进如此关键？从底层看，在A100 80GB上，70B模型的KV Cache每token约需1.2MB（计算公式：2 × n_layers × n_heads × head_dim × sizeof(dtype) = 2 × 80 × 64 × 128 × 2 = 2.5MB/token，经GQA优化后约1.2MB）。传统方式下，S_max=4096时每请求预留4.9GB，16个请求就用完80GB；PagedAttention下，实际只分配每个请求真实需要的页面，可同时服务50+请求。

实现细节：PagedAttention的页面表机制类似操作系统虚拟内存。每个请求维护一个page table，将逻辑页号映射到物理页框。当序列增长时分配新页，当请求完成时释放页回空闲池。关键优化是copy-on-write：当多个请求共享相同前缀（如beam search），只复制页面表而不复制页面数据。

⚠️ 注意事项：页面大小选择是性能关键。page_size太小（如1）导致页面表过大（每个请求4096个条目），管理开销增加；page_size太大（如128）导致尾部浪费（最后一个页可能只用了1个token）。vLLM默认page_size=16是经验最优值——在典型序列长度512-4096范围内，尾部浪费<1%。如果你的应用主要是超长序列（>8192），可考虑增大到32。

4.2 连续批处理的调度原理

连续批处理（Continuous Batching，原论文称Iteration-Level Scheduling）解决了传统静态批处理的效率问题。静态批处理中，一个batch的所有请求必须等最长的那个完成才能释放资源。推导其浪费：

W_static = Σ_{i=1}^{B-1} (t_B - t_i) = (B-1)·t_B - Σ_{i=1}^{B-1} t_i
符号说明：W_static = 静态批处理GPU空闲时间，t_i = 第i个请求完成时间，t_B = 最慢请求完成时间，B = batch大小。公式含义：静态批处理中，先完成的请求需等待最慢请求，产生空闲时间。
数值例子：B=32，完成时间均匀分布在[100ms,500ms]，W_static≈5900ms，GPU空闲时间占比约38%。

其中 t_i 为第i个请求的完成时间，t_B 为最慢请求的完成时间。设B=32，请求完成时间均匀分布在[100ms, 500ms]，则 W_static ≈ 31×500 - Σt_i ≈ 15500 - 9600 = 5900ms，GPU空闲时间占比约38%。

连续批处理的原理是在每个decode step后检查是否有请求完成，完成后立即用新请求填充。数学本质上，这将GPU利用率从：

η_static = Σt_i / (B × t_B) → η_continuous ≈ 100%
符号说明：η_static = 静态批处理GPU利用率，Σt_i = 所有请求完成时间之和，B = batch大小，t_B = 最慢请求完成时间，η_continuous = 连续批处理GPU利用率。公式含义：静态批处理利用率受限于最慢请求，连续批处理利用率接近100%。
数值例子：B=32，完成时间均匀分布在[100ms,500ms]，静态利用率≈62%，连续批处理≈100%。

为什么这个优化的底层影响如此巨大？因为decode阶段的算术强度极低（约2 FLOPs/Byte），GPU本来就处于内存受限状态——每一步的计算时间几乎不随batch大小变化，而batch增大能分摊模型参数的读取开销。连续批处理证明了"永远不让GPU闲着"是高吞吐的关键原理。

实现细节：连续批处理的核心是调度器。vLLM使用FCFS（先来先服务）策略，当GPU有空闲槽位时从等待队列取请求。SGLang使用更激进的策略：优先调度短请求（减少尾部延迟），并支持preemption（抢占）——当显存不足时，将低优先级请求的KV Cache换出到CPU，后续恢复。


# 连续批处理调度器核心逻辑

class ContinuousBatchScheduler:
    def __init__(self, max_batch_size: int = 256):
        self.running = []    # 正在执行的请求
        self.waiting = []    # 等待队列
        self.max_batch = max_batch_size
    
    def step(self):
        """每个decode step调用一次"""
        # 1. 检查完成的请求
        finished = [r for r in self.running if r.is_finished()]
        for r in finished:
            self.running.remove(r)
            free_kv_pages(r.page_table)  # 释放KV Cache页面
        
        # 2. 用等待队列中的请求填充空闲槽位
        while len(self.running) < self.max_batch and self.waiting:
            new_req = self.waiting.pop(0)
            if has_free_pages(new_req.estimated_len):
                self.running.append(new_req)
                allocate_kv_pages(new_req)
            else:
                # 显存不足：触发抢占或跳过
                preempt_lowest_priority(self.running)
        
        # 3. 执行一步decode
        if self.running:
            batch = create_batch(self.running)
            output = model.decode(batch)  # 一次前向传播处理整个batch
            return output
💡 实用技巧：连续批处理在高并发场景下可能导致"队头阻塞"——一个长请求占据batch槽位，导致后续短请求等待。SGLang通过preemption机制解决：当等待队列长度超过阈值，将运行中长请求的KV Cache换出到CPU（约50ms），优先处理短请求。实测在混合负载下，P99延迟降低40-60%。

4.3 框架性能优化的屋顶模型

衡量推理框架性能的核心指标包括延迟（latency）、吞吐（throughput）和资源利用率。从数学本质看，这三者之间存在固有权衡关系：

Throughput = Batch_Size / T_decode
GPU_Utilization = t_compute / (t_compute + t_memory + t_overhead)
符号说明：Throughput = 吞吐量(tokens/s)，Batch_Size = 批大小，T_decode = 单token解码时间，t_compute = 计算时间，t_memory = 内存访问时间，t_overhead = 调度开销。公式含义：吞吐由批大小和解码时间决定，GPU利用率由计算时间占比决定。
数值例子：batch=32时吞吐≈1454 tokens/s，GPU利用率≈78%（A100 80GB部署Llama-3.1-8B）。

为什么不能同时优化三者？因为提高batch_size会增加延迟（更多请求共享GPU时间片），降低延迟会减少batch_size进而降低吞吐。这就是为什么需要针对具体场景选择优化目标的底层原因。

从底层硬件角度分析，推理框架的性能瓶颈通常在于内存带宽而非计算能力。推导：以A100为例，FP16峰值算力312 TFLOPS，HBM带宽2TB/s，算术强度转折点 = 312T/2T = 156 FLOPs/Byte。当实际算术强度低于此值时，任务是内存受限的——增加更多计算单元不会提升性能。

各GPU平台的转折点对比：

H100 80GB 989 TFLOPS 3.35 TB/s 295 FLOPs/Byte ~2 FLOPs/Byte 内存受限

关键发现：即使使用FP8量化，LLM decode阶段的算术强度（~4 FLOPs/Byte）仍远低于GPU转折点（156-590 FLOPs/Byte）。这意味着所有LLM推理框架在decode阶段都是内存带宽受限的——优化方向必须是减少数据搬运，而非提升计算速度。

失败模式：常见的性能优化误区：(1) 过度优化计算——使用FlashAttention优化decode阶段的Attention计算，但decode阶段Attention的计算量极小（Q只有1个token），优化效果微乎其微（<5%提升）；(2) 忽略KV Cache带宽——长序列场景下KV Cache读写占总带宽的30-50%，只优化参数读取不够；(3) 盲目增大batch——当batch超过某阈值后，KV Cache总大小超出L2 Cache，带宽反而下降，吞吐不增反降。

从图可以看出，LLM decode的实际工作点（~2 FLOPs/Byte）远低于所有GPU的转折点，处于严重的带宽受限区域。这意味着：(1) 提升算力（如从A100升级到H100）对decode性能提升有限（约2-3x，主要来自带宽提升）；(2) 减少数据搬运（量化、KV Cache压缩）比提升计算效率更有效；(3) 只有当序列极长（>100K token）时，Attention计算才可能将工作点推向计算受限区。

4.4 推理框架的系统架构

从系统设计的原理出发，推理框架采用分层架构来管理复杂性。为什么分层是主流选择？推导如下：设系统有N个组件，全连接交互复杂度为O(N²)，分层后降低到O(N·L)，L为层数。数学本质上，这是用少量层间通信开销换取大幅降低的组件间耦合。

推理框架系统架构 ┌──────────┐ ┌──────────────┐ ┌──────────┐ │ Input │───→│ Processing │───→│ Output │ │ Layer │ │ Engine │ │ Layer │ └──────────┘ └──────────────┘ └──────────┘ │ │ │ ▼ ▼ ▼ [CPU→GPU] [GPU Compute] [GPU→CPU] PCIe传输 Tensor Core 结果回传

在实际工作机制中，每一层只与相邻层通信，通过标准接口解耦——这类似于TCP/IP协议栈的设计原理，每层独立优化，层内改动不影响整体。

4.5 性能基准测试方法

优化推理框架性能需要系统性的方法论。首先用profiling工具定位瓶颈——从底层看，GPU推理的瓶颈通常表现为三种模式：


# 推理性能基准测试（带profiling）
import torch
import time

def benchmark_inference(model, input_data, warmup=10, iters=100):
    """
    测量推理延迟和吞吐，附带GPU利用率分析
    
    关键指标：
    - SM活跃率: >80%表示计算受限
    - 显存带宽利用率: >70%表示内存受限
    - PCIe传输时间: >10%总时间表示数据搬运瓶颈
    """
    # Warmup：让GPU进入稳定状态
    for _ in range(warmup):
        with torch.no_grad():
            model(input_data)
    torch.cuda.synchronize()
    
    # 正式测量
    start = time.perf_counter()
    for _ in range(iters):
        with torch.no_grad():
            model(input_data)
    torch.cuda.synchronize()
    elapsed = (time.perf_counter() - start) / iters
    
    # 计算关键指标
    batch_size = input_data.shape[0]
    tokens_per_sec = batch_size / elapsed
    
    print(f"=== 性能基准测试结果 ===")
    print(f"Batch Size: {batch_size}")
    print(f"Latency: {elapsed*1000:.2f}ms")
    print(f"Throughput: {tokens_per_sec:.0f} tokens/s")
    print(f"GPU Utilization: {torch.cuda.utilization()}%")
    print(f"显存占用: {torch.cuda.memory_allocated()/1e9:.2f}GB")
    
    # 瓶颈判断
    sm_util = torch.cuda.utilization()
    if sm_util > 80:
        print("→ 瓶颈: 计算受限 → 优化方向: 量化/减少FLOPs")
    elif sm_util < 50:
        print("→ 瓶颈: 内存受限 → 优化方向: 算子融合/增大batch")
    else:
        print("→ 瓶颈: 混合 → 需要更细粒度profiling")
    
    return elapsed, tokens_per_sec

✅ 参考答案与详解
  1. 核心原理: PagedAttention将KV Cache分成固定大小的页面（通常16 token/页），按需分配而非预分配最大长度。类似操作系统虚拟内存管理，通过page table映射逻辑页到物理页框。内存利用率从传统方式的30-50%提升到95%+。在A100 80GB上部署Llama-3-70B时，传统方式只能服务16个并发请求（按S_max=4096预分配），PagedAttention可服务50+请求。
    实际案例: 一个客服系统同时处理100个对话，每个对话平均500 token。传统方式需要100×4096×1.2MB=480GB显存（不可能），PagedAttention只需100×500×1.2MB=60GB（单卡可承载）。
  2. 核心原理: 连续批处理在每个decode step后检查是否有请求完成，完成后立即用新请求填充空闲槽位。消除了静态批处理中"等最慢请求完成"的GPU空闲时间。GPU利用率从60-70%提升到接近100%。
    实际案例: 一个API服务接收的请求长度差异很大（100-3000 token）。静态批处理下，短请求完成后需等长请求完成才能释放资源，GPU空闲时间占30-40%。连续批处理下，短请求完成后立即被新请求替代，GPU利用率提升40%。
  3. 核心原理: 框架选型是将业务需求映射到技术特性的过程。核心权衡是灵活性vs性能：vLLM/SGLang灵活但非极致性能，TensorRT-LLM性能最强但需预编译，Ollama最简单但仅支持单请求。决策关键是识别你的瓶颈维度（延迟/吞吐/成本/易用性），选择对应维度最优的框架。
    实际案例: 一个AI Agent需要LLM输出严格JSON格式。选型分析：需要结构化输出→SGLang的FSM约束解码能保证100%格式正确，而vLLM的结构化生成支持有限。因此选SGLang，省去后处理校验开销，端到端延迟降低30%。
