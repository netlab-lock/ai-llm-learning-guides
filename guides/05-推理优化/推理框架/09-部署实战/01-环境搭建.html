🔧 环境搭建

本节目标：搭建 LLM 推理所需的完整环境。

1. 硬件需求

核心洞察：LLM推理的显存需求远不止模型权重——KV Cache、中间激活值、框架开销合计占20-40%额外显存。7B FP16模型约14GB权重，但实际启动需要18-20GB。显存预算公式：M_total = M_model + M_kv × B + M_overhead，B为并发数。

原理展开：推理是仅前向传播过程，不需要存储梯度（训练需要2-3倍显存）。显存占用主要来自三部分：①模型权重（参数量×精度字节数，FP16=2字节/param，INT4=0.5字节/param）；②KV Cache（2×n_layers×n_heads×d_head×seq_len×batch×bytes，随序列长度线性增长）；③框架开销（CUDA context约1-2GB，PyTorch缓存分配器预留）。

# 显存估算脚本
def estimate_memory(model_params_b, seq_len, batch_size, 
                    precision="fp16", n_layers=80, n_heads=64, d_head=128):
    bytes_per_param = 2 if precision == "fp16" else 0.5  # INT4
    model_memory = model_params_b * 1e9 * bytes_per_param / 1e9  # GB
    
    # KV Cache: 2 × layers × heads × head_dim × seq_len × batch × bytes
    kv_cache = 2 * n_layers * n_heads * d_head * seq_len * batch_size * 2 / 1e9
    
    overhead = 2.0  # CUDA context + framework overhead
    total = model_memory + kv_cache + overhead
    print(f"模型权重: {model_memory:.1f} GB")
    print(f"KV Cache: {kv_cache:.1f} GB")
    print(f"框架开销: {overhead:.1f} GB")
    print(f"总计: {total:.1f} GB")
    return total

# 示例: 7B模型, 4K序列, batch=4
estimate_memory(7, 4096, 4, "fp16")  # 输出约 14 + 6.4 + 2 = 22.4 GB

量化分析：7B FP16需16GB+（如RTX 4090），7B INT4需8GB+（如RTX 3070），70B FP16需160GB+（2×A100 80GB），70B INT4需40GB+（A100 40GB）。KV Cache在长序列场景下可能超过模型权重——128K序列的7B模型KV Cache约16GB，与FP16权重相当。

💡 实用技巧：部署前用nvidia-smi实测显存占用，而非仅按参数量估算。使用AWQ/GPTQ量化可将FP16模型显存减少约75%（7B从14GB降到4GB），推理速度仅降低5-10%。
⚠️ 注意事项：只看"模型大小 ≤ 显存"就认为GPU够用是常见误区。实际峰值显存远超模型权重——tokenizer缓存、KV Cache预分配、中间激活值、框架开销等额外占20-40%。务必用nvidia-smi实测加载后的显存占用。

2. 软件安装

核心洞察：LLM推理软件栈的版本兼容性是"自底向上"的严格依赖链——NVIDIA驱动→CUDA Toolkit→cuDNN→PyTorch→推理框架，每一层必须兼容上层。最常见的错误是只看主版本号（如CUDA 12）而忽略minor版本（12.1 vs 12.4）。

原理展开：CUDA采用前向兼容策略——新驱动能运行旧代码，但旧驱动无法运行新代码。兼容性公式：设Driver版本为D，Runtime版本为R，则兼容条件为D ≥ R。PTX指令集由Runtime编译，由Driver编译为具体GPU架构的SASS指令。版本不匹配时Driver无法识别新PTX导致运行失败。

# 1. NVIDIA 驱动（确认版本 >=  CUDA Toolkit）
nvidia-smi  # 右上角显示 Driver Version 和最高支持的 CUDA 版本

# 2. CUDA Toolkit
nvcc --version  # 确认 CUDA Runtime 版本
# 推荐 CUDA 12.4+（vLLM 0.5+ 和 TensorRT-LLM 8.6+ 的要求）

# 3. Python 环境（使用 conda 隔离）
conda create -n llm python=3.11 -y
conda activate llm

# 4. PyTorch（CUDA 版本必须匹配）
pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124

# 5. 推理框架（选择其一）
pip install vllm                    # 高吞吐场景（PagedAttention + 连续批处理）
# pip install llama.cpp             # CPU/边缘设备场景
# pip install tensorrt-llm          # 低延迟单请求场景

# 6. 量化工具
pip install auto-gptq autoawq

量化分析：PyTorch cu124 wheel约2.5GB，vllm约1.5GB（含CUDA kernels），完整环境约5-8GB。vLLM 0.6.x要求CUDA ≥12.4和PyTorch ≥2.4，TensorRT-LLM 10.0要求CUDA 12.5+和PyTorch 2.5+。版本不匹配时常见错误信息："CUDA error: no kernel image available for execution"（Runtime版本过高）或"undefined symbol: ncclAllReduce"（NCCL版本不匹配）。

💡 实用技巧：使用Docker镜像（如vllm/vllm-openai:latest）可避免版本兼容问题——镜像内已预配置好所有依赖的版本组合。自定义安装时，先确定目标推理框架版本，再向下推导CUDA和PyTorch版本。
⚠️ 注意事项：安装CUDA时只看主版本号（如CUDA 12）是常见错误。vLLM 0.5+要求CUDA 12.4，系统装12.1时nvidia-smi显示正常但运行时报兼容性错误。正确做法是先确认目标框架支持的CUDA版本，再选择对应的PyTorch wheel。

3. 验证安装

核心洞察：验证安装是确认整个软件栈正确配置的关键步骤。核心检查4项：PyTorch版本、CUDA版本、GPU型号、总显存。这4个检查覆盖了软件栈的核心链路：Python环境→PyTorch→CUDA→GPU硬件。

原理展开：验证的核心是确认CUDA的三层抽象（Driver API→Runtime API→cuDNN）都能正常工作。torch.cuda.is_available()返回True意味着：①Driver能识别GPU；②PyTorch的CUDA Runtime能与Driver通信；③cuDNN/cuBLAS库能正常加载。第一次推理较慢是因为CUDA Context初始化（~2s）、cuDNN基准测试（~1s）、JIT编译等一次性开销。

import torch

# 基础验证（4项核心检查）
print(f"PyTorch版本: {torch.__version__}")
print(f"CUDA版本: {torch.version.cuda}")
print(f"cuDNN版本: {torch.backends.cudnn.version()}")
print(f"CUDA可用: {torch.cuda.is_available()}")
print(f"GPU: {torch.cuda.get_device_name(0)}")
print(f"显存: {torch.cuda.get_device_properties(0).total_mem / 1e9:.1f} GB")

# 进阶验证：确认CUDA kernel能正常执行
x = torch.randn(1000, 1000, device='cuda')
y = x @ x  # 触发cuBLAS
print(f"CUDA计算正常: {y.shape}")

# 验证显存分配和碎片情况
print(f"已分配显存: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
print(f"预留显存: {torch.cuda.memory_reserved() / 1e9:.2f} GB")
print(f"碎片率: {1 - torch.cuda.memory_allocated() / max(torch.cuda.memory_reserved(), 1):.1%}")

量化分析：正常验证输出应显示：CUDA版本≥12.0、显存与硬件一致（如RTX 4090显示24.0 GB）、CUDA可用为True。如果torch.cuda.is_available()返回False，99%是CUDA驱动或PyTorch-CUDA版本不匹配。nvidia-smi显示的CUDA版本是Driver支持的版本，nvcc --version显示Runtime版本，二者可能不同。

💡 实用技巧：如果遇到"CUDA out of memory"但nvidia-smi显示显存充足，可能是PyTorch缓存分配器的碎片问题。设置PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True可优化分配策略，减少碎片。
⚠️ 注意事项：PyTorch第一次推理较慢（CUDA Context初始化~2s + cuDNN基准测试~1s + JIT编译），不要将首次推理延迟作为性能指标。vLLM启动时预分配所有KV Cache是为了实现O(1)的block分配效率，这会增加启动时间但提升运行时性能。
🔬 深入探讨：CUDA内存管理的底层机制：PyTorch的CUDA内存分配器采用"缓存分配器"策略——释放的显存不会立即归还给CUDA Runtime，而是保留在内存池中以便复用。碎片率 ≈ 1 - (已分配内存 / 预留内存)，当碎片率超过30%时，应考虑重启进程或使用torch.cuda.empty_cache()。
