⚡ vLLM 部署

本节目标：使用 vLLM 部署生产级 LLM API 服务，理解 PagedAttention 与连续批处理的核心机制，掌握关键参数调优与故障排查方法。

1. 安装

核心洞察：vLLM 的安装看似是简单的 pip install vllm，但底层涉及 CUDA 版本匹配、预编译 kernel 编译和 PyTorch 生态兼容三个关键约束。vLLM 的核心创新——PagedAttention——本质是借鉴操作系统虚拟内存的分页思想，将 KV Cache 从连续显存分配改为按页分配（Kwon et al., 2023）。这意味着 vLLM 必须依赖特定版本的 CUDA 驱动和 PyTorch 才能调用定制 CUDA kernel，版本不匹配会导致运行时 kernel 编译失败或性能退化。

1.1 环境依赖与版本约束

vLLM 对 CUDA 版本有硬性要求：vLLM 0.4.0+ 需要 CUDA 11.8 或 12.1+，且 NVIDIA 驱动版本 ≥ 520.61.05。这是因为 PagedAttention 内核使用 CUDA 的异步 copy 指令（cp.async）和 TMA（Tensor Memory Accelerator）特性，这些仅在较新 CUDA 版本中稳定支持。

# 推荐：使用 Docker 避免环境冲突（vLLM 官方维护镜像）
docker run --gpus all \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8000:8000 \
    --ipc=host \
    vllm/vllm-openai:latest \
    --model meta-llama/Llama-3.1-8B-Instruct

# 或者 pip 安装（需预装匹配的 PyTorch+CUDA）
pip install torch==2.2.0  # PyTorch 2.2+ 含 CUDA 12.1 支持
pip install vllm==0.4.0   # 自动拉取 flash-attn, xformers 等依赖

# 验证安装：检查 CUDA kernel 是否可用
python -c "from vllm import LLM; print('vLLM CUDA kernels loaded OK')"
💡 实用技巧：在 pip 安装后首次运行时会触发 JIT 编译（约 5-10 分钟），编译缓存保存在 ~/.cache/vllm/。如果在 Docker 中使用，建议将该目录挂载为 volume，避免每次重启容器重新编译。对于生产环境，直接用预编译好的 Docker 镜像可跳过此步骤。

1.2 安装后的组件结构

安装完成后，vLLM 提供以下核心组件：

组件功能对应模块

Continuous Batching Engine动态批处理调度，最大化 GPU 利用率vllm.core.scheduler
NCCL Communicator多 GPU 张量并行通信vllm.model_executor.parallel

⚠️ 注意事项：不要混用 conda 安装的 PyTorch 和 pip 安装的 vLLM——两者可能链接不同版本的 CUDA Runtime，导致 CUDA error: invalid device function。正确做法：统一用 pip 安装，或在 Docker 中部署。如果遇到 RuntimeError: CUDA error: no kernel image available，说明预编译 kernel 与当前 GPU 架构不匹配，需设置 export VLLM_PRECOMPILED_KERNELS=0 强制重新编译。
🔬 深入探讨：PagedAttention 的页表设计借鉴了 OS 虚拟内存的二级页表结构。在 vLLM 中，每个请求的 KV Cache 对应一个 block table（类似页表），记录逻辑块到物理块的映射。物理块大小默认 16 tokens/block，与 GPU shared memory tile 大小对齐以最大化数据复用。这种设计的代价是引入了 block table 查找的间接寻址开销，但在 batch_size > 16 时，显存节省带来的吞吐提升远超间接寻址的损耗。

2. 启动服务

核心洞察：vllm serve 命令启动的不仅是一个 HTTP 服务器，而是一个包含模型加载、CUDA kernel 编译、KV Cache 预分配、调度器初始化四个阶段的复杂流水线。理解这个流程对排查启动失败和优化首次请求延迟至关重要——7B 模型在 A100 上完整启动约需 30-60 秒，其中 CUDA kernel 编译占 60% 以上时间。

2.1 启动流程的内部机制

当执行 vllm serve 时，vLLM 按以下顺序完成初始化：

vllm serve 启动流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Phase 1: 模型加载 (10-20s)
  ├─ 从 HuggingFace Hub 或本地路径读取 config.json
  ├─ 按 tensor-parallel-size 切分权重到多 GPU
  └─ 加载 tokenizer 和特殊 token 配置

Phase 2: CUDA Kernel 编译 (15-30s, 首次)
  ├─ PagedAttention kernel (flash_attn_varlen)
  ├─ 量化 kernel (AWQ/GPTQ/FP8 GEMM)
  └─ 融合算子 (RMSNorm + SiLU, QKV projection)

Phase 3: KV Cache 预分配 (5-10s)
  ├─ 按 gpu-memory-utilization 计算可用显存
  ├─ 执行 profile_run 测量单请求峰值显存
  └─ 计算 max_num_blocks = (可用显存 - 模型权重) / block_size

Phase 4: 服务就绪 (<1s)
  ├─ Uvicorn HTTP server 监听端口
  └─ Scheduler 开始接受请求队列
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
总计: 30-60s (7B model, A100 80GB, 首次启动)

2.2 启动命令与参数配置

# 基本启动：单 GPU 部署 Llama-3.1-8B
vllm serve meta-llama/Llama-3.1-8B-Instruct

# 生产级启动：多参数调优
vllm serve meta-llama/Llama-3.1-8B-Instruct \

    --port 8000 \

    --gpu-memory-utilization 0.9 \    # 显存利用率（留 10% 给 CUDA Runtime）
    --quantization awq \              # 量化方法：awq/gptq/fp8
    --enable-prefix-caching \         # 开启前缀缓存加速多轮对话
    --max-num-seqs 256                # 最大并发请求数

# 多 GPU 张量并行部署 70B 模型
vllm serve meta-llama/Llama-3.1-70B-Instruct \
    --tensor-parallel-size 4 \        # 4 卡张量并行
    --quantization fp8                # FP8 量化减少显存和通信量

2.3 KV Cache 显存计算

KV Cache 是 vLLM 显存管理的核心。理解其显存占用公式对参数调优至关重要：

KV Cache 显存 = 2 × num_layers × num_heads × head_dim × seq_len × batch_size × dtype_bytes
符号说明：num_layers=Transformer层数，num_heads=KV注意力头数，head_dim=每头维度，seq_len=序列长度，batch_size=批大小，dtype_bytes=数据类型字节数（FP16=2）
数值例子：Llama-3.1-8B: 2×32×8×128×8192×32×2 = 34.4 GB

以 Llama-3.1-8B 为例：num_layers=32, num_heads=8（KV heads）, head_dim=128, dtype_bytes=2（FP16）。当 seq_len=8192, batch_size=32 时：

= 2 × 32 × 8 × 128 × 8192 × 32 × 2 = 34,359,738,368 bytes ≈ 32 GB
符号说明：代入Llama-3.1-8B参数：num_layers=32, num_heads=8(KV), head_dim=128, seq_len=8192, batch_size=32, dtype_bytes=2(FP16)
数值例子：2×32×8×128×8192×32×2 = 34,359,738,368 bytes ≈ 32 GB

这意味着 8B 模型在 batch_size=32、seq_len=8192 时，KV Cache 需要 32GB 显存——超过模型权重本身（约 16GB）。这也是为什么 --max-model-len 和 --max-num-seqs 需要联合调优：两者共同决定了 KV Cache 的峰值占用。

💡 实用技巧：启动日志中搜索 "Available KV cache memory" 可查看实际可用的 KV Cache 空间。如果该值过小导致频繁 block 回收（日志中出现 "Swapped out"），应降低 --max-num-seqs 或 --max-model-len。
⚠️ 注意事项：首次启动后不要立即压测。vLLM 在首次请求时会触发 lazy initialization（部分 CUDA graph 捕获和内存分配），导致首条请求延迟异常高（可达正常值的 5-10 倍）。正确做法：启动后发送 3-5 个 warmup 请求，等日志显示 "Application startup complete" 且后续请求延迟稳定后再进行基准测试。
🔬 深入探讨：vLLM 的 CUDA Graph 捕获机制会将 small batch 的 forward pass 录制为 CUDA Graph 以消除 kernel launch overhead。但 CUDA Graph 要求输入 shape 固定，因此 vLLM 按 batch_size 分档（如 1, 2, 4, 8, 16, 32...）预录制多组 Graph。当实际 batch 超过最大录制档位时，会回退到 eager mode，导致约 5-10% 的性能下降。这就是为什么 --max-num-seqs 设为 2 的幂次时性能最优。

3. API 调用

核心洞察：vLLM 提供 OpenAI 兼容的 REST API 格式，这不仅是接口规范的兼容，更意味着底层的连续批处理（Continuous Batching）调度对调用方完全透明。传统静态批处理要求等 batch 内所有请求完成后才能返回，而 vLLM 的调度器在每个 forward pass 后可以动态插入新请求、移除已完成请求——这使得 API 层面的平均延迟降低 2-3 倍（Kwon et al., 2023）。

3.1 OpenAI 兼容接口

vLLM 默认在 http://localhost:8000 提供以下端点，与 OpenAI API 格式完全一致：

# 方式一：curl 直接调用 Chat Completions API
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/Llama-3.1-8B-Instruct",
    "messages": [
      {"role": "system", "content": "你是一个有用的AI助手"},
      {"role": "user", "content": "解释 PagedAttention 的原理"}
    ],
    "temperature": 0.7,
    "max_tokens": 512,
    "stream": true
  }'

# 方式二：Python OpenAI SDK（零代码迁移）
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key="dummy"  # vLLM 不校验 key，但 SDK 要求传入
)

# 非流式调用
response = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Hello!"}],
    temperature=0.7,
    max_tokens=256
)
print(response.choices[0].message.content)

# 流式调用（逐 token 返回，降低用户感知延迟）
stream = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)
for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")

3.2 连续批处理的调度机制

理解 vLLM 的调度机制有助于解释为什么 API 调用在高并发下仍能保持低延迟：

连续批处理 vs 静态批处理（4个请求，不同生成长度）

静态批处理:
  req1: [prefill====|decode=]           ← 完成
  req2: [prefill====|decode=====]       ← 完成
  req3: [prefill====|decode=======]     ← 完成
  req4: [prefill====|decode=========]   ← 完成
  GPU: ████████████████████████████░░░  ← 35% 空闲等待

连续批处理 (vLLM):
  req1: [prefill====|decode=]  ← 完成即释放
  req2: [prefill====|decode=====]  ← 完成即释放
  req3: [prefill====|decode=======]
  req4: [prefill====|decode=========]
  req5:          [prefill====|decode==]  ← 动态插入
  req6:                [prefill====|decode====]  ← 动态插入
  GPU: ██████████████████████████████████  ← 95%+ 利用率

从量化角度看，在 A100 80GB 上部署 Llama-3.1-8B 时：静态批处理在 batch_size=32 时达到峰值吞吐约 1200 tokens/s，而 vLLM 的连续批处理可达 2800-3200 tokens/s（提升 2.3-2.7 倍），且 P99 延迟从 8.5s 降至 2.1s。

3.3 关键请求参数

参数类型说明对性能的影响
max_tokensint最大生成长度直接限制 decode 步数，影响单请求延迟
temperaturefloat采样温度 (0.0-2.0)0.0=greedy，越高越随机；不影响速度
top_pfloat核采样概率阈值越小解码越快（候选 token 少）
streambool是否流式返回不改变总延迟，但降低用户感知延迟 50%+
stoplist停止 token 序列提前终止可减少不必要的 decode 计算
💡 实用技巧：对于高并发场景，设置 max_tokens 上限可防止个别长序列独占 GPU 时间片。实测在 batch_size=64 时，不设 max_tokens 会导致 P99 延迟比 P50 高 5-8 倍（长尾效应），设置合理上限后 P99/P50 比值降至 2-3 倍。
⚠️ 注意事项：使用 OpenAI SDK 时注意 api_key 参数不可省略——虽然 vLLM 不校验它，但 SDK 会在 HTTP Header 中发送 Authorization: Bearer None 导致 401 错误。正确做法：传入任意非空字符串如 api_key="dummy"。
🔬 深入探讨：vLLM 的调度器采用 "chunked prefill" 策略：当新请求到达时，不会等待整个 prefill 完成才处理其他请求，而是将 prefill 分成多个 chunk（默认 512 tokens/chunk），在每个 chunk 之间穿插 decode 步骤。这避免了长序列 prefill 阻塞已在 decode 的请求。在 Llama-3.1-8B 上，chunked prefill 将 TTFT（Time To First Token）的 P99 从 1.2s 降至 350ms（batch_size=32 时）。

4. 关键参数

核心洞察：vLLM 的参数调优本质是在"延迟-吞吐-显存-精度"四维空间中寻找帕累托最优。每个参数都不是独立生效的：--max-model-len 决定单请求的 KV Cache 大小，--max-num-seqs 决定并发请求数，两者共同决定 KV Cache 总占用，而 --gpu-memory-utilization 是硬上限。理解参数间的耦合关系是避免 OOM 和性能退化的关键。

4.1 核心参数详解

参数说明推荐值调优逻辑
--tensor-parallel-size张量并行 GPU 数1-870B 模型需 4×A100；8B 模型单卡即可
--max-model-len最大上下文长度4096-32768每增加 2× → KV Cache 显存翻倍
--gpu-memory-utilizationGPU 显存利用率上限0.85-0.95设为 1.0 必 OOM（CUDA Runtime 需 5-10%）
--quantization量化方法awq/gptq/fp8AWQ 精度≈FP16，速度 1.3×；FP8 需 H100
--enable-prefix-caching前缀缓存建议开启多轮对话场景下 prefill 加速 40-80%
--max-num-seqs最大并发请求数128-256过大导致 KV Cache 不足，过小 GPU 空闲

4.2 显存预算计算

部署前需要验证显存是否足够。总显存占用由模型权重和 KV Cache 两部分组成：

总显存 = 模型权重 + KV Cache + 预留 = (params × dtype_bytes) + (2 × L × H × D × S × B × dtype_bytes) + 预留
符号说明：params=模型参数量，dtype_bytes=数据类型字节数，L=num_layers, H=num_kv_heads, D=head_dim, S=seq_len, B=batch_size
数值例子：RTX 4090部署8B: 16GB(权重) + 8GB(KV) + 2GB(预留) = 26GB

其中：params=参数量, L=num_layers, H=num_kv_heads, D=head_dim, S=seq_len, B=batch_size。

数值例子：在 RTX 4090 (24GB) 部署 Llama-3.1-8B (FP16)：

  • 模型权重 = 8B × 2 bytes = 16 GB
  • KV Cache (seq_len=8192, batch=32) = 2 × 32 × 8 × 128 × 8192 × 32 × 2 = 32 GB → 超出！
  • 实际可行：batch=8 时 KV Cache = 8 GB，总计 16 + 8 + 预留(2GB) = 26 GB → 仍超出
  • 正确配置：AWQ 量化(4GB) + batch=16 + seq_len=4096 → 4 + 4 + 1.5 = 9.5 GB ✓

💡 实用技巧：AWQ 和 GPTQ 的选择：AWQ 通过激活感知的权重选择保留重要通道，在同等位宽下 perplexity 比 GPTQ 低 5-10%，但解码速度略慢 5-8%。如果追求精度选 AWQ，追求吞吐选 GPTQ。FP8 在 H100 上最优——利用 FP8 Tensor Core 实现 1.5× 加速且精度损失最小。
⚠️ 注意事项：--gpu-memory-utilization 设为 1.0 是常见错误。CUDA Runtime 和 PyTorch 的 CUDA Allocator 需要约 5-10% 显存用于内存管理元数据、fragmentation 对齐和临时缓冲区。设为 1.0 会导致启动时 OOM 或运行中偶发 CUDA out of memory。推荐值 0.85-0.95。此外，--max-model-len 并非越大越好——过长的上下文会指数级增加 KV Cache 显存（与 seq_len 线性相关），导致可用 batch_size 骤降。
🔬 深入探讨：Prefix Caching 的加速原理基于一个观察：多轮对话中 system prompt 和历史的 KV Cache 可以复用。vLLM 使用 hash-based 匹配（对 prefix token 序列计算 hash）来检测可复用的 KV blocks。在 RAG 场景下（所有请求共享长文档前缀），prefix caching 可减少 60-80% 的 prefill 计算量。代价是额外的 hash 计算和 block 查找开销（约增加 2-5% 的调度时间），因此在短前缀（< 512 tokens）场景下收益不明显。

5. 推理全流程与性能分析

核心洞察：LLM 推理分为 Prefill（预填充）和 Decode（解码）两个计算特性完全不同的阶段。Prefill 是计算密集型的（所有输入 token 并行处理，GPU 利用率高），Decode 是内存密集型的（每步只生成 1 个 token，参数读取量远大于计算量）。理解这个差异是优化延迟的前提——Prefill 决定 TTFT（首 token 延迟），Decode 决定 TOTP（每 token 输出速率）。

5.1 推理流程

LLM 推理全流程
┌─────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────┐
│  用户输入    │───▶│  Tokenizer   │───▶│  Prefill     │───▶│  Decode  │
│  "你好"     │    │  编码        │    │  并行处理     │    │  逐token │
└─────────────┘    └──────────────┘    │  所有输入token│    │  自回归  │
                                       └──────────────┘    └────┬─────┘
                     ┌──────────────┐    ┌──────────────┐      │
                     │  用户看到    │◀───│  Tokenizer   │◀─────┘
                     │  "你好！...\" │    │  解码        │
                     └──────────────┘    └──────────────┘

Prefill 阶段: 并行处理 N 个输入 token → 计算量 ∝ N × params
Decode 阶段: 每步生成 1 个 token → 计算量 ∝ params，但内存读取量 = 参数大小

5.2 性能瓶颈分析

从硬件角度看，LLM 推理的瓶颈取决于算术强度（Arithmetic Intensity）：

算术强度 = FLOPs / 内存读取量 Decode 阶段算术强度 ≈ 2 × params / (params × dtype_bytes) = 2 / dtype_bytes FP16: 算术强度 = 2/2 = 1 FLOP/Byte A100 转折点: 312 TFLOPS / 2 TB/s = 156 FLOP/Byte ∵ 1 << 156 ∴ Decode 阶段严重内存受限
符号说明：FLOPs=浮点运算次数，内存读取量=从HBM读取的数据字节数，dtype_bytes=数据类型字节数
数值例子：FP16 Decode: 算术强度=2/2=1 FLOP/Byte << A100转折点156，严重内存受限

这意味着在 Decode 阶段，GPU 的计算单元 95% 以上的时间在等待数据从 HBM 读取。这也是为什么增大 batch_size 可以提升吞吐——多个请求共享同一份参数读取，摊薄了内存带宽压力。

屋顶模型 (Roofline) 分析
                    
  计算吞吐  │         ╱ 计算受限区 (Prefill, 大batch)
  (TFLOPS)  │       ╱
            │     ╱   ← Prefill 工作点 (算术强度高)
            │   ╱
            │ ╱ 带宽受限区 (Decode)
            │╱  ← Decode 工作点 (算术强度低)
            └──────────────── 带宽利用率
             
  转折点 = 峰值算力 / 峰值带宽
  A100: 312T/2T = 156 FLOPs/Byte
  H100: 989T/3.35T = 295 FLOPs/Byte

💡 实用技巧：如果业务对延迟敏感（如实时对话），优先降低 TTFT：使用 chunked prefill 和 prefix caching。如果业务对吞吐敏感（如离线批处理），优先提高 batch_size 和开启 CUDA Graph。实测 batch_size 从 16 提升到 64 时，吞吐提升 2.1×，但 P99 延迟从 1.2s 升至 3.8s。
⚠️ 注意事项：Prefill 和 Decode 的混合调度是一个经典问题。当长序列 prefill 和短请求 decode 混合时，prefill 会阻塞 decode 导致延迟飙升（prefill 的 compute 是 decode 的 100-1000 倍）。vLLM 通过 chunked prefill 缓解此问题，但如果业务场景允许，建议将长文本处理（高 prefill）和实时对话（低 decode）部署到不同实例。

6. 失败模式与调试

核心洞察：vLLM 部署中的故障 80% 可归为三类：OOM（显存不足）、性能退化（吞吐/延迟不达标）、服务不可用（启动失败/运行时崩溃）。每类都有明确的诊断路径和修复方案。

6.1 OOM 诊断与修复

vLLM 的 OOM 通常发生在两个阶段：启动时（KV Cache 预分配失败）和运行时（突发并发超过 KV Cache 容量）。

OOM 场景日志特征根因修复方案
启动 OOM"Cannot allocate KV Cache"模型权重 + KV Cache > 显存降低 max-model-len 或开启量化
运行时 OOM"CUDA out of memory"并发请求突增导致 KV Cache 耗尽降低 max-num-seqs 或开启请求排队
Prefill OOM"Sequence too long"单请求输入超过 max-model-len客户端截断输入或增大 max-model-len
# 诊断：查看当前 KV Cache 使用率
curl http://localhost:8000/v1/stats 2>/dev/null || \
  curl http://localhost:8000/metrics 2>/dev/null | grep kv_cache

# 修复：限制单请求最大 token 数
vllm serve model --max-num-seqs 128 --max-model-len 4096

# 修复：开启 automatic prefix caching 减少重复 KV 占用
vllm serve model --enable-prefix-caching --max-num-seqs 256

💡 实用技巧：设置环境变量 VLLM_LOGGING_LEVEL=DEBUG 可获取详细的调度器日志，包括每个请求的 prefill/decode 时间分解、KV Cache block 分配情况。对于性能调优，关注日志中的 "avg_prefill_time" 和 "avg_decode_time" 可快速定位瓶颈阶段。
⚠️ 注意事项：不要在生产环境使用 --enforce-eager 禁用 CUDA Graph——虽然它方便调试（支持动态 shape、可单步跟踪），但会损失 15-25% 的吞吐。正确做法：开发调试时用 eager 模式，生产部署时开启 CUDA Graph（默认行为）。
🔬 深入探讨：vLLM 的 KV Cache 分配器采用 "best-fit with eviction" 策略：当 KV Cache 不足时，优先淘汰最久未使用的 block（LRU 策略）。在 prefix caching 开启时，共享前缀的 block 会被 pin 住不被淘汰。这种设计与 OS 虚拟内存的页面置换算法（Clock Algorithm）类似，但 vLLM 的 block 粒度（16 tokens）远大于 OS 页（4KB），导致内部碎片更明显——平均每个 block 有约 30% 的空间浪费。

📝 思考与练习

  1. 为什么 vLLM 的 PagedAttention 能减少 KV Cache 的显存碎片？请用操作系统虚拟内存的概念类比解释。
  2. 在 RTX 4090 (24GB) 上部署 Llama-3.1-70B 模型，需要哪些量化策略？计算显存预算。
  3. 连续批处理相比静态批处理为什么能降低 P99 延迟？从 GPU 利用率角度分析。
  4. 如果 vLLM 服务在高并发下频繁 OOM，有哪些可能的修复方案？
▶显示答案
✅ 参考答案与详解
  1. PagedAttention 减少碎片：传统 KV Cache 为每个请求预分配连续显存（类似 OS 的连续内存分配），导致外部碎片——当部分请求完成后，释放的显存空洞无法被新请求利用。PagedAttention 将 KV Cache 分成固定大小的 block（默认 16 tokens），类似 OS 的页式内存管理。每个请求的 block 可以物理上不连续，通过 block table 映射。这样任何空闲 block 都可被立即分配，消除了外部碎片。代价是 block 内部可能有未用完的空间（内部碎片），但平均浪费仅约 30%，远优于连续分配的 50%+ 外部碎片率。
  2. 70B 在 RTX 4090 部署：70B FP16 = 140GB → 远超 24GB。必须使用量化：AWQ INT4 将模型压缩至 ~38GB → 仍不够。方案一：使用 2×RTX 4090 做 tensor-parallel-size=2，每卡 19GB 模型 + KV Cache。方案二：使用 GPTQ INT3 (约 28GB) + TP=2。KV Cache 预算：24GB - 19GB = 5GB 可用，seq_len=4096 时 batch_size ≈ 8。
  3. 连续批处理降低 P99 延迟：静态批处理中，batch 内最后完成的请求决定了整个 batch 的结束时间。如果有一个请求生成长度远超其他（如 1000 tokens vs 平均 100 tokens），其他 31 个请求的 GPU 时间被浪费在等待上。连续批处理在请求完成后立即释放资源并插入新请求，GPU 利用率从 ~65% 提升至 90%+，且没有"拖尾请求"阻塞整个 batch，P99 延迟降低 3-5 倍。
  4. 高并发 OOM 修复方案：(1) 降低 --max-num-seqs 限制并发数；(2) 降低 --max-model-len 减少单请求 KV 占用；(3) 开启 --enable-prefix-caching 复用共享前缀的 KV block；(4) 开启 --quantization awq 减少模型权重显存，腾出更多空间给 KV Cache；(5) 增加 GPU 数量或升级更大显存的 GPU；(6) 设置请求排队策略（vLLM 默认在 KV Cache 满时排队等待而非 OOM）。
