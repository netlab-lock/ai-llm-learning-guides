🚀 模块 09：部署实战

从零开始部署 LLM 推理服务

一、环境准备

核心洞察：LLM 推理的环境准备核心在于根据模型规模和业务需求，在硬件资源、精度和性能之间找到最优平衡点。7B 模型 FP16 需要 16GB 显存，INT4 仅需 8GB；70B 模型需要多卡 A100。

量化分析：不同模型的显存需求（含 KV Cache 估算）：

模型FP16 权重INT4 权重KV Cache (seq=4096, batch=1)推荐 GPU
7B14GB4GB~2GBRTX 4090 / A10
13B26GB8GB~4GBA100 40GB
70B140GB20GB~16GB2-4× A100 80GB
# 检查 NVIDIA 驱动和 CUDA
nvidia-smi

# 推荐 Python 版本
python --version  # 3.9 - 3.11

# 常用依赖
pip install torch transformers accelerate
💡 实用技巧：显存预算公式：M_total = M_model + M_kv × B + M_overhead，其中 B 是并发数。预留 10% 显存余量防止 OOM。
⚠️ 注意事项：CUDA 版本必须与 PyTorch 和推理框架三者兼容。例如 PyTorch 2.2+ 需要 CUDA 11.8+，vLLM 0.4+ 需要 CUDA 12.1+。版本不匹配是最常见的启动失败原因。

二、方案一：Ollama（最简单，5 分钟）

核心洞察：Ollama 封装 llama.cpp 为非技术用户提供零配置本地推理体验。一行命令运行任何 GGUF 模型，但仅适合本地开发，不适合生产环境。

# 1. 安装 Ollama
curl -fsSL https://ollama.com/install.sh | sh
# 或 macOS: brew install ollama

# 2. 运行模型（自动下载）
ollama run llama3

# 3. 查看已下载的模型
ollama list

# 4. 启动 API 服务（默认端口 11434）
ollama serve

# 5. 用 curl 调用 API
curl http://localhost:11434/api/chat -d '{
  "model": "llama3",
  "messages": [{"role": "user", "content": "Hello!"}]
}'
💡 适合：本地体验、快速测试模型效果、开发原型
⚠️ 常见误区——Ollama用于生产：Ollama本质是单请求串行处理引擎，不支持真正的并发推理。当QPS超过单请求吞吐时，延迟会线性增长。生产环境应使用vLLM、TGI等支持连续批处理的框架。

三、方案二：vLLM（生产级 API 服务）

核心洞察：vLLM 是当前最主流的生产级推理框架，核心创新 PagedAttention 将 KV Cache 内存利用率从 ~60% 提升至 ~95%，连续批处理使吞吐量比 HF Transformers 高 2-4 倍。

# 1. 安装 vLLM
pip install vllm

# 2. 启动 OpenAI 兼容 API 服务
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-7B-Instruct \
    --port 8000 \
    --max-model-len 4096 \
    --gpu-memory-utilization 0.9 \
    --tensor-parallel-size 1 \
    --quantization awq \
    --enable-prefix-caching \
    --max-num-seqs 64

# 3. 用 OpenAI SDK 调用
pip install openai
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")

response = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "用 Python 写一个快速排序"}],
    max_tokens=512,
    temperature=0.7,
)
print(response.choices[0].message.content)

量化分析：vLLM 关键参数对性能的影响：

参数默认值调优建议影响
gpu-memory-utilization0.90.85-0.95越高 KV Cache 越大，并发越多
max-num-seqs25632-512越高吞吐越大，但延迟增加
max-model-len模型最大按需设置越短越快，KV Cache 越小
enable-prefix-cachingFalseTrue（推荐）共享前缀场景提速 2-5x
💡 实用技巧：vLLM 支持 AWQ/GPTQ/FP8 量化模型直接加载，无需额外转换。使用 --quantization awq 参数即可启用。
⚠️ 注意事项：vLLM 的版本更新较快，不同版本支持的模型架构有差异。部署前确认 vLLM 版本支持你的模型架构（如 Gemma2、Qwen2.5 等）。

四、方案三：llama.cpp（本地量化推理）

核心洞察：llama.cpp 是纯 C/C++ 实现的 LLM 推理引擎，支持 CPU/GPU 混合推理，是唯一能在无 GPU 设备上运行 LLM 的方案。GGUF 格式支持从 Q2 到 Q8 多种量化等级。

# 1. 克隆并编译
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
make -j$(nproc)

# 2. 下载 GGUF 模型
wget https://huggingface.co/.../qwen2.5-7b-instruct-q4_k_m.gguf

# 3. 运行对话
./llama-cli -m qwen2.5-7b-instruct-q4_k_m.gguf \
    -p "你好" -n 256 --interactive

# 4. 启动 API 服务
./llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf \
    --host 0.0.0.0 --port 8080
GGUF 量化等级选择：
量化大小 (7B)质量推荐
Q8_0~7.5 GB接近无损质量优先
Q6_K~5.5 GB很好平衡之选
Q4_K_M~4.5 GB好⭐ 推荐
Q4_K_S~4.0 GB可接受内存紧张
Q3_K_M~3.5 GB有损极限压缩
💡 实用技巧：llama.cpp 支持 GPU 卸载——用 -ngl 999 将所有层放入 GPU，或 -ngl 20 只卸载前 20 层。在 Mac 上自动使用 Metal GPU。
⚠️ 注意事项：llama.cpp 的 CPU 推理速度较慢（7B Q4 约 8-15 tok/s），但 GPU 加速后可达 30-80 tok/s。确保编译时启用了 CUDA/Metal 支持。

五、方案四：Docker 部署（TGI）

核心洞察：TGI 提供 Docker 原生部署，一行命令启动。但注意 TGI 已进入维护模式，新项目建议使用 vLLM 的 Docker 镜像。

# 方案A: TGI Docker（已有基础设施）
docker run --gpus all \
    -p 8080:80 \
    -v $PWD/data:/data \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id Qwen/Qwen2.5-7B-Instruct \
    --max-input-length 4096 \
    --max-total-tokens 8192

# 方案B: vLLM Docker（推荐）
docker run --gpus all \
    -p 8000:8000 \
    -v $PWD/huggingface:/root/.cache/huggingface \
    vllm/vllm-openai:latest \
    --model Qwen/Qwen2.5-7B-Instruct \
    --gpu-memory-utilization 0.9
💡 实用技巧：Docker 部署时使用 -v 挂载模型缓存目录，避免每次启动重新下载模型。
⚠️ 注意事项：TGI 已于 2026 年初进入维护模式。已有 TGI 部署建议制定迁移计划。

六、性能基准测试

核心洞察：性能基准测试需要区分"延迟"和"吞吐"两个维度。单请求测试测的是延迟，并发测试测的是吞吐。生产环境需要两者兼顾。

# 使用 vLLM 内置的基准测试工具
python -m vllm.entrypoints.openai.api_server ... &

# 安装基准测试工具
pip install locust

# 或使用简单的 curl 测试
for i in $(seq 1 100); do
  curl -s http://localhost:8000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{"model":"Qwen/Qwen2.5-7B-Instruct","messages":[{"role":"user","content":"Hi"}],"max_tokens":100}' \
    | jq '.usage'
done

关键指标监控

  • TTFT：首 token 延迟（目标 < 500ms）
  • TPS：每秒 token 数（目标 > 30 tok/s）
  • Throughput：并发请求处理能力（tok/s 总和）
  • GPU 内存：显存使用率（nvidia-smi 监控）
  • 队列深度：等待处理的请求数
⚠️ 常见误区——性能基准测试：用单请求循环测试得出"XX tokens/s"就当作服务吞吐量。实际上单请求测试的是延迟而非吞吐。真实吞吐需要用并发客户端（如locust、wrk）同时发送多个请求。首次请求因warmup会异常慢，应丢弃前3-5个请求的数据。

七、部署检查清单

核心洞察：生产部署前需要从功能、性能、稳定性三个维度逐一检查。以下是经过实践验证的检查清单：

  1. ☐ 确认 GPU 显存足够（模型权重 + KV Cache × 并发数 + 10% 余量）
  2. ☐ 选择合适的量化方案（精度 vs 速度 vs 内存的 trade-off）
  3. ☐ 设置合理的 max_model_len（越短越快，按需设置）
  4. ☐ 配置 gpu_memory_utilization（留 10% 余量防 OOM）
  5. ☐ 启用 prefix_caching（如果有共享前缀场景）
  6. ☐ 测试并发性能（逐步加压到目标 QPS 的 1.5 倍）
  7. ☐ 监控 GPU 使用率和显存（设置告警阈值）
  8. ☐ 设置请求超时和重试机制（防止级联故障）
  9. ☐ 配置健康检查端点（/health 或 /ping）
  10. ☐ 准备降级方案（模型不可用时的 fallback）
