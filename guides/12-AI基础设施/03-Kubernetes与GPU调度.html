K8s在AI场景中的角色

K8s在AI场景中的角色

通俗类比：K8s在AI场景中就像是物流调度中心，不再是简单的应用托管。它负责统筹计算、存储、网络等资源，将GPU、CPU、内存等打包，智能地分配给不同的AI训练或推理任务。
常见误区：最常见的错误是试图直接用原生K8s管理AI任务。AI任务（如模型训练）生命周期、资源需求与Web应用差异巨大，缺乏作业队列、GPU感知调度等能力，会导致效率低下甚至失败。
深入探讨：在AI基础设施中，K8s扮演的是编排层。它通过其声明式API管理Pod、Service等资源对象。对于AI，它需要与GPU设备插件（Device Plugin）、集群调度器（如Volcano）以及分布式计算框架（如Ray、PyTorch Operator）深度集成，构成完整的AI作业生命周期管理平台。

📊 量化对比：原生K8s vs 专用调度器

原生K8s调度器管理GPU任务时，由于缺乏作业队列感知和Bin-Packing能力，GPU利用率通常只有30-40%（大量资源碎片导致GPU空闲但无法分配）。使用Volcano等专用调度器后，通过Bin-Packing聚合任务和Gang Scheduling减少等待，GPU利用率可提升至60-75%。在100节点×8GPU集群中，这意味着从320张GPU有效利用提升至480-600张，相当于节省25-47%的硬件采购成本。

Kubernetes已成为云原生AI工作负载的标准编排平台。相比Slurm，K8s提供了更好的容器支持、服务发现和弹性伸缩能力。但对于大规模训练任务，原生K8s调度器存在不足，需要扩展调度器。

💡 K8s vs Slurm

K8s适合混合工作负载（训练+推理+Web服务），Slurm适合纯HPC训练场景。两者可以共存：K8s管理推理服务，Slurm管理训练任务。

GPU设备插件

GPU设备插件

通俗类比：GPU设备插件就像K8s世界里的“硬件翻译官”。它向K8s集群报告“我这里有一块NVIDIA A100，显存80GB”，并让K8s能够像管理内存一样，将一块GPU作为可分配的资源（如`nvidia.com/gpu: 1`）分配给容器。
常见误区：易犯错误是忘记在每个GPU节点上部署设备插件（如`nvidia-device-plugin-daemonset`），或者插件版本与GPU驱动/CUDA版本不兼容，导致节点上虽然有GPU，但K8s无法识别和调度。
深入探讨：设备插件通过K8s的`DevicePlugin` gRPC接口注册设备。当Pod请求`nvidia.com/gpu: 2`时，插件会确保该Pod能访问宿主机的2块物理GPU卡。它通常挂载`/dev/nvidia*`设备文件和必要的库。现代插件还支持MIG（多实例GPU）模式，将一块A100划分为多个独立的GPU实例。
Kubelet (每个节点)
      ↑ 注册设备
GPU设备插件 (DaemonSet)
      ↑ 读取



NVIDIA GPU Device Plugin是K8s管理GPU资源的核心组件，它通过K8s设备插件框架将GPU暴露为可调度资源：


# 安装NVIDIA Device Plugin
kubectl apply -f https://raw.githubusercontent.com/NVIDIA/k8s-device-plugin/v0.14.0/nvidia-device-plugin.yml

# Pod请求GPU资源
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  containers:
  - name: training
    image: nvidia/cuda:12.0-runtime
    resources:
      limits:
        nvidia.com/gpu: 4  # 请求4张GPU

⚖️ 设计权衡：MIG vs 直通模式


MIG (Multi-Instance GPU)将一块A100/H100物理GPU划分为最多7个独立实例（如1g.10gb、3g.40gb），每个实例拥有独立的显存、计算核心和缓存，提供硬件级故障隔离——一个实例OOM不会影响其他实例。但MIG引入约5-10%的性能开销（来自分区管理损耗和显存带宽限制），且不支持跨实例的NVLink通信。


直通模式 (Passthrough)将整块GPU直接分配给Pod，性能零损耗，支持完整的NVLink带宽（600 GB/s on A100），适合大规模分布式训练。但无资源隔离——单个进程的显存泄漏会污染整块GPU，且多个Pod无法安全共享同一块GPU。




维度MIG模式直通模式


性能损耗5-10%（分区开销）0%（原生性能）


隔离性强（硬件隔离）弱（进程级共享）


NVLink不支持跨实例完整支持(600GB/s)


共享能力最多7 Pod/GPU1 Pod/GPU


故障域单实例（仅影响一个负载）整块GPU（影响所有负载）


适用场景推理服务、开发环境、多租户共享大规模DDP/模型并行训练




选型建议：推理场景优先MIG（高隔离、高利用率）；训练场景优先直通（性能敏感、需要NVLink）；混合场景可划分部分GPU为MIG、部分为直通。







⚖️ GPU共享方案对比：MPS vs Time-Slicing


当GPU资源有限但需要支持多个推理服务时，可通过MPS或Time-Slicing实现GPU共享。两者机制不同，适用场景各异：




维度MPS (Multi-Process Service)Time-Slicing (时间切片)


实现机制NVIDIA专有技术，多个进程共享同一GPU上下文，通过MPS Server统一调度CUDA StreamK8s设备插件层实现，通过限制每个Pod的GPU使用时间片（轮转方式）共享GPU


隔离性中等——进程共享GPU显存和计算资源，一个进程OOM会影响其他进程低——仅限制时间份额，无显存隔离，一个进程可能耗尽显存


性能开销低（约2-5%），进程共享GPU上下文，减少上下文切换开销中等（约5-15%），频繁的时间片轮转导致上下文切换开销


并发能力最多48个客户端同时连接一个MPS Server理论上无限制（仅受时间片配置约束）


显存管理共享显存池，无硬隔离，需应用自行控制显存使用无显存隔离，依赖应用自觉控制


配置复杂度中——需部署MPS DaemonSet，设置CUDA_MPS_PIPE_DIRECTORY等环境变量低——仅需在Device Plugin ConfigMap中配置replicas


适用场景多个小模型推理共享同一GPU（如多个BERT推理服务）开发/测试环境快速共享GPU，对隔离性要求不高的场景


局限性不支持所有CUDA API，部分kernel可能不兼容；需NVIDIA GPU无显存隔离，不适合生产环境多租户共享




配置示例：


# MPS配置（通过Device Plugin ConfigMap）
apiVersion: v1
kind: ConfigMap
metadata:
  name: nvidia-device-plugin-config
data:
  config: |
    version: v1
    sharing:
      timeSlicing:
        renameByDefault: false
        resources:
          - name: nvidia.com/gpu
            replicas: 4    # 1块GPU虚拟为4份（适合推理）

# MPS环境变量配置（在Pod中）
env:
- name: CUDA_MPS_PIPE_DIRECTORY
  value: "/tmp/nvidia-mps"
- name: CUDA_MPS_LOG_DIRECTORY
  value: "/tmp/nvidia-log"
- name: CUDA_VISIBLE_DEVICES
  value: "0"


选型建议：生产环境多租户推理优先选择MPS（性能开销低、并发能力确定）；开发测试环境或快速验证选择Time-Slicing（配置简单）；高隔离需求场景选择MIG（硬件级隔离）。

调度策略


核心洞察：原生K8s调度器不理解GPU拓扑，可能将同一Pod的4张GPU分配到不同NUMA节点甚至不同PCIe交换机下，严重影响训练性能。AI场景需要扩展调度器（如Volcano）来实现Gang Scheduling、Bin-Packing和拓扑感知调度。



调度策略


通俗类比：AI调度策略就像智能交通调度员。它不仅要“把车（Pod）停到空车位（节点）”，还要考虑“目的地”（任务队列）、“车辆类型”（GPU型号）和“乘客优先级”（作业优先级），甚至安排“车队”（分布式作业）同时出发。


常见误区：盲目使用K8s默认调度器调度GPU任务，容易导致资源碎片化。例如，两个任务各需1张GPU，节点上有2张，但默认调度器可能将它们调度到不同节点，留下一个节点有1张闲置GPU，无法调度需要2张GPU的大任务。


深入探讨：高级调度策略包括：1. **Bin-Packing**：尽量将任务打包到少数节点，提高利用率。2. **Gang Scheduling**：确保分布式作业的所有Pod同时启动，避免资源死锁。3. **抢占（Preemption）**：高优先级任务可抢占低优先级任务的GPU资源。4. **拓扑感知**：考虑GPU间的NVLink连接，将紧密通信的任务Pod调度在同节点同拓扑下。



节点选择器与容忍度


在讨论高级调度策略之前，先了解K8s原生的基础调度机制——节点选择器（nodeSelector）和容忍度（tolerations）。这些是K8s内置的能力，无需额外调度器即可使用：


# 使用nodeSelector选择GPU节点
spec:
  nodeSelector:
    nvidia.com/gpu.present: "true"
    gpu-type: "a100-80gb"

# 使用tolerations容忍GPU节点taint
  tolerations:
  - key: "nvidia.com/gpu"
    operator: "Exists"
    effect: "NoSchedule"





⚠️ 常见陷阱


原生K8s调度器不理解GPU拓扑，可能将同一Pod的4张GPU分配到不同NUMA节点甚至不同PCIe交换机下，严重影响训练性能。需要使用拓扑感知调度器。







📐 形式化定义：Bin-Packing调度


Bin-Packing问题可形式化为整数线性规划：


min Σj∈J yj


s.t. Σi∈I ri · xij ≤ Cj · yj, ∀j ∈ J


Σj∈J xij = 1, ∀i ∈ I


yj ∈ {0,1}, xij ∈ {0,1}


符号说明：


    

  • I = 任务集合，J = 节点集合
    • 

  • ri = 任务i的资源需求（如GPU数=4）
    • 

  • Cj = 节点j的资源容量（如GPU数=8）
    • 

  • yj ∈ {0,1}：节点j是否被使用（1=使用，0=未使用）
    • 

  • xij ∈ {0,1}：任务i是否分配到节点j（1=分配，0=未分配）
    • 



数值例子：3个任务(r₁=4GPU, r₂=2GPU, r₃=2GPU)，2个节点(C₁=8GPU, C₂=8GPU)。最优解：y₁=1, y₂=0（只用Node1），x₁₁=1, x₂₁=1, x₃₁=1（全放Node1），目标值=1（仅使用1个节点）。相比分散调度（使用2个节点），Bin-Packing节省50%节点占用。


实际约束：真实调度还需考虑GPU型号匹配（A100 vs V100）、NVLink拓扑、显存需求、Pod亲和/反亲和规则，因此是NP-Hard问题，通常用贪心FFD（First Fit Decreasing）近似求解。







📊 量化：拓扑感知调度的性能影响


NVLink亲和调度：当分布式训练Pod的GPU通过NVLink连接（带宽600 GB/s on A100）而非PCIe（64 GB/s）时，AllReduce通信效率显著提升。实测表明，NVLink亲和调度可提升AllReduce性能30-50%（ResNet-50训练，batch size=256，8 GPU配置下，NVLink vs PCIe的吞吐量从1800 img/s提升至2400-2700 img/s）。


NUMA拓扑不感知的代价：当调度器将同一Pod的GPU分配到不同NUMA节点时，GPU间通信需经过QPI/UPI总线（带宽仅约32 GB/s），延迟急剧增加。实测显示，拓扑不感知导致同一Pod的GPU跨NUMA节点时延迟增加3-5倍（AllReduce延迟从50μs增至150-250μs），训练吞吐量下降20-35%。

📋 策略→实现：调度策略与调度器能力映射


上述调度策略（Bin-Packing、Gang Scheduling、拓扑感知、抢占）在原生K8s中无法完全实现。下表展示了各策略与调度器实现的对应关系，以及为什么需要引入专用调度器：




调度策略原生K8s支持Volcano实现关键差异


Bin-Packing❌ 仅支持Spread（分散）✅ 内置Bin-Packing Plugin原生K8s默认分散Pod到多节点，Volcano可聚合到少节点


Gang Scheduling❌ 无PodGroup概念✅ PodGroup CRD（minAvailable）原生逐个调度Pod，Volcano确保所有Pod同时满足


拓扑感知⚠️ 仅nodeAffinity✅ NUMA亲和+NVLink感知原生仅支持节点级亲和，Volcano支持GPU/NUMA级拓扑


抢占（Preemption）⚠️ 仅Pod优先级✅ Queue级抢占+资源预留原生仅支持Pod级抢占，Volcano支持队列级公平抢占


作业队列❌ 无Queue概念✅ Queue CRD（配额/权重）原生无多租户队列，Volcano提供Queue资源配额管理


公平调度❌ 仅ResourceQuota✅ DRF（主导资源公平）原生仅限制总量，Volcano实现多维度资源公平分配




结论：原生K8s调度器设计目标是服务长期运行的无状态Web应用，其调度模型是"逐个Pod最优"。而AI/HPC作业的特征是"一组Pod需要同时运行"，这要求调度器具备全局视野和作业级调度能力。Volcano等专用调度器正是填补了这一能力缺口。





Volcano调度器


Volcano调度器


通俗类比：Volcano是K8s专为AI、HPC等高性能计算场景打造的“超级调度员”。它内置了作业队列、Gang调度、资源预留等高级功能，就像为繁忙的快递站配备了专业的智能分拣管理系统。


深入探讨：Volcano核心组件：1. **vc-scheduler**：实现Gang Scheduling、Fair-share等算法。2. **vc-controller-manager**：管理Queue和PodGroup的生命周期。3. **vc-admission**：进行准入校验。它将一组相关的Pod（如一个训练作业的Worker）作为一个`PodGroup`整体调度，要么全部成功，要么全部不调度，避免了资源碎片和作业饥饿。


常见误区：使用Volcano时，若未正确定义`Queue`（队列）和`PodGroup`（Pod组），或者队列配额（Capability）设置不合理，会导致作业无法调度或资源分配不公，无法发挥其优势。





🤔 为什么需要Volcano？


通过上一节（§3）的策略→实现映射表可以清晰看到，原生K8s调度器存在三个根本性不足：


    

  1. 缺乏作业级调度视角：原生K8s以单个Pod为调度单位，逐个做出局部最优决策。但分布式训练作业（如PyTorch DDP）需要所有Worker Pod同时运行才能开始计算——如果只有部分Worker被调度成功，已调度的Worker会空转等待，白白浪费昂贵的GPU资源（A100每小时成本约$2-4）。
    2. 

  2. 缺乏多租户资源管理：原生K8s的ResourceQuota仅限制命名空间级别的资源总量，无法实现"队列A保证最低40% GPU、队列B最高使用60%"这样的弹性配额管理。在多团队共享集群时，无法防止单一团队耗尽所有GPU资源。
    3. 

  3. 缺乏拓扑感知能力：原生K8s的nodeAffinity只能做到"调度到带gpu-type=a100标签的节点"这个粒度，无法感知"同一Pod的8张GPU是否通过NVLink互联"或"是否在同一NUMA节点内"。这导致分布式训练的AllReduce通信可能降级为PCIe模式（64 GB/s vs NVLink 600 GB/s），训练吞吐下降30-50%。
    4. 



Volcano的解决方案：通过引入PodGroup CRD实现Gang Scheduling（解决同时运行问题）、Queue CRD实现多租户配额管理（解决资源公平问题）、以及拓扑感知插件（解决通信性能问题）。它本质上是在K8s的"单Pod调度"之上，增加了"作业级调度"这一抽象层，使调度器能够从全局视角优化AI/HPC工作负载。





用户创建 PyTorchJob (由Operator转为PodGroup)
      ↓
Volcano Scheduler
      ├── 检查Queue配额
      ├── 执行Gang调度 (所有Worker Pod需同时满足)




Volcano是CNCF孵化的Kubernetes原生批处理调度器，专为AI/HPC工作负载设计：


# Volcano Job示例
apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: distributed-training
spec:
  minAvailable: 4  # 至少4个Pod
  schedulerName: volcano
  policies:
    - event: PodEvicted
      action: RestartJob
  tasks:
  - replicas: 4
    name: worker
    template:
      spec:
        containers:
        - name: worker
          image: training:latest
          resources:
            limits:
              nvidia.com/gpu: 8

Gang Scheduling保证所有Pod同时启动，避免死锁

公平调度多租户资源公平分配


拓扑感知优化GPU/NUMA亲和性







📊 量化：Gang Scheduling延迟改善


原生K8s调度器逐个调度Pod，对于需要N个Pod同时启动的分布式训练作业，最后一个Pod的等待时间不可控。实测中，100GPU任务（如1节点×8GPU + 12节点×8GPU）在原生K8s下的启动延迟为分钟级（2-5分钟，取决于资源碎片程度），而Volcano的Gang Scheduling确保所有16个Pod要么全部调度成功要么全部等待，将启动延迟降至秒级（10-30秒）。这对抢占式GPU集群尤为重要——避免了部分Worker已启动但等待其他Worker时的GPU空转浪费。


资源利用率影响：Gang Scheduling会牺牲部分调度灵活性——当资源不足以同时满足所有Pod时，整个作业等待而非部分运行。在多租户集群中，这可能导致大作业排队时间增加15-25%，但换来的是作业启动成功率的提升（从约70%到95%+）。

KubeRay与分布式训练


KubeRay与分布式训练


通俗类比：KubeRay是运行在K8s上的“分布式计算指挥家”。它让Ray（一个分布式计算框架）能够轻松在K8s集群上部署和管理。就像指挥家协调乐团（Worker Pod）共同演奏复杂交响乐（分布式训练任务）。


常见误区：在K8s上运行分布式Ray集群时，常见错误是未正确配置Pod间网络策略，导致Worker之间无法通过主机名或Pod IP高效通信，严重拖慢训练速度。同时，共享存储（如NFS、PVC）挂载不一致也会导致数据读取失败。


深入探讨：KubeRay Operator管理三个核心自定义资源：`RayCluster`（定义集群规模）、`RayJob`（提交一次性作业）、`RayService`（部署长期服务）。一个典型的`RayCluster`包含一个Head Pod（负责调度和监控）和多个Worker Pod（执行计算任务）。训练时，Worker Pod通过K8s Service或Pod DNS发现彼此，形成计算集群。


KubeRay Operator (部署在K8s)
      ↓ 监听并管理
RayCluster CRD
      ├── Head Pod (协调者)
      │      ↕ gRPC通信
      ├── Worker Pod 1 (GPU)
      ├── Worker Pod 2 (GPU)



KubeRay是运行Ray集群的Kubernetes Operator，适合分布式ML工作负载：


# Ray Cluster CRD
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: ml-cluster
spec:

  - groupName: gpu-workers
    replicas: 4
    rayStartParams:
      resources: '"{\"gpu\": 8}"'
    template:
      spec:
        containers:
        - name: ray-worker
          image: rayproject/ray-ml:latest
          resources:
            limits:
              nvidia.com/gpu: 8

🔍 失败模式深度讨论



1. GPU显存OOM排查路径


症状：Pod日志出现 CUDA out of memory，或Worker进程被OOMKilled（exit code 137）。


排查步骤：


# Step 1: 确认OOM类型（显存 vs 系统内存）
kubectl describe pod <pod-name> | grep -A 5 "Last State"
# OOMKilled: true → 系统内存超限（cgroup限制）
# exit code 137 → 被内核OOM Killer终止

# Step 2: 查看GPU显存使用峰值
kubectl exec -it <pod-name> -- nvidia-smi --query-gpu=memory.used,memory.total --format=csv
# 或使用DCGM指标（历史峰值）
# DCGM_FI_DEV_MEMORY_USAGE 显示显存使用量

# Step 3: 分析显存分配（PyTorch）
# 在训练脚本中添加：
import torch
print(f"Allocated: {torch.cuda.memory_allocated()/1e9:.2f} GB")
print(f"Reserved:  {torch.cuda.memory_reserved()/1e9:.2f} GB")
print(f"Max Alloc: {torch.cuda.max_memory_allocated()/1e9:.2f} GB")

# Step 4: 常见原因与对策
# - Batch size过大 → 减小batch size或使用梯度累积
# - 模型+激活值超显存 → 启用activation checkpointing
# - 显存碎片 → 设置PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:512
# - 数据加载worker泄漏 → 减少num_workers或设置pin_memory=False



2. NCCL超时问题诊断


症状：训练过程中Worker卡住，日志出现 NCCL error: unhandled system error 或 ncclSystemError，最终触发 NCCL_TIMEOUT（默认1800秒）。


诊断方法：


# Step 1: 确认网络连通性（NCCL使用RDMA/RoCE或TCP）
kubectl exec -it <pod-name> -- nc -zv <other-worker-ip> 29500
# NCCL默认端口范围：29500-29509

# Step 2: 检查NCCL环境变量配置
kubectl exec -it <pod-name> -- env | grep NCCL
# 关键变量：
# NCCL_DEBUG=INFO           # 开启详细日志
# NCCL_SOCKET_IFNAME=eth0   # 指定通信网卡
# NCCL_IB_DISABLE=1         # 禁用IB（如无RDMA环境）
# NCCL_TIMEOUT=3600         # 超时时间（秒）

# Step 3: 验证GPU间通信带宽
kubectl exec -it <pod-name> -- \
  /usr/local/nccl-tests/all_reduce_perf -b 8 -e 128M -f 2 -g 8
# 预期：NVLink环境下AllReduce带宽 > 200 GB/s（8xA100）
# 如带宽 < 50 GB/s → 存在网络瓶颈

# Step 4: 常见根因
# - 网络策略阻断Pod间通信 → 检查NetworkPolicy
# - RDMA驱动未加载 → 检查ib_core内核模块
# - GPU间NVLink降级 → nvidia-smi nvlink --status
# - 节点间MTU不匹配 → 统一设置为9000（Jumbo Frame）



3. Pod被抢占后的数据恢复策略


场景：高优先级作业抢占低优先级作业的GPU资源，被抢占Pod的Worker被终止。


恢复策略：


# 策略1: Checkpoint恢复（推荐）
# 训练代码中定期保存checkpoint
torch.save({
    'epoch': epoch,
    'model_state_dict': model.state_dict(),
    'optimizer_state_dict': optimizer.state_dict(),
    'loss': loss,
}, f'/shared/checkpoint/ckpt_epoch_{epoch}.pt')

# 启动时自动恢复
if os.path.exists('/shared/checkpoint/latest.pt'):
    checkpoint = torch.load('/shared/checkpoint/latest.pt')
    model.load_state_dict(checkpoint['model_state_dict'])
    optimizer.load_state_dict(checkpoint['optimizer_state_dict'])
    start_epoch = checkpoint['epoch'] + 1

# 策略2: Volcano Job自动重启（配置policies）
spec:
  policies:
    - event: PodEvicted
      action: RestartJob    # 被抢占后重启整个Job
    - event: TaskCompleted
      action: CompleteJob   # 某Task完成则Job完成

# 策略3: 共享存储持久化
# 使用PVC挂载共享存储（NFS/CEPH/Lustre）
# 确保checkpoint写入共享存储而非本地磁盘
# 被抢占后新Pod挂载同一PVC即可恢复

# 关键指标监控（Prometheus）
# kube_pod_status_reason{reason="Evicted"} - 被驱逐Pod计数
# volcano_job_restart_count - Volcano Job重启次数
# 告警规则：rate(kube_pod_status_reason{reason="Evicted"}[5m]) > 0

✅ 参考答案与详解
  1. 核心原理: Kubernetes在AI场景中扮演编排层角色，通过声明式API管理Pod和Service。核心组件包括：NVIDIA Device Plugin通过DevicePlugin gRPC接口注册GPU设备，支持MIG模式将A100划分为多个独立实例；Volcano调度器实现Gang Scheduling（所有Pod同时启动避免死锁）、Queue管理和拓扑感知；KubeRay Operator管理RayCluster/RayJob/RayService三种CRD。原生K8s调度器不理解GPU拓扑，可能将同一Pod的4张GPU分配到不同NUMA节点，需要使用拓扑感知调度器。Volcano的PodGroup机制将一组相关Pod作为整体调度，要么全部成功要么全部不调度，避免资源碎片和作业饥饿。
    关键要点: ①GPU Device Plugin将GPU暴露为nvidia.com/gpu extended resource；②Bin-Packing策略打包任务到少数节点，Gang Scheduling确保分布式作业所有Pod同时启动；③Volcano的minAvailable控制最小可用Pod数，policies定义驱逐后的重启策略；④KubeRay的Head Pod负责调度监控，Worker Pod执行计算，通过K8s Service发现彼此；⑤tolerations配合GPU节点的NoSchedule taint实现精确调度
    实际案例: 使用Volcano Job部署4节点×2GPU分布式训练：设置minAvailable=8、schedulerName=volcano，每个worker Pod请求nvidia.com/gpu: 2。配置nodeSelector确保调度到A100节点。同时部署KubeRay Operator管理RayCluster，4个Worker Pod各请求8张GPU，通过rayStartParams配置GPU资源。
    关联知识: 与Slurm（第2章）对比——K8s适合混合工作负载，Slurm适合纯HPC训练。容器化（第4章）提供镜像管理基础，Volcano Queue机制与FinOps（第10章）的成本分配关联。
  2. 核心原理: NVIDIA GPU Device Plugin是K8s管理GPU资源的核心组件，通过K8s设备插件框架（Device Plugin gRPC接口）将GPU暴露为可调度资源（nvidia.com/gpu）。它在每个GPU节点上以DaemonSet形式运行，向Kubelet注册GPU设备，使得Pod可以通过resources.limits请求GPU。设备插件负责挂载GPU设备文件（/dev/nvidia*）和必要的CUDA库。对于A100/H100等支持MIG的GPU，设备插件还实现Multi-Instance GPU模式，将一块物理GPU划分为最多7个独立实例。GPU共享方面，MPS通过共享GPU上下文实现低开销多进程共享（2-5%开销），Time-Slicing通过时间轮转实现GPU复用（5-15%开销），MIG提供硬件级隔离但引入5-10%性能损耗。
    关键要点: ①设备插件通过gRPC向Kubelet注册设备；②Pod通过resources.limits[nvidia.com/gpu]请求GPU；③MIG将A100划分为最多7个独立实例（硬件隔离）；④MPS适合生产推理（低开销共享），Time-Slicing适合开发测试（配置简单）；⑤GPU拓扑感知根据NVLink/PCIe拓扑优化分配
    实际案例: 在10节点×8GPU集群中部署推理服务：使用MIG将每块A100划分为2个3g.40gb实例，每节点提供16个GPU实例。在K8s中通过nodeSelector选择MIG节点，每个推理Pod请求1个MIG实例。同时部署Time-Slicing配置用于开发环境（replicas=4），使开发者在无物理GPU的情况下验证代码。
    关联知识: 与容器化（第4章）关联——GPU镜像需包含匹配的CUDA版本；与监控（第9章）关联——DCGM Exporter采集GPU指标；设备插件版本需与GPU驱动兼容。
  3. 核心原理: AI调度策略解决的核心问题是"如何将多个GPU任务高效、公平地分配到集群节点"。Bin-Packing策略将任务聚合到少数节点（减少资源碎片，提高利用率），与默认的Spread策略（分散Pod到多节点）相反。Gang Scheduling确保分布式作业的所有Pod同时启动——若资源不足则全部等待，避免部分Worker空转浪费GPU。拓扑感知调度考虑GPU间连接方式（NVLink 600 GB/s vs PCIe 64 GB/s），将紧密通信的任务调度在同一节点内。抢占机制允许高优先级任务抢占低优先级任务的资源。这些策略在原生K8s中无法完全实现（原生仅支持Spread和Pod级抢占），需要Volcano等专用调度器。
    关键要点: ①Bin-Packing是NP-Hard问题，通常用FFD贪心近似；②Gang Scheduling通过PodGroup CRD实现（minAvailable控制最小Pod数）；③NVLink亲和调度可提升AllReduce性能30-50%；④拓扑不感知导致跨NUMA延迟增加3-5倍；⑤抢占机制需配合Checkpoint实现无缝恢复
    实际案例: 在100GPU集群中运行3个训练作业（分别需32/32/16GPU）：使用Bin-Packing将前两个作业各分配到4个8GPU节点，第三个作业分配到2个节点，剩余2个节点留给推理服务。使用Gang Scheduling确保每个作业的32个Worker Pod同时启动——当集群只剩24GPU时，第三个作业等待而非部分运行。配置nodeAffinity确保每个作业内的GPU在同一NVLink域内。
    关联知识: 与Volcano（§4）实现对应——Bin-Packing Plugin、PodGroup CRD；与FinOps（第10章）关联——调度效率直接影响GPU利用率和成本；与Slurm（第2章）对比——K8s调度器支持更灵活的拓扑感知。
  4. 核心原理: Volcano是CNCF孵化的K8s原生批处理调度器，专为AI/HPC工作负载设计。它通过引入三个核心CRD扩展K8s调度能力：PodGroup（将一组Pod作为整体调度，minAvailable控制最小可用数）、Queue（实现多租户配额管理）和VolcanoJob（批处理作业抽象）。vc-scheduler实现Gang Scheduling（所有Pod同时满足才调度）、Bin-Packing（聚合任务到少数节点）、DRF公平调度（主导资源公平）和拓扑感知。与原生K8s的关键差异在于：原生调度器是"逐个Pod最优"，Volcano是"作业级全局最优"。生产环境中，Volcano可将GPU利用率从30-40%提升至60-75%，启动延迟从分钟级降至秒级。
    关键要点: ①PodGroup的minAvailable确保Gang Scheduling；②Queue CRD实现弹性配额（capability/deserved）；③DRF公平调度基于主导资源（GPU/CPU中占比最大的）分配；④抢占策略支持Queue优先级；⑤拓扑感知插件优化NUMA/GPU亲和性
    实际案例: 多团队共享集群配置：创建3个Queue（research/engineering/production），分别设置权重40/30/30。production Queue配置preemptable=true，允许抢占低优先级Queue的资源。提交分布式训练VolcanoJob时指定queue: production、minAvailable: 16（4节点×4GPU），配置policies在PodEvicted时RestartJob。通过Gang Scheduling确保16个Worker同时启动，配合Checkpoint实现抢占后无缝恢复。
    关联知识: 与调度策略（§3）映射——Volcano实现了Bin-Packing/Gang Scheduling等策略；与KubeRay（§5）集成——KubeRay生成PodGroup由Volcano调度；与监控（第9章）关联——volcano_queue_allocated_gpu等指标。
  5. 核心原理: KubeRay是运行在K8s上的Ray集群Operator，管理Ray分布式计算框架的生命周期。它通过三个自定义资源实现：RayCluster（定义集群规模——Head Pod + Worker Pod配置）、RayJob（提交一次性训练作业，完成后自动清理）和RayService（部署长期推理服务，支持滚动更新）。Head Pod负责全局调度、GCS（Global Control Store）和Dashboard，Worker Pod执行实际计算任务。训练时，Worker通过K8s Service或Pod DNS发现彼此，利用Ray的Actor模型实现分布式数据并行。KubeRay与Volcano集成时，Volcano负责Gang Scheduling确保所有Worker同时启动，Ray负责任务级分布式执行。
    关键要点: ①RayCluster CRD定义Head/Worker组规格和扩缩容策略；②Head Pod运行GCS和Dashboard，Worker Pod运行Raylet；③RayJob提交一次性作业，完成后清理资源（适合训练）；④RayService部署长期推理，支持canary灰度发布；⑤Worker通过Pod DNS（ray-cluster-head-svc:6379）连接到Head
    实际案例: 部署多模态训练集群：创建RayCluster CRD，Head Pod配置4CPU/16GB内存，Worker组配置8个Pod各8×A100 GPU。提交RayJob运行多模态模型训练，Ray自动将数据并行任务分配到32张GPU。训练完成后RayJob自动清理Worker Pod。同时部署RayService运行在线推理，配置minReplicas=2、maxReplicas=10实现自动扩缩容。
    关联知识: 与Volcano（§4）集成——KubeRay + Volcano是生产级训练标准方案；与容器化（第4章）关联——Ray镜像需包含匹配的Python/CUDA版本；与监控（第9章）关联——ray_cluster_active_workers等指标；与模型上线（第8章）关联——RayService支持灰度发布。
学习路径建议： 学习K8s在AI场景中的角色建议按"概念→原理→实验→调优"四步走。先理解核心概念和术语， 再深入数学原理和工作机制，然后用最小化实验验证理解，最后在真实场景中调优参数。 每步都应记录关键指标（延迟/吞吐/精度），建立数据驱动的优化习惯。
