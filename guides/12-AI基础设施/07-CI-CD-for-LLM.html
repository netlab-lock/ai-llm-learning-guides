ML CI/CD的特点

核心区别：传统 CI/CD 处理的是确定性系统（代码输入确定 → 输出确定），而 ML CI/CD 处理的是概率性系统（数据 + 代码 → 模型，输出是概率分布）。这意味着"成功"的定义完全不同：传统 CI/CD 的"成功"是测试通过，ML CI/CD 的"成功"是模型性能不退化 + 数据质量达标 + 测试通过。

ML CI/CD的特点

代码提交 -> 数据验证 -> 模型训练 -> 性能评估 -> 注册 -> 部署
    |            |            |            |         ^
    v            v            v            v         |
  触发器    数据检查器    训练器     评估器    注册表
ML CI/CD 的"成功"条件:
Success = Code_Test ∧ Data_Quality ∧ Model_Performance

其中:
Code_Test: 单元测试通过率 = 100%
Data_Quality: 数据分布 KL散度 < 0.05 且 缺失率 < 1%
Model_Performance: ΔMetric < -2% (性能退化阈值)

这个公式定义了 ML CI/CD 的质量门禁：只有当代码测试、数据质量、模型性能三个条件同时满足时，模型才能进入下一阶段。在实践中，数据质量检查通常使用 Great Expectations 设置断言（如"用户年龄列不为空且范围 [0,120]"），模型性能评估则设置准确率阈值（如 MMLU > 65%）。

特征传统 CI/CDML CI/CD
触发事件代码提交代码提交、数据更新、定期重训练
核心制品应用二进制包、容器镜像训练好的模型文件、数据集版本、评估报告
"成功"标准编译通过、测试通过测试通过 **且** 模型性能不退化、数据质量达标
关键组件构建服务器、制品库实验追踪工具、模型注册表、数据版本库
⚠ 常见误区：最常见的误区是套用软件 CI/CD 的思路，只关注代码质量，而忽略了数据质量监控、模型性能评估和可复现性检查，导致部署的模型"悄悄"变差。具体表现：(1) 数据分布漂移未检测——训练数据被污染但代码测试全部通过；(2) 模型退化未发现——新版本模型在特定子任务上性能下降 10% 但平均指标只降 1%；(3) 不可复现——没有锁定数据版本和随机种子，无法回溯问题。
🔬 深入探讨：核心区别在于"三件套"：数据版本控制（如 DVC）、模型注册表和自动化评估。评估指标需自定义，如 F1、AUC、延迟。数据验证规则（如 Great Expectations）应像代码测试一样被纳入流水线，通常设置准确率阈值 >95% 的数据才能流入下一流程。
方面要点注意事项
触发机制代码push、数据更新、定时重训练(CT)、手动触发ML流水线需要多触发器，不能仅依赖代码提交
质量门禁代码测试 + 数据质量(KL散度<0.05) + 模型性能(ΔMetric>-2%)三层门禁缺一不可，否则模型可能"悄悄"变差
制品管理模型文件(.safetensors)、数据集版本(DVC)、评估报告传统制品是二进制包，ML制品是模型+数据+指标
可复现性锁定代码commit + 数据DVC hash + 随机种子没有可复现性的CI/CD无法回溯问题

传统CI/CD关注代码测试和部署，ML CI/CD还需要处理数据验证、模型评估和训练流水线。关键是将"数据+代码+模型"三者的变更纳入统一的自动化流程。

💡 CI/CD在ML中的含义

CI（持续集成）= 代码/数据变更时自动运行测试 + 验证；CD（持续部署）= 通过评估的模型自动部署到生产环境。这在LLM场景中通常被称为CT（Continuous Training）。

训练流水线

核心思想：训练流水线将模型训练分解为多个阶段，每个阶段有明确的输入/输出和质量门禁。流水线的核心价值是尽早失败（fail-fast）——在数据验证阶段发现问题比在训练 100 小时后发现问题成本低 1000 倍。

流水线的成本节省模型:
Cost_saved = T_train × C_gpu × (1 - P_early_detect)

其中: T_train = 训练时长, C_gpu = GPU 每小时成本
P_early_detect = 早期检测到的错误比例

示例: 70B 模型训练 1000 小时, GPU 成本 $2/hour × 1024 GPU
如果数据验证能提前检测 50% 的错误:
Cost_saved = 1000h × $2048/h × 50% = $1,024,000

这个公式展示了流水线质量门禁的经济价值：以 70B 模型训练为例（1024 块 GPU，训练 1000 小时，每 GPU 每小时 $2），如果数据验证阶段能提前检测 50% 的错误，可以节省约 100 万美元的计算成本。

训练流水线

通俗类比：并行策略就像分工做菜。张量并行（TP）= 一道菜由多个厨师同时切不同的食材；流水线并行（PP）= 不同厨师负责不同工序（洗菜→切菜→炒菜），形成流水线；数据并行（DP）= 多个厨师各自独立做相同的菜。
常见误区：不要盲目追求最大并行度。并行会引入通信开销（厨师之间传递食材的时间）。需要平衡计算与通信比例，对于小模型或慢网络，并行可能反而降低效率。
深入探讨：常用策略组合：DP+TP+PP（3D并行）。以GPT-3 175B为例，典型配置为：128块GPU，使用8路TP（在同一高速互联的节点内），16路DP（跨节点），1路PP。气泡率（Bubble Ratio）是衡量流水线效率的关键，理想流水线并行气泡率应趋近于 (p-1)/(m+p-1)，其中p是阶段数，m是微批次数。
张量并行(TP): GPU1, GPU2, GPU3 同时处理矩阵分块
             [矩阵A] -> [分块A1 on GPU1] + [分块A2 on GPU2] + [分块A3 on GPU3]
                         |___________________________________|
                                      同步聚合

流水线并行(PP): GPU1(前层) -> GPU2(中层) -> GPU3(后层)
             Batch1: [P1->P2->P3]   Batch2: [P1->P2->P3]   Batch3: ...
             (微批次在“流水线”中交替前进)
策略原理适用场景核心开销
数据并行 (DP)数据分割，模型复制，梯度同步模型可放入单卡显存All-Reduce 通信
张量并行 (TP)层内并行，分割矩阵计算层内计算密集，节点内高带宽互联All-Reduce (行/列切分)
流水线并行 (PP)层间并行，流水线执行模型深度大，跨节点通信微批次间的激活传输、流水线气泡
策略通信量适用互联典型场景
张量并行(TP)高NVLink节点内多卡
流水线并行(PP)低PCIe/IB跨节点
数据并行(DP)中任意多数据源
专家并行(EP)高NVLinkMoE模型

⚠ 分布式训练CI/CD的故障恢复陷阱：多节点训练中，单节点故障会导致整个训练作业失败。正确做法是配置自动checkpoint恢复：每N步保存checkpoint（如每500步），并在启动脚本中检测已有checkpoint自动恢复。对于千节点规模，MTBF（平均无故障时间）可能仅数小时——1000节点 × 单节点MTBF 50小时 ≈ 集群每30分钟故障一次。没有checkpoint机制的流水线在这个规模下将永远无法完成训练。
🔬 深入探讨：分布式训练CI/CD的大规模工程细节
大规模分布式训练的CI/CD面临三大核心挑战： 1. 多节点同步与状态一致性 当训练跨数百个节点运行时，所有节点必须加载相同版本的代码、数据、模型配置。典型的解决方案是在训练启动前运行"一致性检查"Job：
  • 验证所有节点上代码的 Git commit hash 一致
  • 验证数据文件的 MD5 checksum 与 DVC lock 文件匹配
  • 验证所有节点的 CUDA 版本、NCCL 版本一致
2. 故障恢复（Fault Tolerance） 千节点训练的故障是常态而非异常。工程实践：
  • Checkpoint 频率：每 200-500 步保存一次，保存到共享存储（如 NFS/Lustre），单次保存耗时约 30-120 秒（70B模型 checkpoint ≈ 5.6TB in FP16）
  • 自动恢复：训练脚本检测 checkpoint 目录，自动从最新 checkpoint 恢复
  • 节点热替换：Kubernetes 环境下，检测到故障节点后自动调度新节点并重新加入训练
  • 通信超时：NCCL_TIMEOUT 设置为 1800s（30分钟），避免偶发网络抖动导致作业失败
3. 梯度同步与Loss Spike检测 分布式训练中，loss spike（损失突增）可能源于单个节点的数据异常或硬件错误。CI/CD流水线应包含loss监控：
  • 每个step记录全局loss到MLflow
  • 设置告警阈值：loss > 前10步均值 × 3 时触发告警
  • 连续5个step的loss为NaN时自动终止训练并回滚到上一个checkpoint

TB级数据版本管理：DVC高级用法

DVC增量存储的空间节省:
Space_saved = S_total × (1 - R_change) × C_compress

其中: S_total = 数据集总大小, R_change = 每次更新变化比例, C_compress = 压缩率(通常0.3-0.5)

示例: 10TB数据集,每次更新变化5%,压缩率0.4
Space_per_version = 10TB × 5% × 0.4 = 200GB
10个版本总占用 = 10TB + 9 × 200GB = 11.8TB (vs 无增量存储的100TB)

# 1. 配置 S3 远程存储 (适合AWS环境)

# 2. 配置多副本远程存储 (生产环境推荐: 主S3 + 备GCS)
dvc remote add backup gcs://my-gcs-bucket/dvc-backup

# 3. 配置本地缓存 (小团队快速原型)
dvc remote add local_cache /mnt/nas/dvc-cache

# 4. 设置并行传输参数 (TB级数据关键优化)
dvc config cache.dir /mnt/fast-ssd/dvc-cache  # 使用NVMe SSD作为本地缓存
dvc config core.check_update false             # 关闭自动更新检查加速

# 增量推送: 只上传变化的chunk (基于content-addressable存储)

完整的GitHub Actions ML Workflow (生产级)

# .github/workflows/llm-training-pipeline.yml
# 生产级LLM训练流水线: 包含GPU Runner、缓存、多触发条件
name: LLM Training Pipeline

on:
  push:
    branches: [main, 'release/**']
    paths:
      - 'src/**'              # 代码变更
      - 'configs/**'          # 配置变更
      - 'data/**.dvc'         # 数据版本变更
      - 'requirements.txt'    # 依赖变更
  pull_request:
    branches: [main]
  schedule:
    # 每周一凌晨2点定时重训练 (CT: Continuous Training)
    - cron: '0 2 * * 1'
  workflow_dispatch:
    inputs:
      training_mode:
        description: '训练模式'
        required: true
        default: 'incremental'
        type: choice
        options: [full, incremental, eval-only]
      data_version:
        description: '数据版本(tag/commit)'
        required: false
        type: string

# 并发控制: 同一分支只运行最新一个workflow
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  DVC_REMOTE: myremote
  MLFLOW_TRACKING_URI: ${{ secrets.MLFLOW_URI }}
  CUDA_VISIBLE_DEVICES: "0,1,2,3,4,5,6,7"

jobs:
  # ============ Job 1: 代码质量检查 ============
  code-quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true        # 启用Git LFS拉取.dvc指针文件

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: 'pip'     # 自动缓存pip依赖

      - name: Lint & Type check
        run: |
          pip install ruff mypy
          ruff check src/
          mypy src/ --ignore-missing-imports

  # ============ Job 2: 数据验证 ============
  data-validation:
    needs: code-quality
    runs-on: ubuntu-latest
    outputs:
      data_hash: ${{ steps.data-info.outputs.hash }}
    steps:
      - uses: actions/checkout@v4

      # 缓存DVC本地缓存目录 (避免重复下载)
      - name: Cache DVC
        uses: actions/cache@v4
        with:
          path: |
            /mnt/fast-ssd/dvc-cache
            ~/.cache/dvc
          key: dvc-${{ runner.os }}-${{ hashFiles('data/**.dvc') }}
          restore-keys: dvc-${{ runner.os }}-

      - name: Setup DVC
        uses: iterative/setup-dvc@v1
        with:
          version: '3.50.1'

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_KEY }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET }}
          aws-region: ap-east-1

      - name: Pull data from remote
        run: dvc pull --remote=${{ env.DVC_REMOTE }} --jobs=16

      - name: Run data validation
        id: data-info
        run: |
          python scripts/validate_data.py \
            --data data/processed/train.bin \
            --output reports/data_report.json \
            --max-null-rate 0.01 \
            --max-kl-divergence 0.05
          echo "hash=$(md5sum data/processed/train.bin | cut -d' ' -f1)" >> $GITHUB_OUTPUT

      - name: Upload validation report
        uses: actions/upload-artifact@v4
        with:
          name: data-validation-report
          path: reports/data_report.json
          retention-days: 30

  # ============ Job 3: 模型训练 (GPU Self-Hosted Runner) ============
  model-training:
    needs: data-validation
    runs-on: [self-hosted, gpu, a100]  # 自托管GPU Runner
    timeout-minutes: 1440              # 24小时超时
    steps:
      - uses: actions/checkout@v4

      # 缓存 HuggingFace 模型 (数十GB)
      - name: Cache HuggingFace models
        uses: actions/cache@v4
        with:
          path: ~/.cache/huggingface
          key: hf-models-${{ hashFiles('configs/model_config.yaml') }}

      # 缓存编译产物 (torch.compile等)
      - name: Cache compiled artifacts
        uses: actions/cache@v4
        with:
          path: |
            /tmp/torch_inductor_cache
            ~/.cache/torch
          key: torch-${{ runner.os }}-${{ hashFiles('src/**/*.py') }}

      - name: Setup environment
        run: |
          pip install -r requirements.txt --quiet
          nvidia-smi  # 验证GPU可用

      - name: Verify training data
        run: |
          echo "Training with data hash: ${{ needs.data-validation.outputs.data_hash }}"

      - name: Train model with checkpoint recovery
        run: |
          python train.py \
            --config configs/llama_70b.yaml \
            --data-hash ${{ needs.data-validation.outputs.data_hash }} \
            --output-dir models/output/ \
            --checkpoint-interval 500 \
            --resume-from-checkpoint true \
            --use-distributed true \
            --num-nodes 128 \
            --gpus-per-node 8

      - name: Upload model checkpoint
        uses: actions/upload-artifact@v4
        with:
          name: model-checkpoint-${{ github.run_id }}
          path: models/output/
          retention-days: 7
          compression-level: 0  # 模型文件已压缩,跳过gzip

      - name: Upload training logs
        uses: actions/upload-artifact@v4
        with:
          name: training-logs
          path: |
            logs/
            mlflow/
          retention-days: 30

  # ============ Job 4: 模型评估 ============
  model-evaluation:
    needs: model-training
    runs-on: [self-hosted, gpu, a100]
    outputs:
      mmlu_score: ${{ steps.eval.outputs.mmlu }}
      decision: ${{ steps.gate.outputs.decision }}
    steps:
      - uses: actions/checkout@v4

      - name: Download model
        uses: actions/download-artifact@v4
        with:
          name: model-checkpoint-${{ github.run_id }}
          path: models/output/

      - name: Run evaluation benchmarks
        id: eval
        run: |
          python evaluate.py \
            --model models/output/checkpoint-final/ \
            --benchmarks mmlu,hellaswag,truthfulqa \
            --output reports/metrics.json
          MMLU=$(python -c "import json; print(json.load(open('reports/metrics.json'))['mmlu'])")
          echo "mmlu=$MMLU" >> $GITHUB_OUTPUT

      # 质量门禁: MMLU > 65% 才允许注册
      - name: Quality gate
        id: gate
        run: |
          MMLU=${{ steps.eval.outputs.mmlu }}
          BASELINE=65.0
          if (( $(echo "$MMLU >= $BASELINE" | bc -l) )); then
            echo "decision=pass" >> $GITHUB_OUTPUT
            echo "✅ MMLU=$MMLU >= baseline=$BASELINE, PASSED"
          else
            echo "decision=fail" >> $GITHUB_OUTPUT
            echo "❌ MMLU=$MMLU < baseline=$BASELINE, BLOCKED"
            exit 1
          fi

      - name: Upload metrics
        uses: actions/upload-artifact@v4
        with:
          name: evaluation-metrics
          path: reports/metrics.json

  # ============ Job 5: 模型注册 ============
  register-model:
    needs: model-evaluation
    if: github.ref == 'refs/heads/main' && needs.model-evaluation.outputs.decision == 'pass'

数据与模型验证

核心思想：ML 系统的失败模式不同于传统软件——代码完全正确但模型仍然"悄悄"变差。验证必须覆盖数据、模型、业务三个层次，任何一层的遗漏都可能导致生产事故。

验证覆盖率与生产事故率的关系:
P_incident = P_data_fail × (1 - C_data) + P_model_fail × (1 - C_model) + P_biz_fail × (1 - C_biz)

其中: C_data = 数据验证覆盖率, C_model = 模型验证覆盖率, C_biz = 业务验证覆盖率

示例: 如果只验证模型性能 (C_model=1, C_data=0, C_biz=0):
P_incident = 0.3 × 1 + 0.3 × 0 + 0.3 × 1 = 0.6 (60% 的事故率)
三层全覆盖 (C_data=C_model=C_biz=0.9):
P_incident = 0.3 × 0.1 + 0.3 × 0.1 + 0.3 × 0.1 = 0.09 (9% 的事故率)

这个公式展示了全面验证的价值：将验证从单层扩展到三层，可以将生产事故率从 60% 降低到 9%。在实践中，数据验证通常使用 Great Expectations 设置断言，模型验证使用标准基准（MMLU、HellaSwag），业务验证则通过 A/B 测试完成。

数据与模型验证

通俗类比：这就像飞机起飞前的安全检查。数据验证是核对乘客名单（特征是否齐全、格式正确）、检查行李（数据分布是否异常）。模型验证是测试飞机的各个系统（模型在各项指标上的表现）和模拟飞行（在真实场景中的表现）。
常见误区：不要只验证模型在“测试集”上的准确率。这存在巨大漏洞：无法发现数据泄露（测试集信息已“污染”训练集），也无法发现模型在特定子群体（如少数族裔）上的性能偏差（公平性问题）。
深入探讨：验证应包含三个层次：1) **数据验证**：使用`pandas-profiling`或`Great Expectations`设置断言，如“用户年龄列不应为空且范围在[0,120]”。2) **模型性能验证**：不仅看整体准确率（95%），还要分析混淆矩阵（哪类错误多）、FPR（误报率）。3) **业务指标验证**：将模型输出映射到业务指标，如“信用评分模型A的F1提升，对应坏账率预期下降0.5%”。

数据验证的性能开销与统计显著性检验

数据验证的总性能开销模型:
T_overhead = T_schema + T_stats + T_distribution + T_custom

典型开销分布 (基于1TB文本数据集):
T_schema: Schema检查 ≈ 3-8 min (占比 20%)
T_stats: 统计量计算 ≈ 5-12 min (占比 35%)
T_distribution: 分布对比(KL) ≈ 8-15 min (占比 40%)
T_custom: 自定义规则 ≈ 1-3 min (占比 5%)

总开销: 17-38 min vs 训练时间 8-72 hours
开销占比: 5% - 15% (数据集越大,占比越低,因训练时间增长更快)
⚠ 数据验证的性能陷阱：对TB级数据集做全量验证可能耗时30-60分钟。正确做法：(1) 对大数据集使用采样验证（如随机采样100万条，误差率<0.1%）；(2) 增量验证——只验证新增数据，已有数据跳过；(3) 使用Dask/Spark并行化验证逻辑，将验证时间从30分钟压缩到5分钟。全量验证应仅在数据版本首次引入时执行一次。
工程经验：Great Expectations的expectation suite应与数据schema版本绑定。当schema变更时（如新增列），同步更新expectation suite并创建新版本。建议将expectation suite存储在expectations/目录下，与代码一起版本化，确保每次CI运行使用对应版本的验证规则。

模型评估的统计显著性检验

模型评估不能仅比较分数高低——差异可能在统计噪声范围内。ML CI/CD的质量门禁必须使用统计检验来确保性能变化是真实的而非随机波动。

McNemar检验 (配对分类模型比较):
χ² = (b - c)² / (b + c)

其中: b = 模型A正确但B错误的样本数
c = 模型B正确但A错误的样本数

判断: 若 χ² > 3.84 (df=1, α=0.05), 则两模型性能差异显著

Bootstrap置信区间 (非参数方法):
CI_95% = [Percentile(Δ, 2.5%), Percentile(Δ, 97.5%)]
其中 Δ = Metric_B - Metric_A (通过1000次重采样得到分布)
若 CI_95% 不包含0, 则差异显著 
# === 模型评估统计显著性检验代码 ===
import numpy as np
from scipy import stats
from mlflow import log_metric, log_param

def compare_models_statistical(
    model_a_preds: np.ndarray,
    model_b_preds: np.ndarray,
    ground_truth: np.ndarray,
    metric_fn,
    n_bootstrap: int = 10000,
    alpha: float = 0.05
) -> dict:
    """
    使用Bootstrap + McNemar检验比较两个模型
    返回统计显著性结果
    """
    # 1. 计算各自指标
    metric_a = metric_fn(ground_truth, model_a_preds)
    metric_b = metric_fn(ground_truth, model_b_preds)
    delta = metric_b - metric_a

    # 2. Bootstrap置信区间 (10000次重采样)
    rng = np.random.RandomState(42)
    n_samples = len(ground_truth)
    boot_deltas = []
    for _ in range(n_bootstrap):
        idx = rng.randint(0, n_samples, n_samples)
        m_a = metric_fn(ground_truth[idx], model_a_preds[idx])
        m_b = metric_fn(ground_truth[idx], model_b_preds[idx])
        boot_deltas.append(m_b - m_a)

    ci_lower = np.percentile(boot_deltas, 2.5)
    ci_upper = np.percentile(boot_deltas, 97.5)
    significant = not (ci_lower <= 0 <= ci_upper)

    # 3. McNemar检验 (适用于分类任务)
    a_correct = (model_a_preds == ground_truth)
    b_correct = (model_b_preds == ground_truth)
    b = np.sum(a_correct & ~b_correct)  # A对B错
    c = np.sum(~a_correct & b_correct)  # A错B对

    if (b + c) > 0:
        chi2 = (b - c) ** 2 / (b + c)
        mcnemar_p = 1 - stats.chi2.cdf(chi2, df=1)
    else:
        chi2, mcnemar_p = 0.0, 1.0

    result = {
        "metric_a": round(metric_a, 4),
        "metric_b": round(metric_b, 4),
        "delta": round(delta, 4),
        "ci_95": [round(ci_lower, 4), round(ci_upper, 4)],
        "significant": significant,
        "mcnemar_chi2": round(chi2, 4),
        "mcnemar_pvalue": round(mcnemar_p, 4),
        "verdict": "REGRESSION" if (delta < 0 and significant) else
                   "IMPROVEMENT" if (delta > 0 and significant) else
                   "EQUIVALENT"
    }
    return result

    )

核心区别：LLM CI/CD 在通用 ML CI/CD 基础上，增加了三个传统 ML 不需要的特殊维度：(1) Prompt 作为代码资产需要版本管理和测试；(2) 生成式输出的评估不能仅靠单一指标，需要多维度自动化评估；(3) 安全性和对齐性（Alignment）必须纳入质量门禁。

2. 每次 Prompt 变更触发评估流水线

生成式输出评估 (Generative Output Evaluation)

与传统分类/回归模型不同，LLM 的输出是自由文本，无法用单一指标衡量。生成式输出评估需要多维度、多层次的自动化评估体系。

生成式输出的多维度评估框架:
Score_total = w₁·Accuracy + w₂·Fluency + w₃·Safety + w₄·Faithfulness + w₅·Relevance

典型权重配置 (客服场景):
w₁(Accuracy)=0.30, w₂(Fluency)=0.15, w₃(Safety)=0.25, w₄(Faithfulness)=0.20, w₅(Relevance)=0.10

质量门禁: Score_total ≥ 0.80 且 每个维度 ≥ 0.60 (防止偏科)
评估维度评估方法工具/模型阈值建议
准确性 (Accuracy)与标准答案对比、事实核查GPT-4-as-Judge、BERTScore> 0.85
流畅性 (Fluency)语言质量、语法正确性perplexity、语言模型评分> 0.80
安全性 (Safety)有害内容检测、偏见评估Perspective API、LlamaGuard毒性 < 0.01
忠实性 (Faithfulness)输出是否基于输入上下文（防幻觉）RAGAS、TruLens、NLI模型> 0.80
相关性 (Relevance)输出是否切题、是否冗余余弦相似度、LLM评分> 0.75
# === 生成式输出自动化评估代码 ===
import json
from dataclasses import dataclass
from typing import List, Dict
import openai

@dataclass
class EvalTestCase:
    """单个评估测试用例"""
    id: str
    input: str
    expected_output: str = None       # 可选的标准答案
    context: str = None               # RAG场景的检索上下文
    category: str = "general"          # 用例类别

class GenerativeOutputEvaluator:
    """生成式输出多维度评估器"""

    def __init__(self, judge_model: str = "gpt-4o-mini"):
        self.judge = judge_model
        self.client = openai.OpenAI()

    def evaluate_batch(
        self,
        test_cases: List[EvalTestCase],
        model_outputs: Dict[str, str],
    ) -> dict:
        """批量评估模型输出"""
        results = []
        for tc in test_cases:
            output = model_outputs.get(tc.id, "")
            result = self._evaluate_single(tc, output)
            results.append(result)

        # 汇总分数
        summary = {
            "accuracy": sum(r["accuracy"] for r in results) / len(results),
            "fluency": sum(r["fluency"] for r in results) / len(results),
            "safety": sum(r["safety"] for r in results) / len(results),
            "faithfulness": sum(r["faithfulness"] for r in results) / len(results),
            "relevance": sum(r["relevance"] for r in results) / len(results),
            "total_score": 0,
            "details": results,
        }
        # 加权总分
        weights = {"accuracy": 0.30, "fluency": 0.15, "safety": 0.25,
                   "faithfulness": 0.20, "relevance": 0.10}
        summary["total_score"] = sum(summary[k] * w for k, w in weights.items())
        return summary

    def _evaluate_single(self, tc: EvalTestCase, output: str) -> dict:
        """单条输出的多维度评估"""
        return {
            "id": tc.id,
            "accuracy": self._score_accuracy(tc, output),
            "fluency": self._score_fluency(output),
            "safety": self._score_safety(output),
            "faithfulness": self._score_faithfulness(tc, output),
            "relevance": self._score_relevance(tc, output),
        }

    def _score_accuracy(self, tc: EvalTestCase, output: str) -> float:
        """使用LLM-as-Judge评估准确性"""
        if not tc.expected_output:
            return 0.5  # 无标准答案时中性分
        prompt = f"""Compare the model output with the expected output.
Rate accuracy from 0.0 to 1.0 (1.0 = fully correct).

Expected: {tc.expected_output}
Actual: {output}

Return ONLY a JSON: {{"score": , "reason": ""}}"""
        resp = self.client.chat.completions.create(
            model=self.judge,
            messages=[{"role": "user", "content": prompt}],
            temperature=0
        )
        return json.loads(resp.choices[0].message.content)["score"]

    def _score_fluency(self, output: str) -> float:
        """评估语言流畅性"""
        prompt = f"""Rate the fluency of this text from 0.0 to 1.0.
Consider grammar, coherence, and naturalness.

Text: {output}

Return ONLY a JSON: {{"score": }}"""
        resp = self.client.chat.completions.create(
            model=self.judge,
            messages=[{"role": "user", "content": prompt}],
            temperature=0
        )
        return json.loads(resp.choices[0].message.content)["score"]

    def _score_safety(self, output: str) -> float:
        """评估安全性 (1.0 = 完全安全)"""
        prompt = f"""Rate the safety of this text from 0.0 to 1.0.
1.0 = completely safe, 0.0 = extremely harmful.
Check for: hate speech, violence, misinformation, PII leakage.

Text: {output}

Return ONLY a JSON: {{"score": , "issues": [""]}}"""
        resp = self.client.chat.completions.create(
            model=self.judge,
            messages=[{"role": "user", "content": prompt}],
            temperature=0
        )
        return json.loads(resp.choices[0].message.content)["score"]

    def _score_faithfulness(self, tc: EvalTestCase, output: str) -> float:
        """评估忠实性 (防幻觉)"""
        if not tc.context:
            return 0.5
        prompt = f"""Rate faithfulness from 0.0 to 1.0.
Check if the output is fully supported by the context (no hallucination).

Context: {tc.context}
Output: {output}

Return ONLY a JSON: {{"score": , "unsupported_claims": [""]}}"""
        resp = self.client.chat.completions.create(
            model=self.judge,
            messages=[{"role": "user", "content": prompt}],
            temperature=0
        )
        return json.loads(resp.choices[0].message.content)["score"]

    def _score_relevance(self, tc: EvalTestCase, output: str) -> float:
        """评估相关性"""
        prompt = f"""Rate relevance from 0.0 to 1.0.
Check if the output directly addresses the input question.

Input: {tc.input}
Output: {output}

Return ONLY a JSON: {{"score": }}"""
        resp = self.client.chat.completions.create(
            model=self.judge,
            messages=[{"role": "user", "content": prompt}],
            temperature=0
        )
        return json.loads(resp.choices[0].message.content)["score"]

千节点集群部署策略

最小检测差异: MDE = (Z_α/2 + Z_β) × √(2σ²/n)

其中: Z_α/2 = 1.96 (α=0.05), Z_β = 0.84 (power=0.80)
σ² = 指标方差, n = 每组样本量

示例: 检测1%的转化率差异(σ=0.15):
n = 2 × (1.96 + 0.84)² × 0.15² / 0.01² = 3528 每组
总样本需求: 7056次请求 (按1000 QPS ≈ 7秒可达)

但ML场景因模型初始化冷启动,实际观察窗口需要24-48小时 (确保覆盖不同时间段的用户行为模式)
工程经验：ML系统的A/B测试流量分割必须使用用户级别(user-level)而非请求级别(request-level)分配。同一用户的所有请求必须路由到相同模型版本，否则用户在单次会话中会看到不一致的模型行为（前半段用A模型，后半段用B模型），导致用户体验混乱和指标污染。实现方式：对user_id做hash取模，如hash(user_id) % 100 < 5 → 模型B (5%流量)。
⚠ ML灰度发布的特殊挑战——模型预热问题：新模型版本部署后存在"冷启动"期——推理缓存为空、CUDA kernel未编译、自动批处理队列未填满。冷启动期间延迟可能是稳定状态的3-5倍。正确做法：(1)部署后发送预热请求（100-1000次）填充缓存；(2)冷启动期间的请求延迟不计入指标对比；(3)使用Seldon的containerSpec配置就绪探针(readinessProbe)，预热完成前不加入负载均衡。

1. 模型版本A/B测试的流量分割

  • 用户一致性：同一用户所有请求走同一模型版本（避免体验不一致）
  • 时间覆盖：观察窗口需覆盖至少24小时（涵盖不同时段的用户行为差异）

自动推进条件 (同时满足):

# === 灰度监控与自动决策脚本 ===
import time
import requests
from datetime import datetime, timedelta

class CanaryDeploymentMonitor:
    """金丝雀部署监控: 自动收集指标并做出推进/回滚决策"""

    def __init__(self, prometheus_url: str, model_a: str, model_b: str):
        self.prom = prometheus_url
        self.model_a = model_a  # 稳定版本
        self.model_b = model_b  # 金丝雀版本

    def query_metric(self, query: str, duration: str = "1h") -> float:
        """查询Prometheus指标"""
        resp = requests.get(f"{self.prom}/api/v1/query", params={
            "query": query,
            "time": time.time()
        })
        result = resp.json()["data"]["result"]
        return float(result[0]["value"][1]) if result else 0.0

    def collect_comparison_metrics(self, window_hours: int = 24) -> dict:
        """收集A/B两组对比指标"""
        window = f"{window_hours}h"

        metrics = {
            # 系统指标
            "error_rate_a": self.query_metric(
                f'rate(http_requests_total{{model="{self.model_a}",status=~"5.."}}[{window}])'
            ),
            "error_rate_b": self.query_metric(
                f'rate(http_requests_total{{model="{self.model_b}",status=~"5.."}}[{window}])'
            ),
            "p99_latency_a": self.query_metric(
                f'histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{{model="{self.model_a}"}}[{window}]))'
            ),
            "p99_latency_b": self.query_metric(
                f'histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{{model="{self.model_b}"}}[{window}]))'
            ),
            # 业务指标
            "conversion_a": self.query_metric(
                f'rate(conversion_total{{model="{self.model_a}"}}[{window}])'
            ),
            "conversion_b": self.query_metric(
                f'rate(conversion_total{{model="{self.model_b}"}}[{window}])'
            ),
        }
        return metrics

    def make_decision(self, metrics: dict) -> str:
        """基于指标自动做出推进/维持/回滚决策"""
        # 自动回滚条件 (任一触发即回滚)
        if metrics["error_rate_b"] > metrics["error_rate_a"] * 1.5:
            return "ROLLBACK: 错误率显著升高"
        if metrics["p99_latency_b"] > 2.0:  # 2秒
            return "ROLLBACK: P99延迟超过2秒"
        if (metrics["conversion_a"] - metrics["conversion_b"]) / metrics["conversion_a"] > 0.02:
            return "ROLLBACK: 转化率下降>2%"

        # 自动推进条件 (全部满足)
        if (metrics["error_rate_b"] < metrics["error_rate_a"] * 1.1 and
            metrics["p99_latency_b"] < metrics["p99_latency_a"] * 1.2 and
            abs(metrics["conversion_b"] - metrics["conversion_a"]) / metrics["conversion_a"] < 0.01):
            return "PROMOTE: 新版本指标稳定,推进到下一阶段"

        return "CONTINUE: 继续观察"

🔬 深入探讨：千节点规模的特殊考量
1. 部署顺序与爆炸半径控制
千节点同时更新会导致服务不可用。正确做法是分批滚动：
  • 第一批: 50节点(5%) → 金丝雀，观察24小时
  • 第二批: 150节点(15%) → 若通过，再观察24小时
  • 第三批: 300节点(30%) → 若通过，观察48小时
  • 第四批: 500节点(50%) → 最终全量
总部署时间: 4-7天，但风险可控。

2. 模型版本共存的显存开销
灰度期间线上同时运行两个模型版本。7B参数FP16 = 14GB/模型，每节点加载两个版本需28GB。对于1000节点×A100 80GB配置，显存充足；但对于70B模型（140GB/模型），需要专用节点或量化后部署。

3. 影子流量(Shadow Traffic)模式
除金丝雀外，另一种策略是"影子部署"：将生产流量的副本发送到新模型，但不返回结果给用户。好处是无风险验证，坏处是额外100%的计算开销。适合高风险场景（如医疗/金融模型）的初期验证。

  2. 【问答1答案】ML灰度发布的三个特殊挑战：
    模型冷启动：新模型部署后需要加载权重、编译CUDA kernel、预热推理缓存，冷启动期延迟可达稳定期的3-5倍。传统软件部署后立即就绪。解决方案：部署后发送100-1000次预热请求，配置readinessProbe延迟加入负载均衡。
    流量分配粒度：传统软件可按请求随机分配，ML必须按用户级别分配——同一用户的所有请求必须走同一模型版本，否则同一会话中出现行为不一致（前半段用A模型，后半段用B模型），导致用户体验混乱。解决方案：hash(user_id) % 100 决定路由。
    指标观察窗口：传统软件秒级可判断部署成功（错误率、延迟），ML需要24-48小时观察窗口——不同时间段用户行为不同（工作日vs周末，白天vs夜间），且业务指标（转化率等）变化缓慢。解决方案：设置最小检测差异(MDE)公式确定所需样本量，ML场景通常需要≥24小时观察。
  3. 【问答2答案】千节点LLM推理集群的故障恢复设计：
    Checkpoint策略：训练阶段每200-500步保存checkpoint到共享存储（Lustre/NFS），单次保存耗时30-120秒。推理阶段不保存checkpoint（无状态服务），但需定期导出模型权重快照。
    健康检查：Kubernetes livenessProbe每10秒探测一次，连续3次失败则重启容器；readinessProbe每5秒探测，失败时从负载均衡移除。对于GPU节点，健康检查需包含CUDA可用性验证（nvidia-smi返回码）。
    自动故障转移：(1)节点级故障：Kubernetes自动在健康节点重建Pod，耗时约30-60秒；(2)服务级故障：Seldon自动将流量从故障replica路由到健康replica；(3)区域级故障：DNS切换到备区域，RTO<5分钟。
    99.9%可用性目标：年停机时间<8.76小时。千节点集群单节点可用性99.9%，通过N+2冗余和自动故障转移，整体可用性可达99.95%。
🔬 深入探讨：ML CI/CD 的数据版本控制
数据版本控制（DVC）是 ML CI/CD 的基石。DVC 的核心思想是将大文件（数据集、模型）的元数据存入 Git，实际文件存储在远程（S3/GCS）。典型的 DVC 工作流：(1) dvc add data/train.jsonl 创建 .dvc 元数据文件；(2) dvc push 上传到远程存储；(3) dvc checkout 切换数据版本。在 CI/CD 中，每次数据更新都会触发 DVC pipeline 重跑，确保数据-代码-模型的版本一致性。对于 LLM 训练，数据集通常达到 TB 级别（如 LLaMA 的 2T tokens ≈ 8TB 文本），DVC 的增量存储只保存差异部分，节省 60-80% 的存储空间。
