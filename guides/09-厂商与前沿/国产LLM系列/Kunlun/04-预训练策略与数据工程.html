天工Agent搜索的预训练数据哲学

与纯对话模型不同，天工在预训练阶段就需要为后续的Agent搜索能力打下基础。在预训练数据的选择上，天工特别注重信息密度高的语料——包括结构化的知识库文章、带有引用来源的百科条目、以及包含搜索结果摘要的问答对。这些数据帮助模型在预训练阶段就学习如何从大量信息中筛选、综合和引用关键内容，为后续的Agent搜索对齐提供了良好的初始化。

天工的预训练数据还特别包含了大量与搜索引擎交互相关的语料，如搜索查询日志、搜索结果页摘要、以及网页点击行为数据。这些数据虽然不直接用于训练模型执行搜索，但帮助模型理解用户的搜索意图表达方式和信息需求模式。昆仑万维在数据采集过程中与旗下搜索引擎产品深度协作，获取了大量高质量的搜索交互数据，经过脱敏和过滤后纳入预训练语料。这种"搜索+语言"的双轮驱动数据策略，使得天工在预训练阶段就具备了比纯对话模型更强的信息检索和综合能力。

💡 Agent搜索专用语料的"搜索掩码预测"任务：天工在预训练中引入辅助任务——随机遮蔽搜索结果中的关键信息片段，要求模型根据上下文和搜索查询预测被遮蔽内容。这一任务帮助模型学习从搜索结果中提取关键信息的能力，对后续Agent搜索的信息综合表现提升显著。在消融实验中，加入该任务使SeedMGS 66.1分→69.8分(提升5.6%)。
⚠️ 搜索语料的时效性陷阱：搜索引擎结果变化快速，预训练数据中的搜索结果摘要可能很快过时（平均半衰期约6个月）。天工团队通过URL活跃度检测和时间戳过滤移除过时内容，每周增量更新搜索语料库。如果忽略时效性，模型会学到过时的信息模式，导致Agent搜索时对新颖查询的处理能力下降。

Agent搜索场景的专用数据采集

天工大模型在数据来源与采集阶段就为Agent搜索能力做了专门规划。除了通用的网页数据、书籍语料、代码数据和数学数据外，天工还采集了大量与信息检索和知识综合相关的专业语料。搜索引擎结果摘要数据是其中最具价值的部分——这些数据包含了用户查询、搜索结果标题、摘要片段和URL的完整结构化信息，帮助模型学习如何从搜索结果中提取关键信息。天工团队还采集了大量的多跳推理数据（multi-hop reasoning），即需要多次信息检索和综合才能回答的复杂问题，这类数据对于训练Agent搜索的多步推理能力至关重要。

在数据采集的规模和质量控制上，天工团队建立了专门的Agent搜索数据管线。搜索相关语料的采集量约占总预训练数据的3-5%，但经过严格筛选后保留的高质量部分对模型的搜索能力提升贡献显著。采集过程中特别注意避免引入搜索引擎的广告内容和低质量SEO页面，通过URL质量评分和内容过滤器将这些噪声数据剔除。

💡 搜索查询日志的脱敏处理：天工使用的搜索查询日志经过严格脱敏——移除所有PII（个人身份信息）、IP地址和用户ID，仅保留查询文本和时间戳。脱敏后的查询日志约50亿条，覆盖中英文主流搜索场景。这些数据帮助模型理解用户的搜索意图表达方式，如"附近好吃的"隐含地理位置需求。
⚠️ 搜索结果的采样偏差：搜索引擎结果存在位置偏差——排名靠前的结果被点击概率远高于靠后的结果。如果直接用搜索结果作为训练数据，模型会学到"排名靠前=更相关"的偏见。天工通过随机打乱结果顺序和加入负采样来缓解这一问题。

Agent搜索语料的清洗挑战

天工大模型的数据清洗流水线在处理Agent搜索相关语料时面临独特的挑战。搜索结果摘要数据通常包含大量重复片段——同一个网页可能出现在多个不同查询的结果中，且摘要内容高度相似。天工团队在标准的MinHash去重之外，针对搜索语料开发了"语义去重"策略：使用嵌入向量计算文档间的语义相似度，将语义相同但表述不同的搜索结果合并。此外，搜索结果中还可能包含过时信息（如已下架的商品页面、已失效的链接），天工通过URL活跃度检测和时间戳过滤移除这些时效性敏感的内容。

搜索语料的质量评估也与通用文本不同。天工团队发现，搜索引擎返回的结果中约有15-20%的内容质量较低（如内容农场、自动生成的摘要），这些低质量内容如果进入预训练数据会严重影响模型的搜索结果评估能力。为此，天工在质量评分阶段增加了"信息可信度"维度，使用专门训练的分类器评估文本的事实准确性和来源可靠性。

💡 天工七阶段清洗流水线的核心指标：整个流水线从原始网页数据到最终训练语料的通过率约为12-15%。URL级过滤基于500万条域名黑名单和2000万条URL模式规则（过滤率35%），文档级去重采用MinHash+LSH算法（Jaccard相似度阈值0.8，消除25%重复），质量评分使用FastText+BERT双分类器对流畅性/信息密度/知识价值三维打分（仅保留均分>6.5的内容，过滤40%）。最终1T token精洗语料在MMLU上达到62.3分，反超未清洗5T token的59.8分。
⚠️ MinHash去重的计算开销陷阱：对PB级网页数据做MinHash去重需要数千CPU核心运行数天。天工使用Apache Spark分布式处理，将2000+核心集群并行化，并使用LSH索引预计算加速Jaccard相似度匹配——将去重复杂度从O(n²)降至O(n log n)。如果直接用暴力两两比较，处理时间将从数周增长到数月。

MinHash+LSH 去重算法实现

天工文档级去重的核心算法：使用6-gram生成MinHash签名，LSH分桶加速Jaccard相似度匹配，阈值0.8判定重复。以下是完整Python实现：

#!/usr/bin/env python3
# 天工数据清洗 - MinHash+LSH文档去重实现
# 参数: num_perm=128(签名长度), ngram_size=6(6-gram), threshold=0.8(Jaccard阈值)

import hashlib
import numpy as np
from collections import defaultdict
from typing import List, Set, Tuple, Dict

# ========== 1. MinHash签名生成 ==========

def shingle_text(text: str, n: int = 6) -> Set[str]:
    """将文本切分为n-gram集合（天工使用6-gram）"""
    text = text.lower().strip()
    # 按字符级n-gram切分（中英文通用）
    return {text[i:i+n] for i in range(len(text) - n + 1)}

def generate_minhash_signature(shingles: Set[str], num_perm: int = 128) -> np.ndarray:
    """
    生成MinHash签名向量
    num_perm: 置换数量（天工使用128，平衡精度与速度）
    使用多个哈希函数模拟随机置换
    """
    signature = np.full(num_perm, np.uint32(-1), dtype=np.uint32)
    for shingle in shingles:
        # 对每个shingle计算num_perm个哈希值
        for i in range(num_perm):
            # 使用不同seed生成独立哈希: h_i(x) = hash(x + seed_i)
            hash_val = int(hashlib.md5(
                f"{shingle}_{i}".encode()
            ).hexdigest(), 16) & 0xFFFFFFFF
            # 保留最小哈希值（MinHash核心操作）
            if hash_val < signature[i]:
                signature[i] = hash_val
    return signature

# ========== 2. LSH分桶与相似度计算 ==========

def lsh_bands(signature: np.ndarray, b: int = 16, r: int = 8) -> List[bytes]:
    """
    LSH分带哈希: 将签名分为b个band，每个band有r行
    天工参数: b=16, r=16 (num_perm=128=16*8)
    理论保证: Jaccard>=0.8的文档有>99%概率至少碰撞1个band
    """
    assert b * r == len(signature), "b*r必须等于签名长度"
    band_hashes = []
    for i in range(b):
        band = signature[i*r : (i+1)*r]
        # 将band内所有哈希值拼接后哈希为一个bucket key
        band_hashes.append(hashlib.md5(band.tobytes()).digest()[:4])
    return band_hashes

def jaccard_similarity(sig_a: np.ndarray, sig_b: np.ndarray) -> float:
    """通过MinHash签名估计Jaccard相似度"""
    return np.mean(sig_a == sig_b)

# ========== 3. 去重主逻辑 ==========

class MinHashLSHDeduplicator:
    """天工MinHash+LSH去重器 - 处理百万级文档"""
    
    def __init__(self, num_perm: int = 128, ngram_size: int = 6,
                 threshold: float = 0.8, bands: int = 16):
        self.num_perm = num_perm
        self.ngram_size = ngram_size
        self.threshold = threshold
        self.bands = bands
        self.rows = num_perm // bands
        # LHS索引: band_hash -> [doc_id, ...]
        self.lsh_index: Dict[bytes, List[int]] = defaultdict(list)
        self.signatures: List[np.ndarray] = []
        self.documents: List[str] = []
    
    def add_document(self, doc_id: int, text: str) -> bool:
        """
        添加文档，返回True表示保留，False表示重复丢弃
        流程: 生成shingle → MinHash签名 → LSH分桶 → 候选匹配 → 精确验证
        """
        shingles = shingle_text(text, self.ngram_size)
        if len(shingles) < self.ngram_size:
            return True  # 过短文档直接保留
        
        sig = generate_minhash_signature(shingles, self.num_perm)
        
        # LSH候选检索: 找到所有共享至少1个band的文档
        candidate_ids: Set[int] = set()
        band_hashes = lsh_bands(sig, self.bands, self.rows)
        for band_hash in band_hashes:
            candidate_ids.update(self.lsh_index[band_hash])
        
        # 精确验证: 计算候选文档的Jaccard相似度
        for cand_id in candidate_ids:
            sim = jaccard_similarity(sig, self.signatures[cand_id])
            if sim >= self.threshold:
                return False  # 重复文档，丢弃
        
        # 保留: 更新索引
        self.signatures.append(sig)
        self.documents.append(text)
        for band_hash in band_hashes:
            self.lsh_index[band_hash].append(doc_id)
        return True
    
    def deduplicate(self, documents: List[str]) -> Tuple[List[str], dict]:
        """批量去重，返回(保留文档列表, 统计信息)"""
        kept, removed = 0, 0
        result = []
        for i, doc in enumerate(documents):
            if self.add_document(i, doc):
                result.append(doc)
                kept += 1
            else:
                removed += 1
        stats = {
            "total": len(documents),
            "kept": kept,
            "removed": removed,
            "dedup_rate": removed / len(documents) if documents else 0
        }
        return result, stats

数据配比策略

核心洞察：天工采用动态数据配比策略，初始配比中信息检索相关语料占8-12%，第二阶段提升到15-20%。核心机制：每训练1000步评估各领域验证集loss变化，对loss下降缓慢的领域自动增加采样比例（增幅上限1.5倍），对收敛领域适当降低比例（降幅下限0.7倍）。相比静态配比，动态策略带来约3.2%的平均性能提升。

Agent搜索能力的数据配比优化

天工大模型在数据配比策略上针对Agent搜索能力进行了专门优化。在初始配比中，信息检索相关语料（搜索结果摘要、知识库文章、FAQ数据）占总数据的8-12%，这一比例是通过大量消融实验确定的——过低会导致模型的搜索结果理解和综合能力不足，过高则会压缩通用语言能力的训练空间。在第二阶段精细化训练中，搜索相关语料的比例提升到15-20%，同时增加了多跳推理数据和工具调用轨迹数据的比例。天工团队发现，搜索数据与代码数据之间存在正向协同效应——代码训练提升的结构化推理能力有助于模型理解搜索结果中的结构化信息，因此在配比调整时会保持两者的平衡增长。

在动态数据配比方面，天工团队为Agent搜索能力建立了专门的评估基准，包括搜索结果摘要质量、多跳问答准确率和信息引用准确性三个维度。每训练1000步，模型在这些基准上的表现会被评估，如果搜索相关能力的loss下降速度低于预期，系统会自动增加搜索语料的采样比例。这种基于能力指标的动态配比机制确保了Agent搜索能力在整个预训练过程中持续提升，而不会因为通用语料的稀释效应而出现能力退化。

💡 动态配比的数据质量监控系统：天工团队开发了基于模型loss的数据质量监控系统。每训练1000步，评估模型在各领域验证集上的loss变化，对loss下降缓慢的领域（表明模型尚未充分学习）自动增加该领域数据比例，增幅上限为原比例的1.5倍；对loss已收敛的领域（下降率<0.1%/100步）适当降低比例，降幅下限为原比例的0.7倍。这种动态调整机制使得模型在训练后期能够将计算资源集中在最需要提升的能力领域。
⚠️ 搜索语料比例过高的风险：当初始配比中搜索相关语料超过15%时，模型的通用语言能力（如创意写作、情感对话）会出现明显退化——在WritingBench上下降约8%。原因是搜索语料的信息密度高但表达方式单一（标题+摘要），过度训练会使模型偏向简短的摘要式回答。天工通过将搜索语料比例控制在8-12%（初始）来避免这一问题。

基于Loss变化率的自适应采样公式

天工动态数据配比的核心数学机制：通过指数移动平均计算各领域loss下降率，据此更新采样比例。以下是完整形式化描述：

天工自适应采样公式:
┌─────────────────────────────────────────────────────────────┐
│  定义:                                                       │
│    D = {d₁, d₂, ..., dₖ} — 数据领域集合 (k=5: 网页/书籍/    │
│          代码/数学/搜索)                                     │
│    pᵢ(t) — 第t轮时领域dᵢ的采样比例 (Σpᵢ=1)                  │
│    Lᵢ(t) — 第t轮时领域dᵢ的验证集loss                         │
│    Δt = 1000步 — 评估间隔                                    │
├─────────────────────────────────────────────────────────────┤
│  Step 1: 计算Loss下降率 (指数移动平均)                        │
│    ρᵢ(t) = α · (Lᵢ(t-Δt) - Lᵢ(t))/Lᵢ(t-Δt)               │
│          + (1-α) · ρᵢ(t-Δt)                                │
│    α = 0.3 (平滑系数)                                        │
│    → ρᵢ(t) > 0 表示loss在下降, 值越大下降越快               │
├─────────────────────────────────────────────────────────────┤
│  Step 2: 计算采样比例更新量                                   │
│    δᵢ(t) = β · (ρ̄(t) - ρᵢ(t)) / ρ̄(t)                    │
│    β = 0.15 (调整速率)                                       │
│    ρ̄(t) = (1/k) Σⱼ ρⱼ(t) (平均下降率)                      │
│    → 下降慢的领域(ρᵢ<ρ̄): δᵢ>0, 增加比例                     │
│    → 下降快的领域(ρᵢ>ρ̄): δᵢ<0, 减少比例                     │
├─────────────────────────────────────────────────────────────┤
│  Step 3: 更新采样比例 (带约束)                                │
│    p̃ᵢ(t+1) = pᵢ(t) · (1 + δᵢ(t))                          │
│    pᵢ(t+1) = clip(p̃ᵢ(t+1), 0.7·pᵢ⁰, 1.5·pᵢ⁰)             │
│    pᵢ(t+1) = pᵢ(t+1) / Σⱼ pⱼ(t+1)  (归一化)               │
│    pᵢ⁰ = 领域dᵢ的初始比例                                    │
│    → 上界1.5x防止单一领域过度采样                            │
│    → 下界0.7x保证各领域最低训练量                             │
├─────────────────────────────────────────────────────────────┤
│  收敛判定:                                                   │
│    若 ρᵢ(t) < ε (ε=0.001/100步) 持续3轮 → 判定为收敛       │
│    收敛领域采样比例降至下限 0.7·pᵢ⁰                          │
│    释放的计算资源分配给未收敛领域                             │
└─────────────────────────────────────────────────────────────┘
💡 公式参数的工程调优经验：平滑系数α=0.3在响应速度与噪声抑制间取得平衡——α过小(0.1)导致配比调整滞后，过大(0.5)导致对短期波动过度反应。调整速率β=0.15确保每轮配比变化不超过15%，避免训练分布突变。天工团队在消融实验中测试了β∈{0.05,0.10,0.15,0.20,0.30}，β=0.15时MMLU最优(62.3)，β=0.30时loss波动增大37%。
⚠️ 动态配比震荡的失败模式：当评估间隔Δt过短(≤500步)或平滑系数α过大(≥0.6)时，采样比例出现频繁振荡——某领域比例在1000步内从12%→18%→9%→15%反复波动。后果：(1)训练loss波动增大42%，收敛速度减慢约20%；(2)模型能力出现"遗忘-重学"循环，MMLU在训练后期反而下降1.2-1.8分。正确做法：(1)评估间隔不低于1000步；(2)使用EMA平滑(α≤0.3)；(3)设置单次调整幅度上限(≤15%)；(4)引入"冷却期"——每次调整后至少2000步内不再修改配比。

Tokenizer 设计

核心洞察：天工的Tokenizer针对Agent搜索场景做了专门优化——URL的平均token数降低约40%，中文搜索查询的编码质量显著提升。标准BPE分词器处理URL时效率极低（一个URL可能被拆分为20-30个token），天工在词表中加入URL相关子词单元和常见域名token，将URL编码效率提升40%。

Agent搜索场景的Tokenizer优化

天工大模型的Tokenizer设计在Agent搜索场景下需要特别考虑URL、搜索查询和结构化数据的编码效率。标准的BPE分词器在处理URL时效率极低——一个典型的URL可能被拆分为20-30个token，严重影响模型处理搜索结果时的上下文利用率。天工团队在词表中专门加入了URL相关的子词单元和常见域名token（如".com"、".cn"、"www."等），将URL的平均token数降低了约40%。

在搜索查询的编码方面，天工的Tokenizer针对中文搜索查询的分词特性进行了优化。中文搜索查询通常比英文更短但信息密度更高，且经常包含未登录词（如新品牌名、网络用语）。天工通过在中文语料上训练的SentencePiece模型配合搜索查询语料的微调，显著提升了对搜索关键词的编码质量。

💡 URL优化的量化效果：在未经优化的Tokenizer中，一个典型URL如"https://www.example.com/path/to/page"会被拆分为约25个token。天工通过加入"https://"、"www."、".com"、".cn"等子词单元，将同一URL压缩到约15个token，节省40%的token数。这在处理包含大量URL的搜索结果时尤为重要——一个包含100个搜索结果页的数据集，URL优化后可节省约1000个token的上下文空间。
⚠️ 词表膨胀的风险：为URL和搜索查询添加专用token会增大数据词表——天工的词表从标准的32K扩展到约48K（增加50%）。更大的词表意味着更大的嵌入层（embedding layer），增加了约15%的模型参数。天工通过将低频URL子词的嵌入维度从d_model降为d_model/2来部分补偿这一开销。

训练超参数与技巧

核心洞察：天工3.0的最终训练消耗约12000张A100-80G GPU运行约45天，总计算量约2.1×10^24 FLOPs。训练采用渐进式序列长度扩展（4K→8K→16K→32K→128K）配合RoPE base频率的渐进调整，有效避免了训练loss尖峰（实测最终loss波动<2%）。

Agent搜索预训练的超参数选择

天工大模型在训练超参数的选择上考虑了Agent搜索能力的特殊需求。在序列长度方面，搜索场景对长上下文的需求尤为突出——一个完整的Agent搜索交互可能包含用户查询、多轮搜索结果、中间推理过程和最终回答，总长度可达数千token。天工在预训练中采用了渐进式序列长度扩展策略，从4K开始，最终扩展到128K，确保模型能够处理复杂的多步搜索交互。

在训练技巧方面，天工团队为Agent搜索能力引入了"搜索掩码预测"辅助任务。在预训练过程中，随机遮蔽搜索结果中的关键信息片段，要求模型根据上下文和搜索查询预测被遮蔽的内容。这个辅助任务帮助模型学习从搜索结果中提取关键信息的能力，对后续Agent搜索的信息综合表现提升显著。

💡 渐进式序列长度扩展的稳定性技巧：天工在训练进行到60%时从4K扩展到8K，80%时扩展到16K，最后5%扩展到32K。每次扩展时同步调整RoPE base频率（从10000逐步降至2500），避免了位置编码失配导致的loss尖峰。实测显示渐进式扩展的loss波动<2%，而直接训练32K序列的loss波动可达15-20%。
⚠️ 长序列训练的梯度不稳定：当序列长度从4K扩展到128K时，注意力矩阵的梯度方差增大约30倍，容易导致梯度爆炸。天工通过将梯度裁剪阈值从1.0降至0.5（在序列长度>32K时）和使用更保守的学习率（降低30%）来保持训练稳定。

    实际案例: 天工团队在Skywork R1V4训练中的具体解决方案：数据清洗使用Apache Spark分布式处理将PB级原始网页数据清洗任务并行化到2000+核心的集群上，MinHash去重使用LSH（Locality Sensitive Hashing）索引预计算加速Jaccard相似度匹配——将去重复杂度从O(n²)降至O(n log n)。动态配比评估采用异步评估管线——在主训练进程中fork出评估进程，共享模型参数checkpoint，避免阻塞主训练流。序列长度从4K扩展到32K时，采用渐进式扩展（每训练20%步长扩展一次序列长度）配合RoPE base频率的渐进调整，有效避免了训练loss尖峰（实测最终loss波动<2%）。搜索语料的更新频率为每周增量更新，使用URL活跃度检测和时间戳过滤移除过时内容。多语言采样采用温度采样策略（T=2.0），将中文、日语等低频语言的采样率提升约1.5-2倍。
    关联知识: 七阶段数据清洗流水线中的MinHash+LSH算法与02章MoE架构中专家路由的均衡性目标一致——都是通过算法设计实现"均衡"（数据去重均衡/专家激活均衡）。动态数据配比的"基于loss变化率调整"方法与强化学习中的学习率调度有共同的数学直觉——对收敛慢的方向加大投入。PII脱敏与01章Skywork Desktop"数据不出设备"的隐私安全承诺形成呼应——训练阶段保护数据隐私，推理阶段保护用户隐私。多阶段预训练策略的超参数设置（AdamW β1=0.9, β2=0.95、梯度裁剪最大范数1.0、权重衰减0.1）是经过大量消融实验验证的最优配置。
  3. 核心原理: 将天工的两阶段高质量数据策略与三类替代路线对比：大规模弱清洗策略（如LLaMA系列的"数据量大+轻度清洗"路线）、纯合成数据策略（如 phi系列教科书级合成数据）、以及课程学习策略（如Chinchilla的最优计算分配方案）。天工路线的核心理念是"每一token都要有价值"——通过末端清洗和精细化训练，使每个训练token的信息密度最大化。LLaMA路线的优势是简单可扩展（需要较少的数据清洗人力），但在同等token数下质量不如天工的精洗数据（天工1T token≈LLaMA 5MMLU效果，2.5%的MMLU差距）。纯合成数据策略（如phi-2的"教科书质量"数据）在小参数量模型（<5B）上效果极好，但扩展到30B+规模时合成数据的多样性不足问题暴露。课程学习策略（Chinchilla的20token/param最优比例）提供了理论最优的计算分配公式，但实际中数据质量不均匀使得理论最优难以实现。
    关键要点: ①天工路线：高质量中等规模数据——适合Agent应用 ②LLaLA路线：大规模弱清洗——适合通用基础模型 ③纯合成数据路线：极高质量小规模——适合小参数量模型（<5B） ④课程学习路线：理论最优计算分配——实现难度大但效果上限高 ⑤天工的独特优势：Agent搜索专用语料预训练+动态配比机制是竞品不具备的
    实际案例: 某AI创业公司要训练一个30B级别的代码助手模型，三个方案对比：方案A（天工路线）：七阶段清洗后保留12-15%高质量代码+数学+文档语料，代码数据配比从10%动态提升至20%，训练约3万亿token。方案B（LLaMA路线）：5万亿token弱清洗通用语料（仅URL去重+基础过滤），代码比例恒定10%。实验结果（HumanEval基准）：方案A达到58.3% Pass@1，方案B达到52.1% Pass@1，天工路线领先6.2个百分点。方案C（合成数据+课程学习）：使用CodeLlama-Python微调数据+Chinchilla最优配比，理论上最优，但实际训练后发现合成代码数据的风格过于单一，模型生成代码缺乏多样性（distinct-2指标下降23%）。结论：对于30B级别的Agent模型训练，天工的高质量数据策略是投入产出比最优的选择。
