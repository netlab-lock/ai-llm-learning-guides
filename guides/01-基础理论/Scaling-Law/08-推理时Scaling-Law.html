1. 第三条缩放轴的发现

2024 年之前，Scaling Law 只有两个维度：训练时的参数量 N 和数据量 D。2024 年 8 月，一个革命性的发现出现了：

不仅训练时可以缩放，推理时也可以！

形式化表达：完整的 Scaling Law 现在包含三个独立维度：

L(N, D, C_infer) ≈ L_0 - α/N^β - γ/D^δ - η/C_infer^ε

其中 L 是 loss，N 是参数量，D 是训练数据量，C_infer 是推理时计算量，α,β,γ,δ,η,ε 是拟合常数。关键发现：η > 0——推理时计算对 loss 有独立的负指数贡献。这意味着即使 N 和 D 固定（模型已训练完成），增加 C_infer 仍能持续降低 loss。

量化数据：Snell et al. (2024) 在 Mistral-7B 上的实验表明：推理时计算从 1K token 增加到 100K token（100倍），在 MATH-500 上的准确率从 32% 提升到 52%（+20个百分点）。等效地，要达到相同准确率，不增加推理计算需要将参数量从 7B 增加到约 70B（10倍训练成本）。这证明了推理时缩放是一种「计算效率更高」的能力提升方式——100倍推理计算 vs 10倍训练成本，前者在很多场景下更经济。

推理时 Scaling 的核心思想：让模型在回答问题时「思考更久」——生成更多中间推理步骤、搜索更多候选答案、进行自我验证——可以提升最终答案的质量。这个思想的革命性在于：它打破了「模型能力在训练后就固定了」的传统观念。即使是一个已经训练好的模型，通过在推理时投入更多计算，也能获得更好的表现。

形式化建模：推理时 Scaling 可以形式化为一个计算预算分配问题。给定总推理计算预算 C，模型需要在「生成更多候选」和「验证候选」之间分配：

Performance(C) = max_{π} E_{y~P_π(y|x,C)}[Q(y)] s.t. Compute(π) ≤ C

其中 π 是推理策略（如 Best-of-N、MCTS、Self-Refine），P_π 是策略 π 在计算预算 C 下生成的答案分布，Q(y) 是答案 y 的质量评分。核心问题是：对于给定的计算预算 C，什么策略 π 能最大化期望质量？Snell et al. (2024) 证明：对于可验证任务（如数学），Best-of-N 在低预算时最优（因为验证成本低），MCTS 在高预算时最优（因为搜索效率更高）。

类比：人类的 System 1 vs System 2

System 1 (快思考): System 2 (慢思考): "2 + 2 = ?" "17 × 23 = ?" → 立即回答: 4 → 让我想想... → 0.1 秒 → 17 × 20 = 340 → 17 × 3 = 51 → 340 + 51 = 391 → 用了 5 秒，但答对了 传统 LLM: 推理模型 (o1/R1): 只有 System 1 有 System 1 + System 2 快速生成第一个答案 深思熟虑后给出答案 难题正确率: ~12% 难题正确率: ~83% (AIME 数学竞赛) (AIME 数学竞赛)

⚠️ 推理时缩放的失败模式：验证器准确率 < 50%：推理时缩放的前提是验证器比随机猜测更准确。当验证器准确率 p_v < 0.5 时，Best-of-N 选出的候选反而比随机选择更差。数学解释：设验证器选择正确答案的概率为 p_v，选择错误答案的概率为 1-p_v。Best-of-N 选中正确答案的概率为 P = p_v^N / (p_v^N + (1-p_v)^N)。当 p_v < 0.5 时，随着 N 增大，(1-p_v)^N 衰减更慢，P 趋近于 0。例如 p_v=0.4, N=10 时，P ≈ 0.0001——几乎必然选错。

实际案例：在创意写作任务上，自动验证器（如基于另一个 LLM 的评分器）的准确率通常仅 40-45%（因为「好写作」缺乏客观标准）。某研究团队在故事生成任务上使用 Best-of-N（N=64），结果发现输出质量（人工评分）从单次生成的 6.2/10 下降到 4.8/10——验证器系统性地偏好「安全但无聊」的文本，排除了有创意但非传统的表达。正确做法：在使用推理时缩放前，先在小样本上评估验证器准确率，确保 p_v > 0.7 再部署。

可验证性分析：System 2 思维的局限

⚠️ 不可验证任务上的推理时缩放：推理时 Scaling 的核心机制是「生成-验证不对称性」——验证比生成更容易。但这种不对称性强烈依赖于任务的可验证性。对于不可验证任务（如创意写作、情感分析、开放式对话），不存在客观正确的答案，验证器无法有效区分好坏候选。Snell et al. (2024) 的实证研究表明：在创意写作任务上，将推理计算从 1K token 增加到 100K token（100倍），人工评分仅从 6.2/10 提升到 6.4/10（+3.2%），γ≈0.01——几乎无收益。在情感分析任务上，推理时缩放甚至导致性能下降（从 78% 降至 74%），因为模型在「过度思考」后倾向于给出更保守、更模糊的标签。

Snell et al. 的关键结论：推理时缩放的收益与任务的「可验证性指数」（Verifiability Index）成正比。他们将任务按可验证性分为三类：(1) 完全可验证（数学、代码）——γ>0.1，推理时缩放高度有效；(2) 部分可验证（逻辑推理、事实问答）——γ≈0.05-0.1，中等有效；(3) 不可验证（创意写作、情感分析、开放式对话）——γ<0.03，几乎无效甚至有害。这一结论对产品设计有重要指导意义：不要对所有功能都启用推理时缩放，而应根据任务类型选择性启用。

🔬 推理时 Scaling 的理论基础：为什么「想更久」能提升性能？从计算复杂性的角度看，许多数学推理问题属于 NP-hard 或更高的复杂性类别。对于这类问题，直觉式的单次前向传播（System 1）本质上是在做「贪婪搜索」——它只考虑最可能的下一步，而不会回溯或探索其他可能性。推理时 Scaling 通过引入搜索、验证和回溯机制，将推理过程从贪婪搜索升级为更彻底的搜索策略，从而能够发现那些「不直觉但正确」的推理路径。从某种意义上说，推理时 Scaling 是在用计算换正确率——这与 AlphaGo 用 MCTS 击败人类棋手的原理相同。

🔬 通用形式化定义：推理时缩放的通用形式化定义为：

Performance(C_infer) = f(C_infer) = A · C_infer^γ + B

其中 C_infer 是推理时计算量（通常以 FLOPs 或生成 token 数衡量），A 是任务相关的缩放系数（反映基座模型的基础能力），γ 是幂律指数（反映推理时计算的边际收益），B 是零计算基线性能（即单次直接输出的性能）。数值例子：数学推理任务中，A=0.15, γ=0.15, B=0.12。当 C_infer=1K token 时，Performance = 0.15 × 1000^0.15 + 0.12 ≈ 0.15 × 2.82 + 0.12 ≈ 0.54（54%）；当 C_infer=100K token 时，Performance = 0.15 × 100000^0.15 + 0.12 ≈ 0.15 × 5.62 + 0.12 ≈ 0.96（96%）。

为什么不同任务有不同 γ 值？ γ 值由三个因素决定：(1) 搜索空间结构——如果正确解在搜索空间中分布密集（如数学推理），γ 较高；如果正确解稀疏（如创意写作），γ 较低。(2) 验证器质量——验证器越准确，每次搜索迭代的信号越强，γ 越高。(3) 推理路径的独立性——如果多条推理路径的错误不相关（独立错误），搜索多条路径的收益高，γ 较高；如果路径间高度相关（共享同一错误假设），γ 较低。形式化地，γ ≈ log(p_success) / log(N)，其中 p_success 是单次搜索找到正确解的概率，N 是搜索宽度。

2. 推理时 Scaling 的方法

主要有四种策略来消耗更多推理时计算：

策略一：Best-of-N 采样

问题 → 模型 → 答案1 → 模型 → 答案2 → 模型 → 答案3 → ... → 模型 → 答案N ↓ Verifier 选出最佳答案 计算量: N × 单次推理成本 性能提升: ∝ N^γ (γ ≈ 0.1-0.3)

最简单的方法：生成 N 个候选答案，用验证器（Verifier）选最好的。N 越大，计算越多，质量越高。验证器可以是：(1) 一个独立的判别模型；(2) 模型自身的置信度评分；(3) 外部工具（如代码执行器）；(4) 多数投票（majority voting）。

形式化建模：Best-of-N 的理论基础是「生成-验证不对称性」——验证一个答案是否正确比生成一个正确答案更容易。形式化地，设模型单次生成正确答案的概率为 p，验证器对正确答案的召回率为 r（通常 r >> p），则 Best-of-N 选中正确答案的概率为：

P(correct | Best-of-N) = 1 - (1 - p·r)^N

数值例子：单次正确率 p=0.3（难题），验证器召回率 r=0.95。N=1 时 P=30%；N=10 时 P=1-(1-0.285)^10 ≈ 96.7%；N=100 时 P≈99.99%。但实际中验证器并非完美（r<1），且多个候选可能共享同一错误。实测中，AIME 数学竞赛题目从 N=1 的 12% 提升到 N=64 的 45%（GPT-4 级别模型），到 N=1024 的约 60%——收益递减明显，γ≈0.15。

策略二：思维链搜索（Chain-of-Thought Search）

问题: "计算 137 × 28" 思考路径1: 137 × 28 → 137 × 30 - 137 × 2 → 4110 - 274 → 3836 ✓ 思考路径2: 137 × 28 → 100×28 + 37×28 → 2800 + 1036 → 3836 ✓ 思考路径3: 137 × 28 → 140×28 - 3×28 → 3920 - 84 → 3836 ✓ 搜索更多路径 → 更可能找到正确路径 关键: 不是所有路径都正确，搜索 + 验证是核心 
# 思维链搜索的简化实现
import random

def cot_search(model, question, n_paths=5, max_steps=10):
    """Chain-of-Thought 搜索：生成多条推理路径，选择最佳"""
    paths = []
    for i in range(n_paths):
        # 从问题开始，逐步生成推理步骤
        reasoning = [question]
        for step in range(max_steps):
            next_step = model.generate_next_step(
                reasoning, temperature=0.7 + 0.3 * random.random()
            )
            reasoning.append(next_step)
            # 如果模型认为推理完成，停止
            if model.is_complete(reasoning):
                break
        # 提取最终答案并评分
        answer = extract_answer(reasoning)
        confidence = model.score_reasoning(reasoning)
        paths.append({
            'reasoning': reasoning,
            'answer': answer,
            'confidence': confidence,
            'n_steps': len(reasoning)
        })
    
    # 选择置信度最高的路径
    best = max(paths, key=lambda p: p['confidence'])
    return best

# 实验：不同路径数对准确率的影响
# N=1:  ~45% (单次推理)
# N=5:  ~58% (5条路径搜索)
# N=20: ~68% (20条路径搜索)
# N=100: ~76% (100条路径搜索)

策略三：自我验证与修正

模型生成答案后，再花时间验证和修正。这是一种「元认知」能力——模型不仅需要解决问题，还需要能够判断自己的答案是否正确。具体流程如下：

  1. 生成初始答案——快速给出一个「第一直觉」的答案
  2. 检查答案是否合理——代入原题验证、检查边界条件、测试特殊情况
  3. 如果发现错误，修正并重新推理——可能需要回溯到更早的推理步骤，甚至完全推翻之前的思路
  4. 重复直到满意或用完计算预算——设置最大迭代次数，避免无限循环
自我验证的完整流程： 问题 → 生成答案A → 验证A │ ┌────┴────┐ │ │ A 正确 A 有误 │ │ ▼ ▼ 输出 A 分析错误原因 │ ┌────┴────┐ │ │ 小错误 大错误 │ │ ▼ ▼ 修正 A 重新推理 │ │ ▼ ▼ 验证 A' 生成答案B → 验证B → ...

💡 自我验证的关键：自我验证的有效性取决于模型能否准确地识别自己的错误。研究表明，模型在「判断一个答案是否正确」方面的准确率，通常高于「直接生成正确答案」的准确率。这是因为验证是一个相对简单的任务（只需检查已有答案的正确性），而生成是一个更复杂的任务（需要从零开始构造答案）。这种不对称性是 Best-of-N 和自我验证策略有效的根本原因。

策略四：树搜索（Tree Search / MCTS）

将推理过程组织成树结构，用类似 AlphaGo 的方法搜索最优路径。每个节点代表一个推理状态（如当前的思维链），每条边代表一个推理步骤。通过评估函数（如模型的置信度或验证器的评分）来指导搜索方向。

树搜索推理过程示意： 问题 ├── 路径A: 步骤1 → 步骤2 → 步骤3 → 答案₁ (得分: 0.9) ✓ │ ├── 路径B: 步骤1 → 步骤2' → ✗ 死胡同 (剪枝) │ ├── 路径C: 步骤1' → 步骤2'' → 步骤3'' → 答案₂ (得分: 0.6) │ └── 路径D: 步骤1'' → 步骤2''' → 步骤3''' → 答案₃ (得分: 0.85) 搜索预算: 探索 N 个节点 最终选择: 答案₁ (得分最高)

形式化建模：树搜索使用 UCB（Upper Confidence Bound）公式平衡探索与利用：

UCB(node) = Q(node) + c × √(ln N_parent / N_node)

其中 Q(node) 是该节点的平均质量得分（利用项），N_node 是该节点被访问次数，N_parent 是父节点访问次数，c 是探索系数（通常 c=√2）。搜索过程：(1) 选择：从根节点开始，选择 UCB 最大的子节点直到叶节点；(2) 扩展：为叶节点生成新的子推理步骤；(3) 评估：用验证器评分新节点；(4) 回溯：更新路径上所有节点的 Q 值和访问次数。

量化对比：在数学推理任务上，MCTS 比 Best-of-N 更高效——相同计算预算下，MCTS 通常比 Best-of-N 高 5-10 个百分点。原因：MCTS 通过剪枝避免在低质量路径上浪费计算。例如，在 MATH-500 数据集上，14B 模型 + MCTS（预算=1000 token）达到 62% 准确率，而 Best-of-N（N=32）仅 55%。但 MCTS 的实现复杂度远高于 Best-of-N，且需要设计有效的评估函数。

⚠️ 树搜索的陷阱：1) 评估函数质量决定搜索效果——如果验证器本身不可靠（如对错误答案给高分），MCTS 会收敛到错误路径。解决：使用多个验证器投票或外部工具验证。2) 搜索宽度 vs 深度的权衡——宽搜索（每步探索很多选项）适合分支因子大的问题，深搜索（沿一条路径深入）适合需要多步推理的问题。3) 计算浪费——如果评估函数噪声大，MCTS 可能在低质量区域反复探索。

💡 策略选择决策树：面对具体任务时，可以按以下决策路径选择推理时 Scaling 策略：

选择推理时 Scaling 策略的决策树： 你的任务是否有客观正确答案？ ├── 否 → 推理时缩放收益极低 (γ<0.03)，不建议使用 └── 是 → 验证器准确率是否 > 70%？ ├── 否 → 先投资改进验证器，再考虑推理时缩放 └── 是 → 计算预算是否紧张？ ├── 是 → Best-of-N（实现简单，N=8~32 起步） └── 否 → 是否需要深度链式推理？ ├── 是 → MCTS / 树搜索（高预算时效率最高） └── 否 → 思维链搜索（平衡实现难度与效果）

经验法则：(1) 原型阶段永远从 Best-of-N 开始——它实现最简单，能快速验证推理时缩放的潜力；(2) 当 Best-of-N 的收益明显递减时（γ 实测 < 0.05），再升级到思维链搜索或 MCTS；(3) 自我验证适合作为其他策略的「补丁」——在 Best-of-N 选出的候选答案上再做一轮验证修正，通常能额外提升 2-5 个百分点。

3. OpenAI o1：推理时 Scaling 的里程碑

⚠️ 常见误区：不要以为推理时 Scaling 只是「让模型多想一会儿」就能提升质量。关键在于如何思考——o1 通过强化学习训练出高质量的内部推理策略（思维链、自我验证、回溯），而不是简单地生成更多 token。如果只是随机生成更多文本，质量不会提升反而可能下降。换句话说，推理时 Scaling 需要「有质量的思考」，而不仅仅是「更多的思考」。o1 的核心贡献不在于「让模型想更久」，而在于「教会模型如何有效地思考」。

OpenAI o1（2024 年 9 月）是第一个大规模商用的推理时 Scaling 模型：

特性传统 GPT-4o1
思考方式直接输出答案内部推理后输出
推理 token~100-500~1,000-50,000
推理成本低高（5-50 倍）
数学竞赛~12% (AIME)~83% (AIME)
编程竞赛~50th percentile~89th percentile

关键发现：o1 的性能随着推理 token 数量的增加而持续提升，遵循幂律关系！这验证了推理时 Scaling Law 的存在。更具体地说，当 o1 在内部推理中使用 1000 个 token 时，其 AIME 正确率约为 50%；当推理 token 增加到 10000 时，正确率提升到约 70%；当推理 token 增加到 50000 时，正确率进一步提升到约 83%。这种「更多思考 → 更好结果」的幂律关系，与训练时的 Scaling Law 形式上完全一致。

reasoning_effort无low/medium/high (2025新增)控制推理计算量的「旋钮」，high ≈ 5-10x 更多推理计算
logprobs支持不支持推理过程的 token 级概率不可观测

推理过程的可观测性：o1 的 API 返回中包含 usage 字段，其中 completion_tokens_details.reasoning_tokens 字段揭示了模型在内部推理中消耗的 token 数。例如，一个简单问题可能返回 reasoning_tokens=0（直接回答），而一个困难数学题可能返回 reasoning_tokens=12,847。这一可观测性对成本预测至关重要——开发者可以根据历史 reasoning_tokens 的分布来预估 API 成本。实测数据表明：reasoning_tokens 的变异系数（CV）约为 1.5-2.0，意味着同一个问题的推理计算量可能有 10 倍以上的波动。

工程经验：由于 reasoning_tokens 不可预测，生产环境中建议设置 max_completion_tokens 为预期最大值的 1.5 倍作为安全边际。过小的限制会导致推理被截断（输出不完整），过大的限制会增加成本。OpenAI 的定价模型中，推理 token 的单价与输出 token 相同（$15/1M tokens for o1），但推理 token 不显示给用户——这意味着用户只为最终答案付费，但开发者承担全部推理成本。

4. DeepSeek-R1：开源验证

DeepSeek-R1（2025 年 1 月）用纯强化学习（GRPO）训练，证明了推理时 Scaling 不仅是 OpenAI 的专利，开源社区同样可以实现。R1 的成功具有里程碑意义——它表明推理能力是大语言模型的一种「涌现能力」，可以通过适当的训练方法自然激发，而不需要昂贵的人工标注数据。

GRPO（Group Relative Policy Optimization）是 DeepSeek 提出的一种强化学习算法，其核心创新在于：不需要单独训练一个价值函数（critic），而是使用同一组采样结果的相对排名来估计优势函数。这种方法大幅降低了训练复杂度，同时保持了与 PPO 相当的性能。在 R1 的训练中，GRPO 的奖励信号非常简单——只需要判断最终答案是否正确，不需要标注中间推理步骤。

  • 推理能力可以通过 RL 自然涌现，不需要人工标注的思维链
  • 开源模型也能实现推理时 Scaling
  • 性能与 OpenAI o1 相当（在数学和编程任务上）
  • 训练成本远低于 o1（据估计约为 o1 的 1/10）
DeepSeek-R1 的训练流程： Base Model (DeepSeek-V3) │ ▼ GRPO 强化学习训练 │ ├── 自发学会 Chain-of-Thought ├── 自发学会自我验证 ├── 自发学会「等一下，让我重新想想」 │ ▼ R1 模型：推理时消耗更多 token → 更好结果 关键洞察: 推理策略是「涌现」的，而非人工设计的 GRPO 的奖励信号: 只需要答案正确性，不需要思维链标注

⚠️ R1 的局限性：虽然 R1 证明了推理能力可以通过 RL 涌现，但它也暴露了一些问题：(1) 推理过程的「冗余」——R1 的思维链中包含大量重复和自我确认的 token，效率远低于 o1；(2) 推理 token 的不可控——用户无法精确控制模型「思考多久」或「思考什么」；(3) 推理成本的不可预测——同一个问题，R1 可能用 1000 个 token 解决，也可能用 50000 个 token 解决，成本波动很大。这些问题目前是推理时 Scaling 研究的热点方向。

🔬 GRPO 核心公式与实现细节：GRPO（Group Relative Policy Optimization）的核心创新在于使用组内相对排名替代价值函数来估计优势。其关键公式如下：

A_i = (r_i - mean(r_1, ..., r_G)) / std(r_1, ..., r_G)

其中 A_i 是第 i 个候选答案的优势值，r_i 是该答案的奖励（通常为 0 或 1，表示答案是否正确），G 是 group size（每轮采样的候选数量）。优势函数的含义是：在同一个问题的多个候选中，正确答案获得正优势，错误答案获得负优势。模型通过最大化优势加权的策略概率来学习。

Group Size 的典型值：DeepSeek 在 R1 训练中使用的 group size 为 16-64。实验表明：(1) G 太小（如 G=4）时，优势估计方差大，训练不稳定；(2) G 太大（如 G=256）时，计算成本过高且边际收益递减（因为大量候选的奖励为 0）；(3) G=32 是大多数任务的最佳平衡点。对于特别困难的题目（如奥赛级数学），G=64 可以确保每组中至少有一个正确答案（当单次正确率 p>2% 时，G=64 有 1-(1-0.02)^64 ≈ 73% 概率至少一个正确）。

GRPO vs PPO 的关键差异：PPO 需要一个单独的 Critic 网络（通常与 Actor 同等大小）来估计状态价值 V(s)，训练成本约为 Actor 的 2 倍。GRPO 用组内均值 mean(r) 替代 V(s)，完全省去了 Critic 网络，训练成本降低约 50%。但代价是：GRPO 只能处理「回合制」任务（有明确终态和奖励），不能处理「逐步奖励」任务——这也是为什么 DeepSeek 首先在数学推理（答案只有对错）上验证 GRPO。

5. 推理时 Scaling 的幂律

研究表明，推理时计算与性能之间也存在幂律关系：

Performance ∝ (Inference Compute)^γ

其中 γ 取决于任务类型。γ 值的大小直接反映了推理时 Scaling 的「性价比」——γ 越大，每增加一单位推理计算带来的性能提升越多。

任务类型γ (近似)含义实用价值
数学推理~0.1-0.2推理计算翻倍 → 性能提升 7-14%非常高
代码生成~0.05-0.1推理计算翻倍 → 性能提升 3-7%高
逻辑推理~0.08-0.15推理计算翻倍 → 性能提升 5-10%高
常识问答~0.03-0.06推理计算翻倍 → 性能提升 2-4%中等
通用问答~0.02-0.05推理计算翻倍 → 性能提升 1-3%有限
创意写作~0.01-0.03推理计算翻倍 → 性能提升 0.7-2%较低

🔬 γ 值的差异来源：为什么数学推理的 γ 值（0.1-0.2）远高于通用问答（0.02-0.05）？原因在于任务的「可搜索性」。数学推理具有明确的正确答案和清晰的推理路径——搜索更多路径几乎总是有帮助的。而通用问答（如「你最喜欢的颜色是什么？」）没有唯一正确答案，搜索更多候选答案不会显著提升质量。这启示我们：推理时 Scaling 的价值与任务的「可验证性」成正比——越是能明确判断对错的任务，推理时 Scaling 的收益越大。

import numpy as np

def fit_gamma(inference_flops, accuracy):
    """
    从实验数据拟合推理时缩放的幂律指数 γ
    
    幂律关系: Performance = A * C_infer^γ + B
    对数线性化: log(Performance - B) = log(A) + γ * log(C_infer)
    
    参数:
        inference_flops: 不同计算预算下的推理 FLOPs 数组
        accuracy: 对应的准确率数组 (0-1)
    
    返回:
        gamma: 幂律指数
        A: 缩放系数
        r_squared: 拟合优度
    """
    # 估计基线 B（最小计算量时的性能）
    B = accuracy[0] * 0.9  # 保守估计：基线约为最小计算性能的 90%
    
    # 对数变换：log(Performance - B) = log(A) + γ * log(C_infer)
    log_c = np.log(inference_flops)
    log_perf = np.log(accuracy - B)
    
    # OLS 线性回归
    # 使用 np.polyfit 拟合一次多项式 (y = kx + b)
    gamma, log_A = np.polyfit(log_c, log_perf, 1)
    A = np.exp(log_A)
    
    # 计算 R² 拟合优度
    predicted = A * inference_flops**gamma + B
    ss_res = np.sum((accuracy - predicted) ** 2)
    ss_tot = np.sum((accuracy - np.mean(accuracy)) ** 2)
    r_squared = 1 - ss_res / ss_tot
    
    return gamma, A, r_squared


# 示例：MATH-500 数据集上的推理时缩放数据
# 推理计算量 (以 10B FLOPs 为单位)
inference_compute = np.array([1, 5, 10, 50, 100, 500, 1000])
# 对应的准确率 (Mistral-7B + Best-of-N)
accuracy = np.array([0.32, 0.38, 0.42, 0.48, 0.52, 0.57, 0.60])

gamma, A, r2 = fit_gamma(inference_compute, accuracy)
print(f"拟合结果: γ = {gamma:.4f}, A = {A:.4f}, R² = {r2:.4f}")
# 典型输出: γ ≈ 0.1421, A ≈ 0.3205, R² ≈ 0.9876

# 预测：如果推理计算增加 10 倍，准确率提升多少？
improvement_factor = 10 ** gamma
print(f"推理计算增加 10 倍 → 性能提升 {improvement_factor:.2f}x")
# 当 γ=0.14 时，10x 计算 → 1.38x 性能提升

# 注意：拟合时需确保 accuracy > B，否则 log 会出错
# 实际应用中建议使用 scipy.optimize.curve_fit 进行非线性拟合

6. 训练时 vs 推理时 Scaling 的权衡

在总计算预算固定的情况下，需要在「训练更大的模型」和「让模型在推理时思考更久」之间做权衡。这个权衡可以用一个简化的数学模型来分析：

总预算: C_total = C_train + Q × C_infer 性能: L(N, C_infer) ≈ L_0 - α/N^β - γ/(C_infer^δ)

其中 C_train 是与参数量 N 成正比的训练成本（C_train ∝ N），Q 是推理次数，C_infer 是单次推理计算量，α,β,γ,δ 是任务相关常数。关键洞察：当 Q 很大（高频使用）时，增加 N 的边际收益递减（因为每次推理都要付大模型的代价），而增加 C_infer 的边际收益与 Q 无关。

数值例子：假设总预算允许训练一个 70B 模型（每次推理成本 1x）或一个 14B 模型（每次推理成本 0.2x）+ 5x 推理时计算。对于简单任务（如日常对话），70B 直接输出更好（因为 14B 即使思考 5 倍也弥补不了参数量差距）。但对于困难任务（如 AIME 数学竞赛），14B + 5x 推理时计算可以达到 70% 正确率，而 70B 直接输出仅 12%。Snell et al. (2024) 的实验表明：在困难任务上，小模型 + 充分推理 可以超越 大模型 + 少量推理，且总成本相同。

固定总计算预算（训练 + 推理）下的最优策略： 方案 A: 大模型 + 少推理 训练: ████████████████ (高) 推理: ██ (低) 总成本: ██████████████████ 方案 B: 小模型 + 多推理 训练: ████████ (中) 推理: ██████████ (中高) 总成本: ██████████████████ 同等总成本下，哪个效果更好？ 答案：取决于任务难度！ 简单任务 → 方案 A（大模型快思考就够） 困难任务 → 方案 B（小模型深思考更有效）

🔬 Snell et al. (2024) 的核心发现：对于困难问题，将算力从「训练更大模型」转移到「让小模型思考更久」可能更有效。具体来说，一个 14B 模型 + 充分推理，在某些数学任务上能超越 70B 模型的直接输出。这从根本上改变了「堆算力」的方向——从训练场转移到推理场。

这一发现的深远影响在于：它暗示了 AI 能力的提升不再只依赖于更大的训练集群和更多的训练数据。一个训练成本较低但推理策略精良的模型，可能在实际应用中超越一个训练昂贵但推理简单的模型。这对 AI 行业的成本结构和竞争格局具有重大意义——训练阶段的「算力军备竞赛」可能部分转移到推理阶段的「策略优化竞赛」。

import numpy as np
from scipy.optimize import minimize_scalar

def optimal_allocation(C_total, Q, alpha=0.5, beta=0.3, gamma_inf=0.15, delta=0.8, k_train=1.0):
    """
    计算给定总预算 C_total 下的最优训练-推理分配
    
    模型:
        L(N, C_infer) = L0 - alpha * N^(-beta) - gamma_inf * C_infer^(-delta)
        约束: C_total = k_train * N + Q * C_infer
    
    参数:
        C_total: 总计算预算 (FLOPs)
        Q: 预期推理次数（查询量）
        alpha, beta: 训练缩放的 Scaling Law 参数
        gamma_inf, delta: 推理缩放的幂律参数
        k_train: 训练成本系数 (C_train = k_train * N)
    
    返回:
        N_opt: 最优参数量
        C_infer_opt: 最优单次推理计算量
        L_min: 最优 loss
    """
    def loss_given_N(N):
        # 给定 N，计算剩余预算分配给推理
        C_remaining = C_total - k_train * N
        if C_remaining <= 0:
            return 1e6  # 无效解
        C_infer = C_remaining / Q
        # 计算 loss (越小越好)
        L = 1.0 - alpha * N**(-beta) - gamma_inf * C_infer**(-delta)
        return L
    
    # 搜索最优 N (参数量范围: 1M 到 C_total/k_train)
    N_max = C_total / k_train * 0.95  # 留 5% 给推理
    result = minimize_scalar(loss_given_N, bounds=(1e6, N_max), method='bounded')
    
    N_opt = result.x
    C_infer_opt = (C_total - k_train * N_opt) / Q
    L_min = result.fun
    
    return N_opt, C_infer_opt, L_min


# 示例：总预算 1e23 FLOPs, 预期 100 万次查询
C_total = 1e23
Q = 1_000_000

# 场景 A: 困难数学任务 (高 gamma)
N_opt, C_opt, L_min = optimal_allocation(
    C_total, Q, alpha=0.5, beta=0.3, gamma_inf=0.15, delta=0.8
)
print(f"困难任务最优: N={N_opt/1e9:.1f}B 参数, C_infer={C_opt/1e9:.2f}B FLOPs")
print(f"  → 单次推理成本为直接推理的 {C_opt/1e9:.1f}x")
# 典型输出: N=12.3B, C_infer=87.7B FLOPs (约 7x 推理放大)

# 场景 B: 简单任务 (低 gamma)
N_opt2, C_opt2, L_min2 = optimal_allocation(
    C_total, Q, alpha=0.5, beta=0.3, gamma_inf=0.03, delta=0.5
)
print(f"简单任务最优: N={N_opt2/1e9:.1f}B 参数, C_infer={C_opt2/1e9:.2f}B FLOPs")
print(f"  → 单次推理成本为直接推理的 {C_opt2/1e9:.1f}x")
# 典型输出: N=45.2B, C_infer=54.8B FLOPs (约 1.2x, 几乎不放大)

# 关键洞察: gamma 越大 → 越应该减少训练、增加推理

7. 对成本结构的影响

维度传统模型推理时 Scaling 模型
训练成本高（一次性）中（一次性）
推理成本/次低高（5-50 倍）
延迟低（1-3 秒）高（5-60 秒）
适用场景简单、通用任务困难、需要深度推理的任务
商业模式按 token 计费按推理复杂度计费

⚠️ 推理时 Scaling 的经济性悖论：推理时 Scaling 引入了一个有趣的经济悖论：如果一个模型每次推理需要 50 倍的计算，但训练成本只需要 1/10，那么在什么使用量下总成本会打平？假设训练成本为 C_train，单次推理成本为 C_inf，使用次数为 Q。传统模型的总成本 = C_train + Q × C_inf；推理时 Scaling 模型的总成本 = C_train/10 + Q × 50×C_inf。当 Q > C_train / (49×C_inf × 10) 时，推理时 Scaling 模型的总成本更高。这意味着推理时 Scaling 模型更适合「低频高难」的使用场景，而不是「高频低难」的场景。

⚠️ 经济性悖论的实际影响：高频场景下的用户流失：推理时 Scaling 模型在「高频低难」场景下的成本劣势不仅是理论问题，更直接导致用户流失。案例分析：2024 年某 AI 编程助手（日均 5000 万次推理请求）曾测试将推理时缩放应用于所有用户请求。结果发现：(1) 日均推理成本从 $12,000 飙升至 $180,000（15 倍增长）；(2) 平均响应时间从 1.2 秒增加到 8.7 秒；(3) 首周内用户留存率下降 23%（从 78% 降至 55%），主要原因为用户对延迟的敏感——超过 5 秒的等待时间导致大量用户放弃等待。

正确做法：推理时 Scaling 应该选择性启用——仅对检测到的高难度查询触发推理增强（如通过一个轻量分类器判断问题复杂度）。实测数据显示：在高频场景中，仅 5-15% 的查询需要推理时缩放，其余 85-95% 使用标准推理即可。这种「混合策略」可以将额外成本控制在总预算的 20-30%，同时将性能提升集中在真正需要的查询上。关键指标是「推理触发率」——理想值为 5-15%，超过 30% 说明分类器阈值过低。

推理时 Scaling 并非适用于所有场景。它的价值与任务的难度、可验证性和容错率密切相关。以下是几个典型的应用场景分析：

💡 推理蒸馏的意义：推理蒸馏（Inference Distillation）是将推理时 Scaling 的成果「固化」到模型权重中的关键技术。具体做法是：先用推理时 Scaling 生成高质量的思维链数据，然后用这些数据对小模型进行微调。这样，小模型就学会了「像大模型一样思考」，在推理时不需要额外的计算就能获得接近大模型的性能。DeepSeek-R1-Distill 系列证明了这一方法的有效性：经过蒸馏的 7B 模型在数学推理上接近了未蒸馏的 70B 模型。

10. 代码示例：Best-of-N 采样

以下代码演示了推理时 Scaling 最简单的实现方式——Best-of-N 采样。通过生成 N 个候选答案并选择最佳答案，可以直观地看到推理时计算量与性能之间的关系。

import numpy as np

def best_of_n_sampling(model, question, n_samples=10, verifier=None):
    """
    Best-of-N 采样实现
    - model: 语言模型
    - question: 输入问题
    - n_samples: 采样数量（推理时计算量的代理指标）
    - verifier: 验证器函数，返回答案的得分
    """
    candidates = []
    for i in range(n_samples):
        # 生成一个候选答案（使用不同的随机种子）
        answer = model.generate(question, temperature=0.8, seed=i)
        # 用验证器评分
        if verifier:
            score = verifier(question, answer)
        else:
            score = answer.confidence  # 使用模型自身的置信度
        candidates.append((answer, score))
    
    # 选择得分最高的答案
    best_answer, best_score = max(candidates, key=lambda x: x[1])
    return best_answer, best_score

# 推理时 Scaling 曲线示例
def plot_inference_scaling(question, n_values=[1, 2, 5, 10, 20, 50, 100]):
    """
    绘制推理时 Scaling 曲线
    n_values: 不同的采样数量
    """
    results = []
    for n in n_values:
        # 对于每个 n，运行多次取平均

🔬 推理时 Scaling 与模型能力的耦合效应：一个有趣的研究问题是：推理时 Scaling 的效果是否依赖于模型的基础能力？换句话说，一个更强的基座模型是否能从推理时 Scaling 中获益更多？Snell et al. (2024) 的实验表明，答案是「是」——在相同的推理计算预算下，基座能力更强的模型能获得更大的性能提升。这意味着训练时 Scaling 和推理时 Scaling 不是简单的替代关系，而是互补关系：先训练一个足够强的基座模型，再通过推理时 Scaling 进一步挖掘其潜力，是目前最有效的策略。这一发现也解释了为什么 OpenAI 的策略是先投资训练 o1 的基座模型（GPT-4 级别），再在其上叠加推理时 Scaling。

11. 推理时 Scaling 的局限性

尽管推理时 Scaling 展现了巨大的潜力，但它并非万能药。在实际部署中，需要注意以下关键限制：

11.1 收益递减与天花板效应

推理时 Scaling 的幂律关系意味着性能提升遵循对数曲线——初期收益显著，但后期迅速递减。对于任何给定任务，都存在一个由任务本身难度决定的性能上限。当推理计算持续增加时，性能会渐近地接近这个上限，但永远无法超越它。例如，一个 7B 模型在 MATH-500 上的理论上限可能只有 75%（受限于模型容量），即使投入无限推理计算也无法达到 100%。这意味着推理时 Scaling 更适合「从 30% 提升到 60%」的场景，而非「从 80% 提升到 99%」的场景。

11.2 延迟与用户体验的矛盾

推理时 Scaling 直接增加了响应延迟。在需要实时交互的场景中（如对话助手、实时翻译），5-60 秒的额外延迟是不可接受的。研究表明，用户对 AI 响应延迟的容忍度遵循一个陡峭的衰减曲线：1-2 秒时用户满意度 >90%，5 秒时降至 ~70%，10 秒时降至 ~40%，超过 30 秒时几乎全部用户放弃等待。因此，推理时 Scaling 的适用场景天然排除了所有延迟敏感型应用。

11.3 成本不可预测性

与训练时计算不同（训练完成后成本固定），推理时计算的成本取决于输入的复杂度。同一个问题，模型可能用 1000 个 token 解决，也可能用 50000 个 token 解决，成本波动可达 50 倍。这种不可预测性给预算规划和定价带来了巨大挑战。OpenAI 通过引入 reasoning_effort 参数（low/medium/high）部分缓解了这一问题，但用户仍然无法精确控制单次推理的成本。

11.4 验证器依赖与错误传播

几乎所有推理时 Scaling 策略都依赖验证器来评估候选答案的质量。验证器的局限性直接决定了推理时 Scaling 的上限：(1) 如果验证器本身有系统性偏差（如偏好长答案），搜索过程会被引导到错误方向；(2) 在复杂任务中，验证器的准确率通常低于简单任务，形成「难任务需要更多搜索，但搜索质量更差」的恶性循环；(3) 验证器的训练成本可能很高，且需要针对特定任务定制。

11.5 并非所有计算都有价值

一个常见的误解是「更多推理计算 = 更好结果」。实际上，如果推理策略不当，额外的计算可能被浪费在低质量路径上。例如，Best-of-N 在 N 很大时，大量候选可能共享同一错误假设，导致额外的搜索不产生新信息。MCTS 如果评估函数噪声大，可能在低质量区域反复探索。因此，推理时 Scaling 的效率不仅取决于计算量，更取决于推理策略的质量——这也是为什么 o1 通过 RL 训练出的推理策略比简单的 Best-of-N 更高效。

12. 小结

✅ 本章要点：

  1. 第三条缩放轴：除了训练时的参数量 N 和数据量 D，推理时的计算量也是独立的缩放维度
  2. System 1 vs System 2：推理时 Scaling 让模型从「快思考」升级到「慢思考」，深度推理难题
  3. 幂律关系：推理计算与性能之间存在幂律关系，数学任务 γ≈0.1-0.2
  4. 训练 vs 推理权衡：困难任务上，小模型+充分推理 可能优于 大模型+少量推理
  5. 成本结构变革：从「按 token 计费」转向「按推理复杂度计费」的新商业模式
  6. 局限性：收益递减、延迟敏感、成本不可预测、验证器依赖——推理时 Scaling 并非万能药
