🏎️ 项目 A：LLM 推理竞速可视化

快速开始

核心洞察：推理竞速可视化项目的价值不在于"展示界面"，而在于将推理系统的数学本质——Roofline模型中的算术强度与带宽瓶颈关系——转化为可交互的视觉隐喻。每个技术节点（FlashAttention、PagedAttention等）背后对应一个可量化的加速比数值，多技术叠加时的综合加速比遵循乘积关系而非简单相加，这直接反映了Amdahl定律在GPU推理系统中的具体体现。

原理展开：为什么不能简单相加加速比？因为两个优化若作用于同一阶段（如都优化Decode阶段），效果会互相重叠。设技术 i 对阶段 j 的加速比为 S_i，该阶段占总时间的比例为 f_j，则综合加速比由Amdahl定律推广形式给出：

Speedup_total = 1 / [ Σ_j ( f_j / Π_i S_i,j ) ]

其中 f_j 为第 j 阶段的时间占比（Σf_j = 1），S_i,j 为技术 i 对阶段 j 的加速比。
数值例子：设Prefill占30%（f₁=0.3），Decode占70%（f₂=0.7）。FlashAttention对Prefill加速3倍（S₁,₁=3），对Decode无加速（S₁,₂=1）。PagedAttention对Decode加速2倍（S₂,₂=2）。则 Speedup = 1/(0.3/3 + 0.7/2) = 1/(0.1 + 0.35) ≈ 2.22×，而非简单相加的 3+2=5×。

实现细节：项目为纯前端实现，无需安装任何依赖。核心渲染使用Canvas API + requestAnimationFrame实现60fps动画循环，技术节点的加速比数据硬编码在 techData.js 中。

🌳 技术树模式

核心洞察：技术树不是简单的知识图谱，而是推理优化领域的依赖关系有向无环图（DAG）的可视化。每个技术节点都有前置依赖——要使用INT4量化（叶节点），需要先理解Tensor Core的4-bit支持（根节点）和量化校准的数值稳定性问题（中间节点）。这种层次结构揭示了优化技术的递进路径：从硬件基础→算法设计→系统实现→应用优化，每层依赖前一层的输出。

原理展开：技术树的5层结构对应推理系统的抽象层次。设系统总延迟为 T_total，各层优化可减少的延迟比例为 r_i（i=1..5），则优化后的延迟为：

T_optimized = T_base × ∏_{i=1}^{5} (1 - r_i)

其中 r_i 是第 i 层优化减少的时间比例。
数值例子：设 T_base = 100ms，各层优化率 r = [0.1, 0.2, 0.15, 0.1, 0.05]，则 T_optimized = 100 × 0.9 × 0.8 × 0.85 × 0.9 × 0.95 ≈ 52.3ms，总加速约1.91×。注意各层优化率不独立——高层优化（如量化）依赖低层（如Tensor Core）的可用性。

实现细节：技术树使用力导向图（Force-Directed Graph）布局算法，节点间通过弹簧模型计算位置。点击节点时，JavaScript计算该节点到根节点的所有路径，高亮显示依赖链。

// 技术树节点数据结构
const treeNodes = [
  { id: "gpu_arch", layer: 0, name: "GPU架构", children: ["tensor_core", "hbm"] },
  { id: "tensor_core", layer: 1, name: "Tensor Core", children: ["fp8", "int4"] },
  { id: "fp8", layer: 2, name: "FP8量化", children: ["gptq", "awq"] },
  { id: "int4", layer: 2, name: "INT4量化", children: ["gptq", "awq"] },
  { id: "gptq", layer: 3, name: "GPTQ", children: [] },  // 叶节点
  { id: "awq", layer: 3, name: "AWQ", children: [] }
];
// 点击节点时递归查找所有祖先节点
function findAncestors(nodeId, visited = new Set()) {
  const node = treeNodes.find(n => n.id === nodeId);
  if (!node || visited.has(nodeId)) return visited;
  visited.add(nodeId);
  // 向上查找父节点（反向遍历）
  treeNodes.forEach(n => {
    if (n.children.includes(nodeId)) findAncestors(n.id, visited);
  });
  return visited;
}

量化分析：技术树包含17个节点，分布在5层中。实测数据：从根节点到最深叶节点的路径长度为4跳（GPU→Tensor Core→FP8→GPTQ/AWQ）。每个节点的"加速比"数据来源于论文报告：FlashAttention 2在A100上对Attention计算加速2-3×，PagedAttention将显存利用率从60%提升到90%+（有效batch_size提升1.5×），Continuous Batching使吞吐提升2-3×。

🏁 赛道竞速模式

核心洞察：赛道竞速模式的核心价值不是"看谁快"，而是揭示不同优化策略在不同场景下的相对优势。同一框架在小batch（bs=1）时最快，在大batch（bs=64）时可能最慢——这是因为各框架的内存管理策略（连续分配 vs 分页分配）在不同batch_size下的效率差异巨大。竞速动画的速度比例直接映射到A100 GPU上的实测吞吐数据。

原理展开：推理框架的性能差异本质上来自有效batch_size的差异。设GPU总显存为 M_total，单个请求的KV Cache占用为 m_kv，框架的内存碎片率为 α，则最大并发请求数为：

N_max = ⌊ M_total × (1 - α) / m_kv ⌋

其中 M_total 为GPU显存总量，α 为内存碎片率（0-1），m_kv 为单个请求的KV Cache大小。
数值例子：A100 80GB，7B模型，序列长度2048。m_kv ≈ 2 × n_layers × d_model × seq_len × 2bytes = 2 × 32 × 4096 × 2048 × 2 ≈ 1GB。传统框架 α=0.4，N_max = ⌊80×0.6/1⌋ = 48。PagedAttention框架 α=0.05，N_max = ⌊80×0.95/1⌋ = 76。有效batch_size提升 76/48 ≈ 1.58×。

实现细节：竞速动画使用Canvas的requestAnimationFrame循环，每条赛道的"赛车"位置由该技术的加速比决定。位置更新公式：position += baseSpeed × techSpeedup × deltaTime。

🔬 流水线透视模式

核心洞察：流水线透视模式解决的核心问题是定位瓶颈——在推理全流程中，哪个阶段占用了最多时间？这直接决定了优化方向：如果Attention占55%，优化Attention的收益远大于优化Tokenizer（仅占2%）。该模式将推理过程分解为Tokenizer→Embedding→Attention→FFN→Sampler→Detokenizer六个阶段，每个阶段的耗时占比随模型规模和序列长度动态变化。

原理展开：推理延迟由Prefill和Decode两个阶段构成，它们的计算特性截然不同。Prefill阶段处理全部输入token（并行，计算密集），Decode阶段逐token生成（串行，密集）。设输入长度为 L_in，输出长度为 L_out，则总延迟为：

T_total = T_prefill(L_in) + L_out × T_decode

其中 T_prefill(L_in) 是Prefill阶段延迟（与 L_in² 成正比，因为Attention是二次的），T_decode 是每token的Decode延迟（常数）。
数值例子：LLaMA-7B，L_in=512，L_out=128。T_prefill ≈ 30ms（Attention占20ms），T_decode ≈ 10ms/token。T_total = 30 + 128×10 = 1310ms。若序列长度增加到2048，T_prefill ≈ 30×(2048/512)² = 480ms，T_total = 480 + 1280 = 1760ms。Prefill占比从2.3%飙升到27.3%。

实现细节：流水线透视使用堆叠条形图展示各阶段耗时。调节Seq Length滑块时，JavaScript根据 T_prefill ∝ L² 和 T_decode ∝ L 的关系实时计算各阶段耗时，更新图表。

// 流水线各阶段耗时计算（简化模型）
function calcPipelineTime(modelSize, seqLen, outputLen) {
  const n_layers = modelSize === '7B' ? 32 : modelSize === '13B' ? 40 : 80;
  const d_model = modelSize === '7B' ? 4096 : modelSize === '13B' ? 5120 : 8192;
  // Attention: O(L^2 * d) — 计算量与序列长度平方成正比
  const attentionTime = n_layers * (seqLen ** 2) * d_model * 1e-12; // 简化
  // FFN: O(L * d^2) — 计算量与序列长度线性
  const ffnTime = n_layers * seqLen * (d_model ** 2) * 1e-12;
  // KV Cache大小: 2 * n_layers * d_model * seqLen * 2bytes (FP16)
  const kvCacheMB = 2 * n_layers * d_model * seqLen * 2 / 1024 / 1024;
  return { attentionTime, ffnTime, kvCacheMB };
}

📊 性能仪表盘模式

核心洞察：性能仪表盘的核心价值是将推理系统的黑盒变为白盒。生产环境中，推理服务的尾部延迟（P99）往往比平均延迟（P50）更重要——用户感受到的是最慢的那1%请求。仪表盘同时展示P50/P95/P99延迟、吞吐趋势、GPU利用率和队列状态，帮助运维人员快速发现"延迟突增"、"显存碎片化"、"队列堆积"等典型问题。

原理展开：推理系统的吞吐与延迟之间存在固有权衡。设系统服务率为 μ（请求/秒），到达率为 λ，根据排队论（M/M/1模型），平均排队延迟为：

W_q = ρ / (μ - λ) , 其中 ρ = λ/μ

其中 ρ 为系统利用率，μ 为服务率，λ 为到达率。
数值例子：设 μ = 100 req/s，λ = 80 req/s，则 ρ = 0.8，W_q = 0.8/(100-80) = 0.04s = 40ms。若 λ 增加到95 req/s，ρ = 0.95，W_q = 0.95/5 = 0.19s = 190ms——利用率从80%提升到95%，排队延迟却增长了4.75倍。这就是为什么生产环境通常将利用率控制在70-80%。

实现细节：仪表盘使用SVG绘制实时图表，数据通过setInterval模拟更新。切换模型大小时，JavaScript根据模型参数数量重新计算理论显存和延迟。

// 仪表盘数据计算（简化模型）
function calcMetrics(modelSize, batchSize, seqLen) {
  const params = { '7B': 7e9, '13B': 13e9, '70B': 70e9 }[modelSize];
  // 显存 = 参数×2bytes(FP16) + KV Cache + 激活值
  const modelMemGB = params * 2 / 1e9;  // FP16
  const kvCacheGB = 2 * 32 * 4096 * seqLen * 2 * batchSize / 1e9;
  const totalMemGB = modelMemGB + kvCacheGB + 2; // +2GB激活值
  // 延迟模型: T = T_base × (params/7e9) × f(batchSize)
  const tpot = 10 * (params / 7e9) * (1 + batchSize * 0.02); // ms/token
  const throughput = batchSize * 1000 / tpot; // tokens/s
  return { modelMemGB, kvCacheGB, totalMemGB, tpot, throughput };
}

⚙️ 控制面板

核心洞察：控制面板是连接"理论"与"实验"的桥梁。通过调节Batch Size、Seq Length、Chunk Size等参数，你可以直观观察到推理系统的非线性响应——batch_size从16增加到32时吞吐可能提升80%，但从32到64时仅提升30%（因为内存带宽开始饱和）。这种非线性正是Roofline模型的直接体现：低batch时是计算瓶颈，高batch时转为带宽瓶颈。

原理展开：Batch Size对吞吐的影响存在"收益递减"点。设单请求计算时间为 T_comp，单请求访存时间为 T_mem，batch_size为 B，则：

T_batch(B) = T_comp × B + T_mem × √B (计算线性增长，访存亚线性)
Throughput(B) = B / T_batch(B) = 1 / (T_comp + T_mem/√B)

当 B→∞ 时，Throughput → 1/T_comp（理论上限）。
数值例子：设 T_comp = 0.5ms，T_mem = 5ms。B=1时，吞吐 = 1/(0.5+5) = 0.18 req/ms。B=16时，吞吐 = 1/(0.5+1.25) = 0.57 req/ms（3.2×）。B=64时，吞吐 = 1/(0.5+0.625) = 0.89 req/ms（5.0×）。B=256时，吞吐 = 1/(0.5+0.3125) = 1.23 req/ms（6.8×）。从64到256仅提升38%，收益递减明显。

原理展开：论文筛选基于关键词匹配 + 分类器打分。设论文 p 与推理加速的相关性得分为：

核心洞察：知识图谱将论文中分散的技术概念组织为结构化网络，揭示技术间的依赖、改进和竞争关系。例如，查询"FlashAttention被哪些论文改进了？"可以返回FlashAttention-2、FlashDecoding、FlashAttention-3等改进路径，帮助研究人员快速了解技术演进脉络。

原理展开：知识图谱使用图结构 G = (V, E)，其中节点 V 表示技术概念，边 E 表示关系（改进、依赖、竞争）。设节点 i 的重要性可以用PageRank衡量：

PR(i) = (1-d)/N + d × Σ_{j→i} PR(j)/L(j)

其中 d 为阻尼系数（通常0.85），N 为节点总数，L(j) 为节点 j 的出边数。
数值例子：设图谱有100个节点，"Transformer"节点有20条入边（被20个技术引用），PageRank值约为0.05（远高于平均值0.01），表明它是核心节点。

🔗 两个项目的关系

核心洞察：两个项目构成闭环系统：论文雷达（项目B）追踪最新技术进展，为竞速可视化（项目A）提供新的技术节点和加速比数据；竞速可视化的测试结果又可以验证论文中的性能声称是否准确。这种"理论→实践→反馈"的循环是技术演进的核心动力。

原理展开：两个项目的数据流可以用反馈回路建模。设论文项目提供的技术加速比为 S_claim（论文声称），竞速项目测得的实际加速比为 S_actual，则偏差为：

Δ = |S_claim - S_actual| / S_claim × 100%

当 Δ > 30% 时，说明论文的测试条件与实际部署条件存在显著差异（如论文使用短序列但实际使用长序列）。
数值例子：论文声称FlashAttention加速3×，实测在序列长度512时仅加速1.5×。Δ = |3-1.5|/3 × 100% = 50%。原因：论文测试序列长度为4096，而512时计算量太小，kernel launch开销占主导。

推理竞速可视化的工作机制与数据驱动设计

竞速可视化的底层原理是将推理系统的数学本质——Roofline模型中的算术强度与带宽关系——转化为直观的动画。每个技术节点（如FlashAttention、PagedAttention）对应一个加速比数值，多技术叠加时的综合加速比 = ∏(1 + speedup_i × coverage_i)，其中coverage_i是该技术的覆盖范围比例。为什么不能简单相加加速比？因为推导表明：两个优化若优化同一阶段（如都优化Decode），效果会互相重叠，实际收益小于各自独立收益之和。

Speedup_total = 1 / [ Σ_j ( f_j / Π_i (1 + S_i,j × C_i,j - C_i,j) ) ]

其中 f_j 为阶段 j 的时间占比，S_i,j 为技术 i 对阶段 j 的加速比，C_i,j 为覆盖率。
当两个技术优化同一阶段时，它们的有效加速比不是 S₁×S₂，而是 S₁×C₁ + S₂×C₂ - C₁×C₂（考虑重叠），因此总加速比小于简单乘积。

竞速排行榜的技术价值

推理竞速排行榜不仅展示了各框架的性能差异，更揭示了优化技术的底层原理。为什么vLLM在大多数场景下领先？推导其核心优势在于PagedAttention的内存管理工作机制——通过将KV Cache分割为固定大小的页面，消除了内存碎片化，使得batch_size可以显著增大。从数学本质看，吞吐量 = batch_size / latency，当batch_size增大而latency不显著增加时，吞吐量线性提升。

Throughput = N_active × 1000 / T_TPOT (tokens/s)

其中 N_active 为活跃请求数（受显存限制），T_TPOT 为每token延迟。
数值例子：传统框架 N_active=8, T_TPOT=10ms → 吞吐=800 tokens/s。vLLM N_active=64, T_TPOT=12ms → 吞吐=5333 tokens/s。提升约6.7×，其中batch_size贡献8×，但TPOT增加抵消了部分收益。

如何解读性能数据

解读竞速数据时需要注意底层的度量差异。TTFT（首token延迟）和TPOT（每token延迟）反映了不同的工作机制：TTFT主要受Prefill阶段影响，与计算能力正相关；TPOT受Decode阶段影响，与内存带宽正相关。为什么同一个框架在不同指标上排名可能不同？因为Prefill是计算密集型而Decode是内存密集型——这一原理决定了没有"万能最优"的框架，只有最适合特定场景的框架。

推理竞速的技术原理： 从底层硬件角度看，推理性能的数学本质可以用屋顶模型推导： 有效吞吐 = min(峰值算力, 峰值带宽 × 算术强度)。 为什么不同框架在同一硬件上性能差异巨大？ 因为框架的内存管理工作机制（如PagedAttention vs 传统连续内存） 直接影响有效batch_size，进而影响算术强度。 这一原理解释了为什么vLLM在大batch场景下 通常优于其他框架的底层原因。

  2. 核心原理: 技术树模式将推理优化技术组织成树状层次结构，从底层硬件优化（量化、算子融合）到中层调度优化（批处理、内存管理）到高层应用优化（提示缓存、推测解码），帮助用户系统性地理解优化技术的依赖关系和递进路径。核心思想：优化不是孤立的，每个技术都有前置依赖。例如，要使用INT8量化（叶节点），需要先理解Tensor Core架构（根节点）和量化校准方法（中间节点）。

    实际案例: 推理优化技术树路径：GPU架构→Tensor Core→FP8量化→INT4量化→GPTQ/AWQ。沿着这条路径逐步优化，每步都有明确的性能收益。
