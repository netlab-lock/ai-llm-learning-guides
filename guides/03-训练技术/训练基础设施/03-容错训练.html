🛡️ 容错训练

1. 大规模训练的故障率模型

核心洞察：在万卡集群上训练 LLM，故障是常态而非异常。Meta 训练 Llama 3 时使用了 16,000 个 GPU，训练期间经历了数百次硬件故障。理解故障率的数学模型是设计容错机制的前提——只有量化了故障概率，才能计算最优检查点频率、评估不同恢复策略的效率。没有这个数学基础，容错设计就是在"凭感觉"。

故障率与集群规模的关系 (假设单 GPU MTBF = 10,000 小时): 集群规模 单GPU MTBF 集群MTBF 每年故障次数 ────────────────────────────────────────────────────────── 100 GPU 10,000 h ~100 h ~87 1,000 GPU 10,000 h ~10 h ~876 10,000 GPU 10,000 h ~1 h ~8,760 16,000 GPU 10,000 h ~37 min ~14,016 关键洞察: MTBF_cluster = MTBF_single / N，N个组件串联系统 结论: 万卡集群每37分钟就可能发生一次故障，容错是必需品

1.1 指数故障模型与可靠性推导

GPU 故障通常建模为泊松过程：假设单个 GPU 的故障率为 λ (单位时间内的期望故障数)，则 N 个 GPU 组成集群的等效故障率为 Λ = Nλ。

R(t) = e^(-Λt) = e^(-Nλt) 其中: R(t) = 系统在时间 t 内无故障的概率 N = GPU 数量 λ = 单 GPU 故障率 (如 1/10000 h⁻¹) Λ = 集群总故障率

由此推导出集群的平均故障间隔时间 MTBF_cluster = 1/Λ = 1/(Nλ)。当 N=16000，λ=10⁻⁴/h 时，MTBF ≈ 62.5 小时。但实际中，网络故障、存储故障、软件崩溃使有效 λ 远高于纯硬件故障率，实测 MTBF 通常只有 30-120 分钟。

1.2 检查点频率的最优化——Young-Daly 公式

Young-Daly 最优检查点间隔: T_opt = √(2 × δ × MTBF) 其中: T_opt = 最优检查点间隔 (小时) δ = 保存一个检查点的时间 (checkpointing overhead) MTBF = 集群平均故障间隔时间 有效训练效率: η = T_opt / (T_opt + δ + MTBF/2 × δ/T_opt) → 简化近似: η ≈ 1 - 2√(δ / (2×MTBF)) (当 δ << MTBF)
实际计算示例：假设 16K GPU 集群 MTBF = 1 小时，δ = 3 分钟： T_opt = √(2 × 180s × 3600s) = √(1,296,000) ≈ 1138 秒 ≈ 19 分钟 训练效率: 每 19 分钟保存一次，保存耗时 3 分钟 故障后平均回退 MTBF/2 = 30 分钟训练量 效率 η = T_opt / (T_opt + δ + MTBF/2) = 1138 / (1138 + 180 + 1800) = 1138/3118 ≈ 36.5% 现代系统使用异步增量检查点（δ ≈ 30s）： T_opt = √(2 × 30 × 3600) ≈ 465 秒 ≈ 7.75 分钟 效率 η ≈ 1 - 2√(30/(2×3600)) ≈ 93.5%
💡 实用技巧：故障率与 GPU 数量近似线性关系，而非指数关系。这意味着即使集群规模翻倍，只要恢复机制完善，训练效率几乎不受影响。关键是把恢复时间做到足够短。恢复时间从 10 分钟降到 1 分钟，16K GPU 集群的训练效率从 ~80% 提升到 ~95%。
⚠️ 注意事项：万卡集群的实际故障分布并不均匀——网络故障和 GPU 故障通常集中在特定机架或交换机下。Meta 的经验是：同一机架在 24 小时内出现多次故障的概率是随机预期的 3-5 倍，说明存在"故障热点"（如劣质电源批次、散热不良区域）。建议在故障恢复时主动避开故障区域的节点。

2. 故障检测机制

核心洞察：故障检测是容错训练的第一道防线。检测延迟直接决定了故障造成的计算浪费：检测耗时 10 分钟意味着 10 分钟的训练进度全部丢失。现代训练系统采用分层检测策略——从毫秒级的心跳到分钟级的应用健康检查，不同层级覆盖不同的故障模式。

2.1 多层级检测架构

故障检测层级: 层级 检测方式 延迟 覆盖故障 ──────────────────────────────────────────────────────── L0 硬件 ECC/热节流 毫秒 显存位翻转、过热 L1 驱动 XID 事件 秒级 驱动崩溃、GPU挂起 L2 通信 NCCL Watchdog 秒~分钟 网络抖动、死锁 L3 进程 Heartbeat 秒~分钟 进程OOM、死循环 L4 应用 Loss/Metric监控 分钟级 梯度爆炸、数据损坏 L5 人工 运维巡检 小时级 性能劣化趋势

2.2 心跳协议与故障判定

心跳检测的可靠性分析: 设单跳心跳丢失概率为 p (网络丢包率), N_miss = 允许连续丢失的心跳数 P(误判) = p^(N_miss+1) (正常节点被误判为故障) P(漏判) ≈ 0 (故障节点最终会被检测到) 检测延迟: T_detect = T_heartbeat × (N_miss + 1) 典型配置: T_heartbeat = 10s, N_miss = 2 T_detect = 30s, P(误判) = (0.01)³ = 10⁻⁶

2.3 应用层健康检查——Loss 异常检测

EWMA Loss 异常检测: EWMA_t = α × loss_t + (1-α) × EWMA_{t-1} 异常条件 (满足任一): 1. loss_t > EWMA_t + k × σ_t (Loss突增) 2. |loss_t - loss_{t-1}| > threshold (Loss跳变) 3. loss_t > 3 × loss_0 (Loss未下降) 4. isnan(loss_t) or isinf(loss_t) (数值溢出) 典型参数: α=0.01 (约100步的平滑窗口), k=3 (3σ阈值)
⚠️ 常见陷阱：Loss 检测的滞后性是最大的挑战。当 Loss 已经明显异常时，通常意味着模型已经被"毒化"了数十到数百步。如果检查点间隔是 15 分钟，你可能需要回退数千步才能找到"干净"的恢复点。这也是为什么有些团队实现"影子检查点"（shadow checkpoint）——每 1 分钟在内存中保存一个轻量快照，只在检测到异常时才持久化。

3. Checkpoint 与恢复策略

核心洞察：Checkpoint 是容错训练的核心机制——它定期保存训练状态，使得故障后可以从最近的保存点恢复而非从头开始。Checkpoint 设计的核心权衡是：保存太频繁则浪费训练时间，保存太少则故障后损失大量计算。Young-Daly 公式给出了理论最优值，但实际中还需要考虑存储成本和恢复速度。

3.1 Checkpoint 大小分析

Checkpoint 大小计算 (70B 模型, AdamW, BF16): 模型参数: 70B × 2 bytes (BF16) = 140 GB 优化器状态: 70B × 4 bytes (FP32 master) = 280 GB + 70B × 4 bytes (m) = 280 GB + 70B × 4 bytes (v) = 280 GB 梯度: 70B × 2 bytes (BF16) = 140 GB ──────────────────────────────────────────── 总计: ~1,120 GB = 1.12 TB (单个完整checkpoint) 使用 ZeRO-3 分片 (64个GPU): 每个GPU存储: 1.12 TB / 64 = 17.5 GB

3.2 同步 vs 异步检查点

同步检查点: GPU ──[训练N步]──[暂停]──[保存M秒]──[恢复]──[训练N步]── 训练效率 = N/(N+M) 异步检查点 (双缓冲): GPU ──[训练]──[训练]──[训练]──[训练]──[训练]── ↓ ↓ Copy [复制到CPU] [复制到CPU] ↓ ↓ Flush [异步写存储] [异步写存储] 训练效率 ≈ 100% (复制开销 ~2%) 
import torch.distributed.checkpoint as dcp

# 定义 checkpoint 内容
state_dict = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "step": global_step,
}

# 异步保存 (非阻塞)

# 检查点恢复
dcp.load(state_dict, checkpoint_id="/checkpoint/path/step_10000")

3.3 增量检查点与压缩

增量检查点大小: ΔW = W_t - W_{t-1} 稀疏化: 只保存 |ΔW| > ε 的元素 量化: 将 ΔW 量化为 INT8 (降低4x) 典型压缩率: 全量: 1.12 TB 增量: ~50-100 GB (稀疏度 5-10%) 压缩后: ~15-30 GB (INT8 量化) 保存时间 (10GB/s 存储带宽): 全量: ~112 秒 增量: ~15-30 秒 → 符合 "δ < 60s" 的最优区间
💡 Meta 的 Llama 3 实际参数：使用增量检查点，每 15 分钟保存一次到 Distributed Checkpoint (DCP)，检查点间隔内如果检测到 Loss 异常，从内存中的影子检查点恢复（延迟 <5 秒）。全集群 16K GPU 的 checkpoint 保存耗时约 45-90 秒（增量模式），训练效率维持在 92-95%。

4. 弹性训练（Elastic Training）

核心洞察：传统数据并行训练要求所有 worker 数量固定——任何一个 worker 故障都会导致整个训练作业失败。弹性训练打破这个限制，允许在运行时动态增减 worker，使训练作业能够容忍节点故障而不需要完全重启。这是万卡集群的关键能力。

4.1 弹性训练的数学基础

弹性训练的动态调整策略: 策略A - 保持全局batch size不变: B' = (N × B) / N' (增大单worker batch) 优点: 训练动力学不变 缺点: 显存可能不够 (B' > max_batch_per_gpu) 策略B - 保持单worker batch size不变: B' = B 全局batch size = N' × B < N × B 学习率需按 sqrt scaling: η' = η × √(N'/N) 优点: 不需要重新分配显存 缺点: 小batch可能影响训练稳定性 PyTorch 默认使用策略B + sqrt LR scaling 推荐配置: min_workers = N/2 (保证至少一半worker存活)

4.2 TorchElastic 实现详解

# torchrun 启动弹性训练 (自动处理worker增减)
torchrun \
    --nnodes=16:32 \        # 允许16-32个节点弹性伸缩
    --nproc_per_node=8 \     # 每节点8个GPU
    --rdzv_id=100 \          # rendezvous ID
    --rdzv_backend=etcd \    # 协调服务
    --rdzv_endpoint=etcd:2379 \
    --max_restarts=3 \       # 最大重启次数
    train.py
弹性训练恢复流程 (一个worker故障时): 1. etcd 检测到 worker-7 心跳超时 2. 向存活的 worker {0..6,8..15} 发送 MEMBERSHIP_CHANGE 事件 3. 所有 worker 暂停训练，进入 BARRIER 4. 重建通信组: ProcessGroup 从 16 → 15 成员 5. 重新分配数据: DataLoader 的 DistributedSampler 重新分片 6. 调整超参数: lr *= sqrt(16/15) ≈ 1.033 (轻微提升) 7. 从最近 checkpoint 恢复 8. 恢复训练 总耗时: 通常 30-120 秒 (取决于 checkpoint 大小和数量)

4.3 弹性训练 vs 容错训练的权衡

维度Checkpoint+Restart (容错)Elastic Training (弹性)
恢复时间5-30 分钟（需重启所有进程）30-120 秒（只重建通信组）
数据丢失回到上一个 checkpoint只丢失当前 step 的梯度
实现复杂度低（框架无关）高（需要动态 ProcessGroup）
最佳场景故障间隔 > 30 分钟故障间隔 < 30 分钟
⚠️ 弹性训练的陷阱：动态增减 worker 会导致数据分配不均衡。假设原始 16 个 worker 各处理 1000 个样本，worker-7 故障后 15 个 worker 各需处理 1067 个样本。如果某些 worker 分配到了特别"难"的样本（长序列、高频 token），会导致这些 worker 成为 Straggler，反而降低整体效率。

5. Straggler 检测与处理

核心洞察：Straggler（掉队者）是指比其他 worker 慢的节点——它不是完全故障，而是由于硬件差异、网络拥塞、I/O 竞争等原因导致单步耗时显著增加。在数据并行训练中，AllReduce 是同步操作，所有 worker 必须等待最慢的那个完成。一个 Straggler 可以将整个集群的效率拉低 20-40%。

5.1 Straggler 的形式化定义与检测

Straggler 判定条件: 设 μ(t) = median(T_1(t), ..., T_N(t)) ← 中位数 (对异常值鲁棒) 设 σ(t) = MAD(T_1(t), ..., T_N(t)) ← 中位数绝对偏差 worker i 是 Straggler 当且仅当: T_i(t) > μ(t) + k × σ(t) / 0.6745 典型阈值: k = 2 (约 95% 置信度) 示例: μ = 2.0s, σ = 0.15s, k = 2 阈值 = 2.0 + 2 × 0.15 / 0.6745 ≈ 2.45s 若某 worker 耗时 2.6s → 标记为 Straggler 
import numpy as np
from collections import deque

class StragglerDetector:
    def __init__(self, window_size=100, threshold_k=2.0):
        self.step_times = {i: deque(maxlen=window_size) for i in range(N)}
        self.k = threshold_k
    
    def detect(self):
        latest = [times[-1] for times in self.step_times.values() if len(times) > 0]
        mu = np.median(latest)
        mad = np.median(np.abs(latest - mu))
        sigma = mad / 0.6745  # 转换为标准差尺度
        threshold = mu + self.k * sigma
        
        stragglers = []
        for rank, times in self.step_times.items():
            if len(times) > 0 and times[-1] > threshold:
                stragglers.append((rank, times[-1], threshold))
        return stragglers

5.3 处理策略：预防 vs 补救

Straggler 工程的经验数据： 在 8K GPU 集群上，不做任何 Straggler 处理时，平均每步的"等待时间"（AllReduce 前等待最慢 worker 的时间）占总 step 时间的 15-25%。使用节点预筛选后降到 5-10%。加上动态 batching 和通信-计算重叠后降到 2-5%。最终 Straggler 处理的开销（burn-in 测试 + 检测器运行时开销）不到总训练时间的 1%。投入产出比极高。

6. 完整容错训练系统设计

核心洞察：一个生产级容错训练系统需要将故障检测、决策、恢复三个步骤解耦为独立微服务。Google 的 TPU Pod 容错经验表明，这是最关键的架构决策——任何一个服务故障不会阻塞其他服务。

7. 失败模式与调试方法论

核心洞察：容错系统的最终目标不是"避免故障"，而是"快速检测和恢复"。理解常见失败模式的特征、根因和解决方案，是设计高效容错系统的前提。本节系统总结 LLM 训练中的常见失败模式及其调试方法论。

7.4 训练效率的长期退化监控

除了突发故障，训练系统的"渐进式退化"也需要监控。这包括：

  • 存储 I/O 退化：共享文件系统的吞吐量随时间下降（其他任务竞争带宽）。监控数据加载时间，如果 7 天移动平均增长 > 10%，应考虑将数据迁移到本地 NVMe。
  • 网络带宽退化：IB 网络在高负载下可能出现 PFC（Priority Flow Control）反压，导致 AllReduce 延迟增加。监控 NCCL 通信时间，超过 baseline 20% 时需联系网络团队。
  • GPU 计算退化：GPU 因散热问题降频（thermal throttling），实际频率从标称值（A100: 1.41GHz）下降到 1.0-1.2GHz。监控 SM clock 和温度。
深入理解：训练效率的量化 ROI 模型
容错系统的 ROI 可以精确计算：

ROI = (避免的故障损失 + 效率提升节省) / 容错系统成本

以一个 $5M 训练项目为例：
避免的故障损失：MTBF 从 2h 提升到 4h（更好的预防），每次故障节省 1h 检测时间 × $15K/h × 2次/周 × 4周 = $120K
效率提升：Training Efficiency 从 85% 提升到 93%（更好的恢复），节省 8% 训练时间 = $400K
容错系统成本：开发 + 部署 + 运维 ≈ $50K
ROI = ($120K + $400K) / $50K = 10.4x
即每投入 $1 在容错系统上，获得 $10.4 的回报。
