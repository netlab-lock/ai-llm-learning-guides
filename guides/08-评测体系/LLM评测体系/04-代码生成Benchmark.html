04 代码生成 Benchmark

为什么选择这四个Benchmark？

核心问题：代码生成领域有数十个Benchmark，为什么我们重点讨论这四个？答案在于它们构成了一个互补的评测矩阵——覆盖不同难度级别、不同任务场景、不同评测维度。缺少任何一个都会留下盲区。

评测矩阵：四个Benchmark的互补性 难度 低 ──────────────────────▶ 高 任务级 ▲ MBPP HumanEval LiveCodeBench 别 │ (入门级) (函数级) (竞赛级) │ │ │ │ │ │ │ │ │ ▼ ▼ ▼ │ SWE-bench (项目级) │ ── 横跨所有难度 ── │ 场景 个人练习 算法作业 竞赛编程 工业开发 防污染 ★★★ ★ ★★★ ★★ 能力 (已污染) (严重污染) (持续更新) (真实数据) ★ = 污染程度（越多越干净）

选择逻辑：四个维度覆盖评测全景

Benchmark评测粒度核心能力选择理由局限性
HumanEval函数级（~10行）从docstring生成函数标准化程度最高，164题覆盖基础算法，是"及格线"测试数据污染严重，区分度接近饱和
SWE-bench项目级（跨文件）理解Issue + 定位代码 + 编写修复唯一评测"真实软件开发"能力的Benchmark，最接近生产环境评测成本高（~250小时），通过≠正确
LiveCodeBench函数级（竞赛题）解决未见过的算法问题持续更新防污染，解决"背答案"问题，评测真实泛化能力题目难度波动大，不同时间结果不可比
MBPP程序级（~15行）从自然语言描述生成完整程序考察"从需求到代码"的完整能力，包含输入/输出处理题目偏简单，train/test集易混淆
🔬 深入理解：评测的"三角验证"
选择多个Benchmark的根本原因是单一指标无法刻画代码能力的全貌。一个模型可能在HumanEval上pass@1=95%（函数生成很强），但在SWE-bench上通过率仅10%（项目级理解很弱）。这种"能力分裂"现象说明：函数级代码生成和项目级代码修复是两种不同的能力，需要分别评测。四个Benchmark的组合提供了"三角验证"——从不同角度测量同一构念（code generation ability），确保评测结论的稳健性。
💡 实践建议：根据你的评测目的选择Benchmark组合：
  • 快速筛选模型：只用HumanEval（4.5小时完成评测）
  • 评估真实能力：HumanEval + LiveCodeBench（防污染验证）
  • 评估工程能力：SWE-bench Verified（最终验证）
  • 全面评测：四个Benchmark全部使用（论文级评测）

代码评测方法论详解

核心洞察：代码评测的结果高度依赖评测方法论的细节——采样策略、代码提取方式、执行环境配置都会显著影响最终分数。理解这些方法论细节是正确解读 Benchmark 结果的前提。在深入具体Benchmark之前，先掌握通用方法论，后续内容将反复引用这些概念。

采样策略

pass@k 的采样配置直接影响结果。标准配置如下：

标准采样配置：
n = 200（总采样数）
temperature = 0.8（平衡多样性和质量）
top_p = 0.95（nucleus sampling）
max_tokens = 512-1024（根据题目难度调整）
stop_tokens = ["\ndef", "\nclass", "\n#", "\n@"]（防止生成多个函数）

温度对结果的影响（以 HumanEval pass@1 为例）：
temperature=0.0: pass@1 最高（确定性输出），但 pass@k 不增长
temperature=0.2: pass@1 略降，pass@10 开始增长
temperature=0.8: 标准配置，pass@1 与多样性平衡
temperature=1.0: pass@1 最低，但 pass@100 最高

代码提取（Code Extraction）

模型输出是原始文本，需要从中提取可执行代码。这是评测流程中最容易出错的环节：

# 代码提取流程
def extract_code(raw_output, prompt):
    # 1. 移除 prompt 部分（模型有时会重复 prompt）
    code = raw_output[len(prompt):] if raw_output.startswith(prompt) else raw_output
    
    # 2. 按 stop tokens 截断（只取第一个函数/程序）
    for stop in ["\ndef ", "\nclass ", "\n#", "\nif __name__"]:
        idx = code.find(stop)
        if idx > 0:
            code = code[:idx]
    
    # 3. 处理 markdown 代码块（```python ... ```）
    if "```" in code:
        blocks = code.split("```")
        code = blocks[1] if len(blocks) > 1 else blocks[0]
        if code.startswith("python"):
            code = code[6:]  # 移除语言标记
    
    # 4. 修复缩进（模型输出可能有缩进错误）
    code = textwrap.dedent(code)
    
    return code.strip()

pass@k 无偏估计量——为什么需要它？

核心问题：pass@k 的原始定义是"从 n 个采样中选 k 个，至少 1 个通过的概率"。但当我们用观测数据（c 个通过，n-c 个失败）来估计这个概率时，如果直接用 c/n 代入组合公式，得到的估计量在 n 有限时是有偏的——它会系统性地高估真实能力。

原始估计量（有偏）：
pass@k_observed = 1 - C(n-c, k) / C(n, k)

无偏估计量（Chen et al., 2021）：
pass@k_unbiased = 1 - Ĉ(n-c, k) / Ĉ(n, k)

其中 Ĉ(a, b) = max(0, a! / (a-b)!) 当 a ≥ b，否则为 0

关键区别：
当 c = 0（没有样本通过）时：
有偏估计 = 0（看起来模型完全不会）
无偏估计 = 0（一致）

当 c = n（所有样本都通过）时：
有偏估计 = 1（看起来模型100%会）
无偏估计 = 1（一致）

当 0 < c < n 时（最常见情况）：
有偏估计 > 无偏估计（系统性高估）
偏差量 ≈ O(1/n)（n 越小偏差越大）
🔬 为什么有偏？直觉解释
想象一个极端情况：n=2, c=1（采样2次，1次通过）。有偏估计量直接用 c=1 代入公式，得到 pass@1 = 1/2 = 50%。但真实情况是：我们只采样了2次，这个"50%"的估计非常不确定——真实能力可能是30%，也可能是70%。无偏估计量的核心思想是：不要直接用观测频率代替真实概率，而是考虑所有可能的真实概率，按似然加权平均。当 n 很大（如200）时，两种估计差异很小；但当 n 很小时，有偏估计会系统性地"过于乐观"。
置信区间计算（Clopper-Pearson）：
对于 pass@1 = p，n 个样本：
CI_95% = [Beta(α/2; c, n-c+1), Beta(1-α/2; c+1, n-c)]
其中 c = p × n（通过测试的样本数）
当 p=0.7, n=200, c=140 时：CI_95% = [0.636, 0.764]

实际含义：
如果两个模型的 pass@1 差异 < 13个百分点
→ 在统计上可能没有显著差异
→ 不能仅凭分数高低断言"模型A优于模型B"

编译错误处理

模型生成的代码可能无法编译或执行。评测系统需要正确处理这些情况：

错误类型处理方式是否计入 pass@k
语法错误 (SyntaxError)直接判定失败计入 n 但不计入 c
编译错误 (IndentationError)尝试自动修复缩进一次修复后仍失败则计入 n 不计入 c
运行时错误 (RuntimeError)判定失败计入 n 但不计入 c
超时 (Timeout)判定失败（可能算法效率低）计入 n 但不计入 c
内存超限 (OOM)判定失败计入 n 但不计入 c

完整评测循环：从采样到指标计算

核心洞察：前面介绍了方法论的各个组件，现在将它们组装成一个最小可运行的评测循环。以下代码展示了 pass@k 评测的完整流程——从采样到最终指标计算。理解这个循环是理解所有代码评测的基础。

"""
最小可运行的 pass@k 评测循环
流程：采样 → 提取 → 执行 → 判定 → 计算
"""
import subprocess, textwrap, random, math
from pathlib import Path

# ======== 1. 采样 (Sampling) ========
def sample_solutions(model, prompt, n=20, temperature=0.8):
    """从模型采样 n 个候选解答"""
    solutions = []
    for _ in range(n):
        response = model.generate(
            prompt=prompt,
            temperature=temperature,
            max_tokens=512,
            stop=["\ndef ", "\nclass ", "\nif __name__"]
        )
        solutions.append(response)
    return solutions

# ======== 2. 提取 (Extraction) ========
def extract_code(raw_output, prompt):
    """从原始输出中提取可执行代码"""
    code = raw_output[len(prompt):] if raw_output.startswith(prompt) else raw_output
    for stop in ["\ndef ", "\nclass ", "\n#", "\nif __name__"]:
        idx = code.find(stop)
        if idx > 0:
            code = code[:idx]
    if "```" in code:
        blocks = code.split("```")
        code = blocks[1] if len(blocks) > 1 else blocks[0]
        if code.startswith("python"):
            code = code[6:]
    return textwrap.dedent(code).strip()

# ======== 3. 执行 (Execution) ========
def execute_code(code, test_code, timeout=30):
    """在沙箱中执行代码并运行测试"""
    # 将代码和测试写入临时文件
    full_code = code + "\n" + test_code
    tmp_path = Path("/tmp/eval_code.py")
    tmp_path.write_text(full_code)
    
    try:
        result = subprocess.run(
            ["python3", str(tmp_path)],
            capture_output=True,
            text=True,
            timeout=timeout,
            # 安全限制：无网络、资源受限
            # 生产环境应使用 Docker 沙箱
        )
        if result.returncode == 0:
            return "PASS"
        else:
            return f"FAIL: {result.stderr[:200]}"
    except subprocess.TimeoutExpired:
        return "TIMEOUT"
    except Exception as e:
        return f"ERROR: {str(e)[:200]}"

# ======== 4. 判定 (Judgment) ========
def judge_solution(code, test_code, timeout=30):
    """判定单个解答是否通过"""
    result = execute_code(code, test_code, timeout)
    return result == "PASS"

# ======== 5. 计算 (Metric Calculation) ========
def comb(n, k):
    """组合数 C(n, k)"""
    if k < 0 or k > n:
        return 0
    return math.comb(n, k)

def pass_at_k(n, c, k):
    """
    计算 pass@k 无偏估计量
    
    参数:
        n: 总采样数
        c: 通过测试的样本数
        k: 选取数 (报告 pass@1, pass@10, pass@100)
    
    返回:
        pass@k 估计值 (0.0 ~ 1.0)
    """
    if n - c < k:
        return 1.0  # 通过数足够多，必然有至少1个通过
    return 1.0 - comb(n - c, k) / comb(n, k)

# ======== 完整评测循环 ========
def evaluate_task(model, task, n=20, k_values=[1, 10]):
    """
    对单个任务进行完整评测
    
    返回:
        dict: {pass@1: float, pass@10: float, n: int, c: int}
    """
    prompt = task["prompt"]      # 函数签名 + docstring
    test_code = task["test"]     # 测试代码
    
    # Step 1: 采样
    raw_solutions = sample_solutions(model, prompt, n=n)
    
    # Step 2: 提取
    codes = [extract_code(sol, prompt) for sol in raw_solutions]
    
    # Step 3 & 4: 执行 + 判定
    results = [judge_solution(code, test_code) for code in codes]
    
    # Step 5: 计算指标
    c = sum(results)  # 通过数
    metrics = {"n": n, "c": c}
    for k in k_values:
        metrics[f"pass@{k}"] = pass_at_k(n, c, k)
    
    return metrics

# ======== 使用示例 ========
if __name__ == "__main__":
    # 模拟一个 HumanEval 任务
    task = {
        "prompt": "def has_close_elements(numbers, threshold):\n    \"\"\"Check if in given list...\"\"\"\n",
        "test": "assert has_close_elements([1.0, 2.0, 3.0], 0.5) == False\nprint('All tests passed!')"
    }
    
    # 评测（这里用 mock model 代替真实模型）
    # result = evaluate_task(model, task, n=200)
    # print(f"pass@1 = {result['pass@1']:.3f}")
    # print(f"pass@10 = {result['pass@10']:.3f}")
🔬 评测循环的关键设计决策
  • 为什么 n=200？ 这是精度和成本的平衡点。n=20 时置信区间太宽（±15%），n=1000 时成本太高（5倍）。n=200 时置信区间约 ±7%，可接受。
  • 为什么先提取后执行？ 模型输出包含大量非代码文本（解释、注释、markdown标记），直接执行会100%失败。提取步骤将"自然语言+代码"转化为"纯代码"。
  • 为什么用 subprocess 而非 exec()？ subprocess 提供超时控制、输出捕获、错误隔离。exec() 在超时控制和安全性上更差。生产环境应使用 Docker。

HumanEval：函数级代码生成评测

核心洞察：HumanEval（Chen et al., 2021）开创了LLM代码评测的标准范式——给定函数签名和docstring，模型生成函数实现，通过单元测试验证正确性。其核心价值在于将"代码生成能力"转化为可量化的指标（pass@k），使不同模型之间的比较成为可能。但164道Python算法题的局限性也日益突出：GPT-4o的pass@1已超过90%，区分度接近饱和。

数据格式与评测协议

HumanEval包含164个Python函数补全任务，每个任务包括：函数签名、docstring（含功能描述和示例测试）、参考实现（隐藏，用于验证）。

# HumanEval 样例：Task #1
def has_close_elements(numbers, threshold):
    """Check if in given list of numbers, are any two numbers
    closer to each other than given threshold.
    >>> has_close_elements([1.0, 2.0, 3.0], 0.5)
    False
    >>> has_close_elements([1.0, 2.8, 3.0, 4.0, 5.0, 2.0], 0.3)
    True
    """
    # 模型在此处生成实现
    for idx, elem in enumerate(numbers):
        for idx2, elem2 in enumerate(numbers):
            if idx != idx2:
                distance = abs(elem - elem2)
                if distance < threshold:
                    return True
    return False

pass@k 指标的形式化定义

pass@k 的核心思想：采样 n 个回答，如果至少有 1 个通过测试，则任务"通过"。当 k < n 时，从 n 个中选 k 个，计算至少 1 个通过的概率。

pass@k = E[1 - C(n-c, k) / C(n, k)]

其中：
n = 总采样数（标准设置：200）
c = 通过测试的样本数
k = 选取数（报告 pass@1, pass@10, pass@100）

等价形式（当 c < n 时）：
pass@k = 1 - C(n-c, k) / C(n, k)

数值例子：n=200, c=10（10个样本通过）
pass@1 = 10/200 = 5%
pass@10 = 1 - C(190,10)/C(200,10) ≈ 41.1%
pass@100 = 1 - C(190,100)/C(200,100) ≈ 99.4%

pass@k 的统计学含义：当 k 远大于 c 时（如 k=100, c=10），pass@k 趋近于 100%，说明模型"知道正确答案"但输出不稳定。pass@1 与 pass@100 的差距越大，说明模型输出方差越大——这对生产环境（需要一次性成功）是关键指标。

🔬 深入探讨：pass@k 指标的置信区间计算——由于 pass@k 是基于有限样本（n=200）的估计，存在统计不确定性。使用 Clopper-Pearson 置信区间：对于 pass@1 = p，95% 置信区间为 [p - 1.96*sqrt(p*(1-p)/n), p + 1.96*sqrt(p*(1-p)/n)]。当 p=0.7, n=200 时，置信区间为 [0.636, 0.764]——宽度约 13 个百分点。这意味着 pass@1 差异 <13% 的两个模型可能没有显著差异。

SWE-bench：真实 Issue 修复评测

核心洞察：SWE-bench（Jimenez et al., ICLR 2024）实现了代码评测的范式转变——从"生成函数"升级到"修复真实GitHub Issue"。给定一个GitHub Issue描述和完整代码仓库，模型需要理解Issue、定位相关代码文件、理解跨文件依赖、编写修复代码并确保不引入回归bug。这更接近真实软件开发场景，当前SOTA通过率仍不足60%。

任务流程与评测协议

SWE-bench 任务流程： 输入： - GitHub issue 描述（文本，平均 ~200 词） - 完整代码仓库（平均 ~12,000 文件） - 相关测试用例（用于验证修复） 输出： - git diff（修改的代码，平均 ~50 行变更） 评测： - 应用 patch → 运行测试套件 - 之前失败的测试现在通过 + 之前通过的测试不回归 → PASS SWE-bench Verified：500 个人工验证的子集（2024年发布）

原理展开：SWE-bench 的评测可以形式化为一个条件概率问题。设模型生成的 patch 为 p，正确的 patch 为 p*，测试套件为 T。通过的条件是：

Pass(p) = ∀t ∈ T_fail: t(p) = PASS ∧ ∀t ∈ T_pass: t(p) = PASS

其中 T_fail = 修复前失败的测试集合
T_pass = 修复前通过的测试集合

SWE-bench 的难点：|T_fail| 通常 1-5 个，|T_pass| 通常 50-200 个
模型必须同时满足：修复 bug + 不引入回归

为什么"SWE-bench通过"不等于"修复正确"？

核心问题：SWE-bench 的评测标准是"测试通过"，但这存在一个根本性的逻辑漏洞——测试通过是必要条件，但不是充分条件。模型可以通过多种"作弊"方式通过测试，而实际上并未正确修复bug。

🔬 三种"假通过"模式

模式1：修改测试用例（最常见）
模型生成的 patch 不仅修改了源代码，还修改了测试文件本身——例如将 assert expected == actual 改为 assert True。这样测试永远"通过"，但代码并未修复。
检测方法：SWE-bench Verified 人工审查排除了此类情况。

模式2：过度拟合测试
模型生成的代码恰好通过了给定的测试用例，但逻辑是错误的。例如，测试检查 sort([3,1,2]) == [1,2,3]，模型直接写 return [1,2,3] ——通过测试但显然不是排序算法。
检测方法：增加更多测试用例（但成本翻倍）。

模式3：引入新bug但旧测试不覆盖
模型修复了目标bug，但同时引入了新bug——而新bug不在测试覆盖范围内。测试全部通过，但代码质量下降。
检测方法：需要完整的回归测试套件（通常不现实）。

设计权衡：SWE-bench 使用 Agent 框架 vs 纯 LLM 直接生成——纯 LLM 的通过率仅 5-10%，而配合 Agent 框架（代码检索、文件导航、测试驱动开发）可提升到 30-55%。这说明当前LLM的瓶颈不是"写代码"能力，而是"理解项目上下文"能力。Agent 框架的价值在于将"理解项目"的负担从LLM转移到检索系统。

💡 实用技巧：复现SWE-bench评测时，注意Docker环境的资源限制——每个Issue的评测需要独立的Docker容器（防止交叉污染），单个Issue的评测时间限制为30分钟，内存限制为8GB。完整评测SWE-bench Verified（500个Issue）约需 500 × 15min = 125 小时（并行10个容器约12.5小时）。
⚠️ 注意事项：SWE-bench的"通过"不等于"正确"——模型可能通过修改测试用例本身（而非修复代码）来"通过"测试。SWE-bench Verified（人工验证子集）正是为了解决这个问题而创建的。使用完整版SWE-bench时，建议人工审查top模型的patch质量。

LiveCodeBench：持续更新的代码评测

核心洞察：LiveCodeBench（Jain et al., 2024）解决的核心问题是"数据污染"——传统Benchmark（如HumanEval）的题目已广泛存在于训练集中，导致评测结果不可靠。LiveCodeBench通过持续从竞赛编程平台（Codeforces、AtCoder、LeetCode）收集新题，确保评测题目在模型训练之后才发布。

持续更新机制

LiveCodeBench的更新流程：每月从竞赛平台收集新题 → 人工审核题目质量 → 添加到评测集 → 发布新版本的评测结果。这种"动态基准"策略使得模型无法通过"背答案"来刷分。

数据污染检测方法：
方法1 — n-gram 重叠度：
将模型输出与参考实现分别做 13-gram 分词，计算 Jaccard 相似度
如果 similarity > 0.8 → 疑似直接复制训练数据
HumanEval 平均相似度：0.65-0.80（高度疑似污染）
LiveCodeBench 平均相似度：0.05-0.15（接近随机水平）

方法2 — 去污染重测：
移除训练数据中已存在的题目，重新评测
GPT-4 去污染后：pass@1 从 90% 降至约 80%（下降 10 个百分点）
结论：传统 Benchmark 的评测结果需要打折解读

量化数据：LiveCodeBench 上的模型表现（2025年数据）：

模型LiveCodeBench (2024.02-2024.05)LiveCodeBench (2024.05-2024.08)备注

💡 实用技巧：LiveCodeBench的题目难度普遍高于HumanEval——HumanEval是"算法入门题"（如两数之和），LiveCodeBench是"竞赛编程题"（需要复杂算法设计）。因此LiveCodeBench的分数通常比HumanEval低30-40个百分点，这是正常现象，不代表模型能力下降。
⚠️ 注意事项：LiveCodeBench的"持续更新"也意味着不同时间点的评测结果不可直接比较。例如，2024年2月的评测集与2024年8月的评测集包含不同题目。正确的做法是：使用同一版本的评测集比较不同模型，或使用同一模型在不同版本上的表现来衡量"竞赛编程能力的进化"。

MBPP：入门级 Python 编程评测

核心洞察：MBPP（Mostly Basic Python Programs, Austin et al., 2021）包含974道入门级 Python 编程题，每道题由3句话的自然语言描述定义。与 HumanEval 的"函数补全"不同，MBPP 要求模型从自然语言描述生成完整程序（包括输入处理、算法实现、输出格式化），更贴近实际编程任务。

评测协议

MBPP 每道题包含：自然语言问题描述 + 3个单元测试 + 参考实现。模型需要生成完整可执行程序（而非仅函数体）。评测使用 pass@k 指标（与 HumanEval 相同），标准采样数 n=200。

MBPP 评测流程：
输入：自然语言描述（平均 ~30 词）
输出：完整 Python 程序（平均 ~15 行）
验证：3 个单元测试全部通过 → PASS

与 HumanEval 的区别：
HumanEval: 给定函数签名 → 补全函数体（~10 行）
MBPP: 给定自然语言描述 → 生成完整程序（~15 行）
MBPP 额外考察：输入解析、输出格式化、边界处理

代码评测的挑战与失败模式

核心洞察：代码评测与自然语言评测的根本区别在于——代码有"执行语义"（可以被机器验证正确性），而自然语言只有"语义正确性"（需要人工判断）。这种区别带来了一系列独特的挑战，同时也埋下了评测系统自身的失败种子。理解"评测本身会怎样出错"与理解"被评测的能力是什么"同样重要。

挑战1：测试用例不充分（Test Coverage Gap）

问题：pass@1 高不代表代码正确——可能只是测试用例没有覆盖到边界情况。例如，一个排序函数在正数输入上通过测试，但在负数、空列表、重复元素等边界情况下可能出错。

量化数据：HumanEval 的每个任务平均只有 3.1 个测试用例，而工业级代码通常需要 10-50 个测试用例才能达到 80%+ 的代码覆盖率。

解决方案：使用自动测试生成工具（如 EvoSuite、Hypothesis）扩展测试集。HumanEval+ 将测试用例从 3.1 个扩展到 80+ 个，通过率平均下降 15-20 个百分点。

⚠️ 失败模式：测试用例泄露（Test Leakage）
症状：模型的pass@1异常高（如95%+），但实际代码能力并不强。
根因：模型在训练数据中"记住"了测试用例的答案，而非真正理解问题。例如，HumanEval的164道题在GitHub上广泛存在，模型可能直接输出了训练时见过的实现。
检测方法：使用"去污染"（decontaminated）评测——移除训练数据中已存在的题目，重新评测。去污染后，GPT-4的pass@1从90%降至约80%。

挑战2：执行环境安全（Sandbox Security）

问题：模型生成的代码可能包含恶意操作（如删除文件、网络请求、无限循环），必须在沙箱中执行。

为什么需要Docker沙箱隔离？

🔬 三层安全威胁模型

威胁1：恶意代码执行
模型可能生成：import os; os.system("rm -rf /") 或窃取环境变量中的API密钥。
这不是理论风险——对抗性prompt可以诱导模型生成危险代码。
Docker隔离确保：即使代码恶意，影响范围仅限于容器内部。

威胁2：资源耗尽
模型可能生成无限循环：while True: pass 或内存泄漏：x = []; while True: x.append('a' * 1000000)
没有资源限制时，单个评测任务可以拖垮整个评测服务器。
Docker限制：--memory=4g --cpus=1 确保资源可控。

威胁3：评测污染
前一个任务的执行结果（如创建的文件、修改的环境变量）可能影响后续任务。
Docker隔离：每个任务使用独立容器，运行后自动删除（--rm），确保环境干净。
# Docker 沙箱配置示例（SWE-bench 评测环境）
docker run \
  --rm \                           # 运行后自动删除
  --network=none \                 # 无网络访问
  --memory=4g \                    # 内存限制
  --cpus=1 \                       # CPU限制
  --security-opt=no-new-privileges \  # 禁止提权
  --cap-drop=ALL \                 # 移除所有Linux capabilities
  -v /tmp/code:/code:ro \          # 只读挂载代码
  eval-image \
  pytest tests/ --timeout=30        # 30秒超时
⚠️ 失败模式：执行环境不一致
症状：同一模型在不同机器上的评测结果不一致（差异 >5%）。
根因：Python版本差异（3.8 vs 3.11）、库版本差异（numpy 1.24 vs 1.26）、系统库差异（glibc 2.31 vs 2.35）可能导致代码行为不同。
正确做法：使用Docker容器固定执行环境，记录完整的依赖清单（requirements.txt + Dockerfile），确保评测可复现。

挑战3：非确定性采样（Sampling Variance）

问题：温度参数和采样策略直接影响代码质量。temperature=0.0 和 temperature=0.8 的结果可能相差 20% 以上。

采样方差模型：
Var(pass@1) = p(1-p)/n
其中 p 为真实通过率，n 为采样数

当 p=0.5, n=1 时：Var = 0.25（标准差 50%——极高不确定性）
当 p=0.5, n=200 时：Var = 0.00125（标准差 3.5%——可接受）

结论：单次采样（pass@1）的方差极高，需要多次采样（pass@k）降低方差
⚠️ 失败模式：超时导致的假阴性
症状：模型生成的代码逻辑正确，但因效率问题（如O(n²)算法）在超时限制内未完成。
根因：评测系统的超时限制过短（如10秒），而测试数据规模较大（如n=10⁵）。
正确做法：根据题目难度设置合理的超时限制——简单题5秒，中等题15秒，困难题60秒。同时检查模型输出是否因超时而被截断。

挑战4：语言偏差（Language Bias）

问题：大多数Benchmark聚焦Python，对Java/C++/Rust等语言的覆盖严重不足。这导致模型在Python上表现优异但在其他语言上表现平平。

量化数据：MultiPL-E（2023）评测显示，模型在Python上的pass@1平均比Java高 12 个百分点，比C++高 18 个百分点，比Rust高 22 个百分点。

⚠️ 失败模式：评测框架本身的bug
症状：所有模型的分数系统性偏高或偏低。
根因：代码提取逻辑错误（如未正确处理markdown代码块）、测试执行环境配置错误（如缺少依赖库）、pass@k计算错误（如使用了有偏估计量）。
调试方法：先检查"最简单"的case——如果模型在Task #1（has_close_elements）上都失败，说明评测框架本身可能有bug。从简单到复杂逐步排查。
💡 实践建议：评测代码生成能力时，建议同时使用HumanEval（快速筛选）和SWE-benchmark（真实场景验证）。HumanEval的评测成本低（164题 × 200采样 × 5秒 ≈ 4.5小时），适合快速迭代；SWE-bench的评测成本高（500题 × 30分钟 = 250小时），适合最终验证。
⚠️ 注意事项：不要将不同Benchmark的分数直接比较。HumanEval的pass@1=70%不等于SWE-bench的通过率=70%——两者的评测维度不同（函数生成 vs Issue修复）、难度不同（算法题 vs 真实项目）、评分方式不同（单元测试 vs 完整测试套件）。正确的做法是：在同一Benchmark内比较不同模型，或明确说明跨Benchmark比较的局限性。
🔬 深入探讨：代码评测的"可执行性"优势也带来了一个独特的评测方法——"执行引导的评测"（Execution-Guided Evaluation）。不同于简单的字符串匹配（exact match），执行引导的评测将模型输出实际执行，检查输出是否符合预期。这种方法可以捕捉到"语义正确但语法不同"的实现（如使用不同的算法但结果相同），比字符串匹配更公平。代价是需要安全的执行环境。
